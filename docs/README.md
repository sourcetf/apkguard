# 落地方案文档

这些文档是**动手前的设计**：每个未实现（或已实现但有明确边界）的功能项一份，
内容包含技术方案、与现有 Pass 的交互与注册顺序、可自动化断言的验收标准、
风险与取舍、**最小可落地子集**、以及工作量估计。

写它们的目的是让「下一步做什么」有据可依，也让**为什么不这么做**被记下来——
后者往往更有价值（例如 A6 与 C2 的取舍、B7 需要 NDK 的交付约束）。

| 文档 | 内容 | 结论摘要 |
|---|---|---|
| [`方案-A6-控制流混淆.md`](方案-A6-控制流混淆.md) | 基本块平坦化、不透明谓词、指令替换 | 方案完整，但落地后实测会破坏真实应用，已退回「未实现」（见实测记录第三轮） |
| [`方案-A7-反射化调用.md`](方案-A7-反射化调用.md) | 将敏感调用改为 `Class.forName` + `invoke` | 最大基建改动是给注入方法加异常表（现有 `CodeBlob` 不支持），注册位置必须在 A2 之前 |
| [`方案-B5-函数抽取.md`](方案-B5-函数抽取.md) | 清空 CodeItem、运行时 native 回填 | 必须用「等长合法 stub」；回填的可靠时机是覆写 `DexClassLoader.findClass`，「内存里永远是空方法体」的说法不成立 |
| [`方案-B6-VMP.md`](方案-B6-VMP.md) | 私有指令集 + VM 解释器 | 私有指令是数据、解释器是固定 C 代码，因此**不需要 NDK**；不用 RegisterNatives |
| [`方案-B7-Dex2C.md`](方案-B7-Dex2C.md) | Java → C → SO | 短期不现实：本项目定位是「单二进制、预编译 native 库、无需 NDK」，B7 是第一个要求用户装 NDK 的功能 |
| [`方案-C2-SO加壳.md`](方案-C2-SO加壳.md) | 原生库加密 | **已实现整文件形态**；段级加密在「由同一个 .so 的 JNI_OnLoad 解密」下时序不可行 |
| [`方案-C3-OLLVM.md`](方案-C3-OLLVM.md) | native 代码的控制流平坦化 | 唯一现实落点是 C 源码层变换，且作用对象只能是我们自己的守卫库，价值有限 |
| [`方案-成员名覆盖率.md`](方案-成员名覆盖率.md) | 成员改名的根本性改进 | **已实现**（按 (类,名字) 引用决策 + 追加字符串通道），覆盖三类可证明安全的成员 |
| [`方案-包合并.md`](方案-包合并.md) | 进一步合并包名 / 提高默认包比例 | 合并与拆分不对称：合并只放宽访问权限，真正的风险是 package-private 方法**凭空生成覆写** |
| [`方案-载荷完整性.md`](方案-载荷完整性.md) | 载荷 MAC / AEAD | **已实现** HMAC-SHA256（encrypt-then-MAC）；不换 GCM 的原因与确定性 IV 有关 |
| [`方案-资源内容加密.md`](方案-资源内容加密.md) | 加密资源内容 | `resources.arsc`/Manifest/系统解析的 res/ 都不能加密；可行路线只有「只加密 assets（可选 res/raw）」 |
| [`方案-双APK架构.md`](方案-双APK架构.md) | 外层壳 + 内层完整 APK（样本做法） | **不推荐**：投放器模式，需安装权限与系统安装界面，受 Android 10+ 后台安装限制，且违反商店政策 |

> 样本 `sample.apk` 就是双 APK 架构，我们逐条评估后认为：它在「省掉就地资源改写」
> 上的收益被组件代理、体积翻倍与首启耗时抵消，因此维持现有的「逐 DEX 加密 +
> 进程内 ClassLoader 接管」架构。
