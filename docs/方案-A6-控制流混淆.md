## 1. 目标与预期效果

### 1.1 要防住的分析手法

A6 针对的是**基于控制流图（CFG）的静态理解**，而不是名称或字符串：

| 分析手法 | A1/A2/A3 是否防住 | A6 是否防住 |
|---|---|---|
| 按类名/方法名定位核心算法 | ✅ | 无关 |
| `strings` / 字符串池提串 | ✅ | 无关 |
| jadx/JEB 反编译后按 CFG 顺序阅读业务逻辑 | ❌ 逻辑仍线性可读 | ✅ 打散为 dispatcher + switch |
| 自动化工具（Flutter/JEB 脚本）做支配树/循环识别 | ❌ | ✅ 平坦化后循环结构消失 |
| 对关键常量/算法做数据流常量折叠 | ❌ | ⚠️ 不透明谓词制造假分支干扰 |
| 按调用图定位敏感 API | ❌ | 由 A7 负责，A6 不涉及 |

A6 **不防**：动态调试、内存 dump、Frida hook（那是 C4/C5/D4 的职责）；也不防
「耐心的人工逐块阅读」——它提高的是**自动化与半自动化的成本**，不是绝对不可读。

### 1.2 预期效果如何量化

对齐设计文档「性能下降 10~30%」，并给出可测指标：

- **平坦化覆盖率**：满足门槛的方法中，`packed-switch`（操作码 0x2b）数量应
  从 0 增至「被平坦化方法数」；每个被平坦化方法至少 1 个 dispatcher switch。
- **原 CFG 边消失率**：被平坦化方法内，原始无条件 `goto`（0x28/0x29/0x2a）与
  顺序落空（fallthrough）边中，经 dispatcher 中转的比例 = 100%（最小切片只保证
  goto + fallthrough，见 §6）。
- **不透明谓词注入量**：每个被平坦化方法注入 1~3 组恒真谓词，产物中该谓词
  特征指令序列（`mul-int` + `sub-int` + `and-int/lit8` + `if-eqz`）出现次数 ≥ 方法数。
- **语义不变**：用 `internal/dex/interp_test.go` 的解释器对改写前后逐方法执行，
  返回值/寄存器快照逐条一致（这是硬指标，不是抽样）。
- **性能**：单次 dispatcher 往返约多 3~5 条指令；只在**冷路径/关键方法**上启用，
  避免热循环方法。可用 Android Studio profiler 或方法级计时对比，目标 <30%。
- **体积**：每方法增加约 10~25 字（dispatcher + 各块回边 + payload），全量启用
  时 DEX 增长约 3~8%。

### 1.3 非目标

- 不做 VMP（B6）、不做函数抽取（B5）；A6 只改「指令顺序与分派」，不隐藏指令语义。
- 不保证对抗「先脱壳再平坦化逆向」；A6 与 B1 组合后防护面才完整。

## 2. 技术方案

### 2.1 基本块如何识别

不引入独立 CFG 库，直接复用 `InsnList` 已有的分支信息。`ParseInsns` 已经把
`goto`(0x28/0x29/0x2a)、`if-*`(0x32~0x3d)、`fill-array-data`(0x26)、
`packed-switch`(0x2b)、`sparse-switch`(0x2c) 记录为 `branchRef`，并把 switch
payload 的 target 换算成绝对旧字偏移。基本块划分如下：

**leader 集合**（块的首指令旧字偏移）：

1. 方法首条指令（偏移 0）；
2. 所有 `branchRef.target`（含 switch payload 内部 target）；
3. 所有 try_item 的 `StartAddr` 与 `StartAddr+InsnCount`（端点必须落在边界上，
   这是 `encryptCodeItem`/`arrayizeCodeItem` 已经依赖的不变量）；
4. 所有 `CatchHandler.Addrs` 与 `AllAddr`（异常处理器入口）；
5. 任意「终结指令」之后的下一条指令：终结指令 =
   `goto/goto16/goto32`、`if-*`、`return*`(0x0e~0x11)、`throw`(0x27)、
   `switch`（payload 之后的第一条）；
6. **不得**把 `move-result*`(0x0a~0x0c) 当作独立块首：它与前一条 `invoke` 必须
   紧邻，拆开会触发 ART
   `VerifyError: move-result-object not immediately after invoke`。

块 = 相邻 leader 之间的指令区间。switch/fill-array-data 的 payload 属于
「引用它的那条指令所在块」的尾部，不能单独成块。

识别只读 `ItemOldOffset` / `ItemWords`，不改动 `InsnList`；判定结果是一组
「旧字偏移 → 块号」的映射，作为后续插入的锚点。

### 2.2 平坦化后 dispatcher 的形态

采用**不物理重排块顺序**的平坦化（原因见 §5）。在方法入口插入：

```
; ---- 方法入口新增 ----
const/4   vS, #entryBlockId          ; 状态变量
:disp
packed-switch vS, :dispatch_payload  ; 0x2b，格式 31t，3 字
; ---- 原块 0 的物理位置不变 ----
...原指令...
; ---- 原块 k 的出口改写 ----
const/4   vS, #succBlockId
goto/16   :disp
; ---- 原块 k+1 ... ----
...
; ---- 方法末尾追加 ----
:dispatch_payload
packed-switch-payload                ; ident=0x0100, size=N, targets[N]
```

- **dispatcher 的每个 case 目标**直接指向对应块的首指令旧偏移（不重排时块首就是
  原指令项），因此不需要为 case 生成跳板。
- 每个原块的**出口**改为：先 `const vS, #succId`，再 `goto :disp`。
  - 原块以无条件 `goto` 结尾：把该 `goto` 的目标改指向 `:disp`，并在它之前插入
    `const vS,#succId`（succId = 原 goto 目标所在块）。**不能**直接删除原 goto
    后依赖 fallthrough——原 goto 目标可能不是物理相邻块。
  - 原块以 `if-*` 结尾：最小切片**保留** `if-*` 直连原目标（true 边不经过
    dispatcher），只把 fallthrough 边改为 `const vS,#fallId; goto :disp`；
    完整版把 true 边也改成「跳板块」再进 dispatcher。
  - 原块以 `return*` / `throw` 结尾：不改（无后继）。
  - 原块正常 fallthrough：在下一块 leader 之前插入 `const vS,#succId; goto :disp`
    （用 `InsertBefore`，锚定下一块 leader，语义是「跳过插入项落到 leader」）。
- **switch 的处理**：最小切片**跳过含 switch 的方法**（原因见 §5）。完整版需把
  原 `packed-switch`/`sparse-switch` 的每条 payload target 改成跳板块；payload 的
  owner 关系必须通过 `InsnList.payloadOwner` 维护。
- 状态变量用 `const/4`（≤15 个块）或 `const/16`；块数超过 0x7fff 的方法直接跳过。

### 2.3 不透明谓词怎么选

**硬约束：谓词必须 (a) 无池引用、(b) 不抛异常、(c) 结果恒真、(d) 不依赖未初始化
寄存器、 (e) 不引入除法/取余（除零抛 `ArithmeticException`）、(f) 不改动 `ins`
参数寄存器。**

推荐模板（32 位 int 溢出回绕不影响恒真性）：

```
; vP = (c*c - c) & 1  —— 对任意 int c，c*(c-1) 恒为偶数，故 vP 恒为 0
const/16  vP, #c              ; c 由种子随机选取，可为任意 16 位值
mul-int   vP, vP, vP          ; vP = c*c（溢出回绕仍为整数）
sub-int   vP, vP, vC          ; vC 预先 = c；得 c*c - c
and-int/lit8 vP, vP, #1       ; 取最低位，恒 0
if-eqz    vP, :real           ; 恒成立，跳转目标即原入口块
; 不可达的假分支（可选，制造 BCF）
goto/16   :decoy
```

- 为什么选这个模板：`mul/sub/and/if-eqz` 全部是纯整数运算，ART 校验器不做常量
  折叠，反编译器要证明 `c(c-1)` 恒偶需要算术推理；同时**不会**产生任何新的
  字符串/类型/方法引用，因此不干扰 A2/A3 的池处理，也不会被 `remapCode` 误改。
- 假分支（`:decoy`）里只放**不改变可达状态**的指令（如 `const/4 vD,#0; goto :real`
  或写一个恒被覆盖的临时寄存器），且不得以 `return`/`throw` 结尾，否则会改变语义。
- 谓词插入位置：方法入口、以及若干块的入口；**绝不插入** invoke 与 move-result
  之间，也绝不插入 switch 与 payload 之间。
- 因为最小切片跳过含 try 的方法，谓词不会落进 try 区间；完整版若要在 try 内插入，
  谓词的无异常性保证不扩大 catch 覆盖，但 try 端点仍必须映射到指令边界
  （依赖 §2.5 的锚点规则）。

### 2.4 指令替换的等价性要求

指令替换（SUB）只在**纯整数/纯位运算、无副作用、不抛异常、不涉及池引用**的指令上做。
典型等价式：

| 原指令 | 替换 | 成立条件 |
|---|---|---|
| `add-int vD,vA,vB` | `sub-int vD,vA,vN`（vN = `neg-int vB`） | 仅 32 位 int；`vN` 为临时寄存器 |
| `add-int/lit8 vD,vA,#k` | `sub-int/lit8 vD,vA,#-k` | k ∈ [-128,127] |
| `xor-int vD,vA,vB` | `xor-int vD,vA,vB` 保持 | 无更简等价，不建议强改 |
| `shl-int vD,vA,#k` | `mul-int vD,vA,vPow2` | k ≤ 15，且 `vPow2=1<<k` 可安全编码 |

**必须同时满足**：

1. 操作数位宽不变（int 只能换 int，long 用 `add-long/sub-long`，不得混用；
   float/double 不得用位运算替换）；
2. 不改变 `vD` 之外任何寄存器的最终值；
3. 不引入新的控制流终结指令，不改变 fallthrough 关系；
4. 不改变异常可见性：替换序列中任何一条都不得可能抛异常（因此禁用 div/rem、
   字段访问、数组访问、类解析）；
5. 不破坏 invoke/move-result 邻接、switch/payload 邻接；
6. 每条替换后仍可被 `InsnList.Encode` 正确编码（宽度变化会触发 `goto` 加宽，
   这由引擎自动处理，但替换不得让 `if-*` 的 16 位范围溢出，超出则放弃该替换）。

### 2.5 与 `insn.go` 的 try_item / handler_off / 分支重定位协作

A6 不新写偏移修正逻辑，全部交给现有 `InsnList.Encode()`：

- **插入锚点**：用 `InsertBefore(i, ...)` 时，插入项与原第 i 项共享同一 `old`
  偏移；`Encode` 建立的 `old2new` 映射中，后出现的原项覆盖同 `old` 的值，因此
  「原本指向第 i 项的分支」在重定位后落到**原第 i 项**（跳过插入项），语义不变。
  这正是 `ReplaceWithArrayData` 依赖的机制。A6 必须利用它来保证
  「块 leader 的旧偏移 → 新偏移」稳定。
- **合成项的旧偏移**：dispatcher 的 switch 指令、payload、跳板块没有原始项，
  必须分配**唯一**的合成旧偏移（沿用 `InsnList.synth` 计数，从 `total` 之后取），
  否则无法被分支指向。需要在 `InsnList` 上补一个「插入合成项并返回其旧偏移」的
  方法（现有 `ReplaceWithArrayData` 是特例，不能直接复用于任意合成序列）。
- **分支重定位**：dispatcher 的 `packed-switch` 必须以 `branchRef{form:form31t}`
  登记，`target` = payload 合成旧偏移；payload 内每条 target 以
  `branchRef{form:formPayload}` 登记，且 `payloadOwner[payloadOld] = switchItem`。
  这样 `Encode` 才会按「相对 switch 指令」而非「相对 payload」重算偏移——
  DEX 规范如此，写错会被 ART 判 `invalid switch target`。
- **try / handler_off**：`CodeItemFull.Encode` 会用 `old2new` 修正 try 区间端点与
  处理器目标地址，并用 `HandlerOffs`（解析时的字节事实）重算 `handler_off`。
  因为 A6 只插入、不删除、不重排，所有原 try 端点/处理器入口都保留原 `old`，
  映射稳定；插入项又都是无异常指令，不改变 catch 覆盖语义。
  **不要**手工改 `ci.Tries`；改完 `ci.Insns` 后直接调用
  `ci.Encode(func(old uint32) uint32 { return FixAddr(m, old) })` 即可。
- **payload 对齐**：`Encode` 会在非指令项（payload）前自动补 nop 保证 4 字节对齐，
  A6 的 dispatcher payload 沿用同一机制，不要自己算对齐。

### 2.6 寄存器预算（最容易炸的一环）

**绝对不能在 A6 里增大 `registers_size`。** Dalvik 的入参寄存器是
`v(regSize-ins) .. v(regSize-1)`：一旦把 `registers_size` 从 R 增到 R+k，所有
入参寄存器整体后移 k，而原指令仍引用旧编号，结果是
「方法读到错误的参数」——本地解释器可能恰好不报错，真机 ART 直接
`VerifyError` 或运行结果错乱。现有 `A2/A3` 都不改 `Registers`，A6 也必须保持。

因此状态变量与临时变量**只能从方法内未使用的局部寄存器里取**：

1. 扫描方法内全部指令的寄存器操作数（按 `insnWidths` 逐条解码各格式的 vA/vB/vC
   字段），得到「被读或被写」的寄存器集合 `used`；
2. 候选集 = `[0, registers_size - ins)` 且 `∉ used` 且 **编号 ≤ 15**（因为
   `packed-switch` 的 vAA 是 8 位，但反射/数组类指令在 A7 里受 4 位限制；
   A6 的 `const/4`/`if-*` 可用 ≤15，`const/16` 可到 255。为统一与安全，
   A6 状态变量优先取 ≤15）；
3. 需要 1 个状态变量 `vS` + 1~2 个谓词临时寄存器；候选不足则**跳过该方法**，
   不要尝试复用仍活跃的寄存器；
4. 若确实需要更多寄存器，唯一安全做法是「整体寄存器重编号」（把所有引用偏移
   到高编号再腾出低位），但这属于重写方法体级别的改动，风险与工作量都大，
   列入完整版的可选增强，不进最小切片。

### 2.7 实现落点（建议）

- 在 `dex.RebuildOptions` 增加 `ControlFlow *ControlFlow`（与 `StringEncrypt`/
  `ConstantArray`/`ClassPad` 同构），`buildPlan` 记录为 `pl.controlFlow`。
- 在 `builder.generate` 第 3 步 code_item 循环里，与 `encryptCodeItem`/
  `arrayizeCodeItem` 并列增加 `flattenCodeItem(pl, blob)`：解析 → 划分块 →
  插入 dispatcher/谓词 → 改写出口 → `InsnList.Encode` → 返回新 blob。
  处理顺序放在 A2/A3 之后（见 §3），因此它看到的是已经改写过的稳定字节流。
- 统计信息（平坦化方法数、注入谓词数、跳过的原因分布）走 `RebuildStats`，
  与 `StringsEncrypted`/`StringsArrayized` 同一风格。
- Pass 层（`internal/passes/`）新增 `controlFlow`，注册方式见 §3。

## 3. 与现有 Pass 的交互与执行顺序

`passes.go` 的注册顺序即执行顺序。当前 L1 块为：

```
renameClass(A1) → encryptString(A2) → constantArray(A3) → classPad(A13)
→ dropDebugInfo(A4) → fakeDex(A9) → junkEntries(A10) → zipPathAttack(A12)
→ resourceObf(A5) → resourceFlatten(A11) → decoyClass(A8)
```

**建议把 A6 注册在 `dropDebugInfo`(A4) 之后、`fakeDex`(A9) 之前**：

```go
r.Register(&renameClass{})    // A1
r.Register(&encryptString{})  // A2
r.Register(&constantArray{})  // A3
r.Register(&classPad{})       // A13
r.Register(&dropDebugInfo{})  // A4
r.Register(&controlFlow{})    // A6  ← 新增，必须在 A1/A2/A3/A4 之后、B1 之前
r.Register(&fakeDex{})        // A9
...
```

理由（每条都是硬约束）：

1. **必须在 A1 之后**：A1 会重建索引表并改写全部方法/字段引用。A6 通过
   `ParseInsns` + `Rebuild` 处理，若排在 A1 前，A6 重建后 A1 再重建一次也没问题，
   但 A1 的改名白名单会扫描 `const-string` 类名——A6 不新增字符串，无影响；
   真正的理由是**减少无谓的重复重建**，且 A6 的分支/块分析在改名后更稳定。
2. **必须在 A2/A3 之后**：A2/A3 会把 `const-string` 替换成
   「`const-string/jumbo` 密文 + `invoke-static` 解密 + `move-result-object`」。
   若 A6 排在 A2 之前，A2 会在已平坦化的代码里插入指令，虽然 `Encode` 能处理，
   但 A6 的「块出口改写」与 A2 的「指令项替换」会互相干扰（A2 替换会改变项长度，
   使 A6 记录的合成偏移与块出口布局失效）。排在 A2/A3 之后，A6 面对的是最终
   指令流，只做控制流改写，最稳。
3. **必须在 A4 之后**：A4 丢弃 `debug_info` 与 `source_file_idx`。A6 会大幅平移
   指令地址，若 debug_info 还在，行号表会指向错位地址（虽然 ART 不严格校验，
   但反编译视图会出现错乱行号，且 A4 若排在 A6 后又要再重建一次）。排在 A4 后，
   A6 的重建直接继承「无 debug_info」的状态。
4. **必须在 B1 之前**：B1 把明文 DEX 加密成 assets 载荷并移除明文条目；A6 是
   DEX 层改写，B1 之后就没有明文 DEX 可改了（要改只能解密-改-重加密，破坏
   B1 的设计）。因此 A6 必须在 B4/B1 之前完成。
5. **与 A8/A13 的先后**：A8 诱饵类、A13 膨胀类都是**注入类**，其方法体由
   `CodeBlob` 生成、不含 try、结构简单。A6 排在 A8 之前则不会处理它们（省时、
   避免把注入的诱饵方法也改乱）；A6 排在 A13 之后（A13 在 A6 前）则会把膨胀类
   也纳入候选，浪费体积且无收益。因此 A6 放在 A13 之后、A8 之前是最优区间——
   即 A4 之后即可（A13 本来就在 A4 前）。
6. **与 D1/C1 等运行时防护**：它们注入的是壳 DEX 里的类（B2 之后才存在），
   A6 排在 B2 之前，天然不会碰壳代码（壳代码不能混淆控制流，否则排障困难）。

**若实现为独立 Pass 而非 RebuildOption**：仍需满足同样的相对顺序，且要在每次
`Rebuild` 后调用 `dex.Verify` 与结构自检；两种实现方式的顺序结论一致。

## 4. 验收标准（可自动化断言）

对齐现有守卫风格：`branch_test.go` / `handler_test.go` / `outs_test.go` 都在
**产物 DEX 字节**上做结构体检。A6 新增守卫建议命名 `cff_test.go`，全部用
`t.Errorf` 而非只 `Log`，失败信息必须写清「ART 会怎么报」。

### 4.1 结构性判据（每条对应一类回归）

| # | 判据 | 自动化做法 | 防住的回归 |
|---|---|---|---|
| 1 | **分支目标集合不变** | 对每个被改写方法，改写前记录「原块 leader 旧偏移集合」，改写后重解析并断言该集合 ⊆ 合法分支目标集合（`checkBranchTargets` 的 `starts`）；且每个 leader 仍是某条指令/合成项起点 | 偏移算错、跳进指令中间（ART `invalid branch target`） |
| 2 | **所有分支仍落在指令边界** | 复用 `checkBranchTargets`，断言产物中 checked 分支数 > 0 且零 `Errorf` | `goto` 加宽/相对偏移算错 |
| 3 | **try 区间端点仍在指令边界** | 复用 `checkTryHandlers`；额外断言被改写方法的 `len(Tries)` 与改写前一致，端点经 `old2new` 映射后仍等于某指令项起点 | 插入项破坏 try 端点 → ART `Bogus handler offset` 丢整个 DEX |
| 4 | **`handler_off` 仍指向处理器起点** | `checkTryHandlers` 已覆盖（用解析字节事实 `HandlerOffs`） | 地址 ULEB 变长导致处理器后移 |
| 5 | **`dex.Verify` 通过** | 每次 `Rebuild` 后调用 `dex.Verify`（SHA-1 + Adler-32），失败即 fail | 产物校验和/签名不自洽，加载即拒 |
| 6 | **描述符合法** | 调用 `dex.ValidateDescriptors` | 合成项误写类型描述符 |
| 7 | **`outs_size` 不变且足够** | A6 不新增 invoke，断言被改写方法 `Outs` 与改写前相同；复用 `checkOutsOf` | 误插 invoke 未更新 outs → `VerifyError` |
| 8 | **`registers_size` 不变** | 断言被改写方法 `Registers` 与改写前完全相同 | 增大寄存器导致入参错位（最危险的一类） |
| 9 | **invoke/move-result 邻接** | 扫描：每条 `invoke-*` 若其结果被使用，下一条必须是 `move-result*`；被改写方法内不出现「move-result 不是紧跟 invoke」 | 块首切分到 move-result → `VerifyError` |
| 10 | **switch/payload 邻接与 owner** | 每个 `packed-switch`(0x2b) 的 31t 目标指向一个 `0x0100` payload；payload 内 target 相对 switch 指令解码后落在合法边界 | ART `invalid switch target` |
| 11 | **产物形态出现 N 次** | 统计产物中 `0x2b` 数量 ≥ 被平坦化方法数；谓词特征序列（`mul-int`+`sub-int`+`and-int/lit8`+`if-eqz` 连续出现）≥ 方法数；`A6.methods`/`A6.preds` 统计与之一致 | 「启用了 A6 但产物里没有任何平坦化」——功能项声明已实现、退出码 0、实际无效 |
| 12 | **语义等价** | 用 `interp`（`internal/dex/interp_test.go`）对改写前/后的方法用同一组参数执行，断言返回值与关键寄存器快照一致 | 谓词非恒真、块出口 succId 映射错误、指令替换不等价 |

### 4.2 端到端 / 真机判据

- **ART 结构校验**：`dex2oat --compiler-filter=verify` 通过是**必要非充分**——
  README 已明确它对 `handler_off`、`static_values` 这类错误会 rc=0 漏报。
  因此必须叠加：模拟器装机 + `adb logcat` 断言无
  `VerifyError` / `invalid branch target` / `Bogus handler offset` /
  `FATAL EXCEPTION`，并断言进程存活。这条对应现有
  `scripts/device-test.sh` 的判定方式（「被检测拦停」与「结构损坏崩溃」分开）。
- **三真实应用回归**：Termux / Dhizuku / RustDesk（Flutter）在启用 A6 后必须
  仍正常运行；Dhizuku 的类型索引 >127，能触发 ULEB 边界类缺陷；RustDesk 含大量
  try/catch 与 goto，是分支/异常表重定位的压力样本。
- **`go test ./...` 全绿**，且新增守卫在干净检出（`testdata/` 固件）下真正执行，
  不允许静默 `t.Skip`。

## 5. 风险与取舍

### 5.1 明确会破坏产物、不能做的做法

1. **增大 `registers_size`**：入参寄存器整体后移，原引用失配 → 参数读错 /
   `VerifyError`。必须复用未使用局部寄存器，不足则跳过。
2. **物理重排基本块**：`InsnList` 只支持插入与单条替换，`Encode` 依赖
   「`items` 按 `old` 递增」来推导流末尾（它取「最后一个 `old ≤ total` 的项的新终点」
   作为异常表区间端点映射）。重排会破坏这个假设，导致 try 端点映射到错误位置。
   要做重排必须同时改 `Encode` 的末尾推导逻辑，风险高，不进最小切片。
3. **在 invoke 与 move-result 之间插入指令**：ART 判
   `move-result-object not immediately after invoke`，整个类被拒。块划分时必须把
   move-result 并入前一块，插入点只能在块边界。
4. **拆分 switch 与 payload**：payload 是内联伪指令，owner 关系记录在
   `payloadOwner`；若在两者之间插入或把 payload 当普通指令处理，会算错
   `payloadWidth` 与 target 基准（规范要求 target 相对 switch 指令，不是相对 payload），
   ART 报 `invalid switch target`。
5. **在 try 区间内插入可能抛异常的指令**：会改变 catch 覆盖（原本不抛的现在抛、
   或处理器被意外触发）。A6 插入的指令必须无异常；最小切片直接跳过含 try 的方法。
6. **用 div/rem 构造谓词**：除零抛 `ArithmeticException`，等于给方法凭空加了一个
   异常出口；且 ART 不会折叠，编译器可能优化掉。
7. **依赖 `dex2oat --compiler-filter=verify` 当唯一验收**：它对结构性错误漏报，
   必须叠加产物级守卫与真机 logcat。
8. **在 A2/A3 之前跑 A6**：A2/A3 的指令替换会改变项长度，使 A6 预先计算的合成
   偏移与出口布局失效（见 §3 理由 2）。
9. **混淆壳代码（B2 之后）**：壳 Loader/Application 需要可读以便排障（`-debug-shell`），
   且 A6 在 B1 之前就结束了，天然不碰。

### 5.2 取舍

- **覆盖率 vs 安全**：为通过 ART 校验，最小切片放弃「含 try 的方法」「含 switch 的
  方法」「寄存器不足的方法」。真实应用中这三类占比不低（RustDesk 遍布 try），
  因此最小切片的效果有限，但保证不破坏产物。
- **强度 vs 性能**：不透明谓词与 dispatcher 往返使方法变慢 10~30%。设计上只建议
  对关键方法启用；但本项目没有「按方法白名单」配置项，需要新增
  `-cff-keep`/`-cff-only` 之类的过滤（见 §6）。
- **不重排的代价**：块在磁盘上仍保持原顺序，静态分析者仍能看到「相邻块」的线索，
  防护弱于经典 CFF；换来的是对现有 `InsnList`/`Encode` 的零破坏。完整版再评估重排。
- **指令替换收益有限**：Dalvik 是栈式寄存器字节码，`add→sub` 这类替换对反编译
  器几乎无压力（JEB 会还原），主要价值是配合不透明谓词制造噪声，不应作为主要手段。

## 6. 最小可落地子集

**第一个可交付切片（M1）**，能独立验证、不破坏现有三个真实应用的运行：

范围：

- 只处理满足全部条件的方法：
  - `tries_size == 0`（无异常表）；
  - 方法内**没有** `packed-switch`/`sparse-switch`/`fill-array-data` payload；
  - 指令项数 ≤ 80，块数 ≤ 15（可用 `const/4` 编码状态）；
  - 存在 ≥ 2 个未使用的局部寄存器（编号 ≤ 15）作为 `vS` 与谓词临时；
  - 不是 `<init>`/`<clinit>`，不是 `native`/`abstract`；
  - 不含 `invoke-polymorphic`/`invoke-custom`（引擎对这两类的引用处理不完整）。
- 只做：入口 dispatcher（`const/4 vS,#entry; packed-switch vS,payload`）+
  把**无条件 `goto` 与 fallthrough** 改为经 dispatcher 中转 +
  1 组恒真不透明谓词（§2.3 模板）。
- 条件分支 `if-*` 的 true 边保持直连（不经过 dispatcher）。
- 不做物理重排、不做指令替换、不做寄存器重编号。

交付物：

1. `dex.RebuildOptions.ControlFlow` + `flattenCodeItem`（约 250~300 行 Go）；
2. `InsnList` 增加「插入合成项并返回唯一旧偏移」的方法（约 30 行）；
3. `internal/passes/` 的 `controlFlow` Pass + `passes.go` 注册（A4 之后）；
4. `config.implementedIDs` 加 `A6`，并补依赖校验（见下）；
5. `cff_test.go`：判据 1/2/3/5/7/8/9/10/11/12。

与完整版的差距：

- 不支持含 try 的方法（完整版需在 try 区间内安全插入并严格保持端点边界）；
- 不支持含 switch/fill-array-data 的方法（完整版需重建 payload 并维护 owner）；
- 条件分支 true 边不过 dispatcher（完整版全部中转，平坦化更彻底）；
- 不做物理块重排（完整版可选，需改 `Encode` 末尾推导）；
- 不做指令替换（完整版叠加 SUB，收益有限、优先级最低）；
- 无按方法白名单（完整版加 `-cff-only`/`-cff-keep` 以把性能代价限制在关键方法）。

M1 能独立验证的点：产物里 `0x2b` 数量上升、谓词特征序列出现、解释器逐方法
语义一致、六项结构守卫全绿、三真实应用装机正常。
