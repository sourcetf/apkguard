## 1. 目标与预期效果

### 1.1 要防住的分析手法

A7 针对的是**基于调用图（call graph）的自动化分析**，与 A6 互补：

| 分析手法 | A1/A2/A3/A6 是否防住 | A7 是否防住 |
|---|---|---|
| 反编译后搜索敏感 API 调用点（`getDeviceId`、`SystemProperties.get`） | ❌ 调用点明文可见 | ✅ 调用点变成 `Method.invoke`，目标字符串被 A2/A3 加密 |
| 自动化工具构建调用图、定位敏感 API 的所有调用者 | ❌ | ✅ 调用图断裂 |
| 按调用图做数据流传播（taint analysis）追踪敏感数据 | ❌ | ✅ 目标方法不再是直接调用边 |
| 人工阅读反编译代码 | ⚠️ 反而更醒目 | ❌ 反射是逆向者的强信号，看到反射会重点看 |

**关键认知（写进产品说明）**：A7 是**双刃剑**。它切断自动化调用图，但同时给
逆向者一个显眼的「这里用了反射」信号。因此设计文档原话「建议仅对少量关键调用
使用」必须落实为**白名单驱动的选择性改写**，而不是全量替换。

### 1.2 预期效果如何量化

- **白名单调用点消除率**：白名单中每个被选中的调用点，改写后产物里对目标
  方法 `method_id` 的 `invoke-*` 引用数 = 0；同时
  `Ljava/lang/reflect/Method;->invoke` 的调用点数增加 K（K = 改写点数）。
- **调用图断裂**：用 `dexdump`/自研扫描统计「目标方法的调用者数量」，应从 N
  降到 0（改写点不再出现在其调用者集合里）。
- **目标名不可见**：启用 A2 或 A3 或 B1 后，产物字符串池中不再出现目标的
  类名二进制串（如 `android.os.SystemProperties`）与方法名字面量。
- **性能代价**：单次改写调用由「1 条 invoke」变为「forName + getMethod +
  invoke + 建数组」约 20~60 条指令；无缓存时单次开销从纳秒级升到微秒级
  （实测口径：Android 上 `Class.forName` 首次约数十微秒、`getMethod` 数微秒、
  `Method.invoke` 亚微秒 + 装箱/数组分配）。**只用于冷路径**；缓存 Method 后
  可降到 invoke 的几倍。
- **语义不变**：用 `internal/dex/interp_test.go` 的解释器（配合反射 API mock）
  对改写前后执行，正常路径返回值逐条一致；异常路径见 §2.5。

### 1.3 非目标

- 不反射化：构造函数、`invoke-super`、含基本类型参数的调用（避免装箱）、
  热循环内的调用。
- 不保证对抗「脱壳后重建调用图」；A7 与 B1 组合后防护面才完整。

## 2. 技术方案

### 2.1 哪些调用值得反射化（判据）

判据分两层：**白名单**（用户配置，决定「值不值得」）与**结构可行性**（引擎判断，
决定「能不能」）。二者都满足才改写。

**第一层：白名单（默认内置一组，允许 `-reflect-only` / `-reflect-keep` 覆盖）**

候选应是「分析者会顺藤摸瓜的敏感入口」，而不是随便一个方法：

| 目标 | 理由 |
|---|---|
| `android.os.SystemProperties.get(String,String)` | 样本手法；读取系统属性，常被用于设备指纹/环境探测 |
| `android.telephony.TelephonyManager.getDeviceId()` / `getImei()` | 设备标识，隐私与风控分析焦点 |
| `android.provider.Settings$Secure.getString(ContentResolver,String)` | 设备标识/开关 |
| `android.app.ActivityManager.isLowRamDevice()` 等环境探测 | 反模拟器/反调试线索 |
| 应用自身声明的「敏感业务方法」（用户用 `-reflect-only` 指定） | 保护核心算法入口 |

默认**不**包含：`Object`/`String`/集合等高频方法、SDK 内部热路径、构造器。

**第二层：结构可行性（逐调用点判断，任一不满足即跳过）**

1. **目标方法是 public**：`getMethod` 只返回 public 成员；非 public 需要
   `getDeclaredMethod` + `setAccessible(true)`，在 Android 9+ 会受隐藏 API
   限制（`NoSuchMethodException`/`IllegalAccessException`），一律排除。
   判据：目标类若在本 APK 的 DEX 中有 `class_def`，检查类与方法
   `ACC_PUBLIC`；若为外部框架类，则只允许白名单里已知 public 的项。
2. **目标类本身是 public**（应用类需检查 `class_def` 的 `ACC_PUBLIC`），否则
   跨包反射会 `IllegalAccessException`。
3. **全部参数与返回值都是对象或数组类型**（`L...;` 或 `[...`）：
   - 基本类型参数需要装箱（`Integer.valueOf` 等），工作量与出错面成倍增长，排除；
   - 返回基本类型需要拆箱并处理 null，排除。
4. **调用形式**：只处理 `invoke-static`(0x71/0x77)、`invoke-virtual`(0x6e/0x74)、
   `invoke-interface`(0x72/0x78)。排除：
   - `invoke-direct`(0x70)：多为 private/构造器，`setAccessible` 受限；
   - `invoke-super`(0x6f)：反射无法表达 super 调用语义；
   - `invoke-polymorphic`/`invoke-custom`：引擎对这两类引用处理不完整。
5. **调用点不在任何 try 区间内**（最小切片；完整版见 §2.5）：避免把
   `InvocationTargetException` 暴露给上层 catch。
6. **目标不是 `java.lang.reflect.*` / `java.lang.Class`**：防止改写反射自身的调用，
   造成递归或语义错乱。
7. **寄存器预算足够**（见 §2.4）。
8. **目标方法没有被 A1 改名**：A1 只改应用类；框架类不改。若目标是应用类，
   必须使用 A1 后的最终名称（因此 A7 必须在 A1 之后，见 §3）。

### 2.2 签名串从哪来

全部来自 `method_ids`，不猜、不硬编码：

- `f.MethodRefAt(methodIdx)` 返回 `{ClassIdx, ProtoIdx, NameIdx}`；
- 类名：`f.Type(ClassIdx)` 得到描述符，如 `Landroid/telephony/TelephonyManager;`，
  转成 `Class.forName` 接受的二进制名：
  - 去掉首 `L` 与尾 `;`，把 `/` 换成 `.`，`$` 原样保留（内部类二进制名也用 `$`）；
  - 例：`Landroid/os/SystemProperties;` → `android.os.SystemProperties`；
  - 数组类型 `[Ljava/lang/String;` → `[Ljava.lang.String;`（`Class.forName` 接受）；
- 方法名：`f.String(NameIdx)`；
- 参数类型：从 proto 的 `params` 取每个类型描述符，逐个转成二进制名（仅对象/数组，
  基本类型已在 §2.1 排除）；
- 返回值类型：不生成字符串，改写末尾用 `check-cast vRes, <原返回描述符>` 直接引用
  类型表（`Asm.CheckCast` 已支持）。

这些字符串通过 `Asm.ConstString`（一律 jumbo，32 位索引对任意池规模安全）写入，
重建时由 `plan.resolveRef` 解析为真实索引。

### 2.3 改写后的字节码形态

以 `invoke-virtual {vR, vA0}, Ltarget;->m(Lfoo;)Lbar;` 为例，等价改写为：

```
; ---- 取 Class 与方法（声明类名来自 method_ids）----
const-string/jumbo vCls, "com.example.Target"        ; Asm.ConstString
invoke-static {vCls}, Ljava/lang/Class;->forName(Ljava/lang/String;)Ljava/lang/Class;
move-result-object vCls
; ---- 构造 Class[] 参数类型数组 ----
const/16  vN, #1                                     ; 参数个数
new-array vPT, vN, [Ljava/lang/Class;                ; 22c，vPT/vN 必须 ≤ v15
const-string/jumbo vCn, "com.example.Foo"            ; 每个对象参数一个
invoke-static {vCn}, Class.forName(...)              ; 省略，同前
move-result-object vCn
const/4   vIdx, #0
aput-object vCn, vPT, vIdx
; ---- 取 Method ----
const-string/jumbo vMn, "m"
invoke-virtual {vCls, vMn, vPT}, Ljava/lang/Class;->getMethod(Ljava/lang/String;[Ljava/lang/Class;)Ljava/lang/reflect/Method;
move-result-object vM
; ---- 构造 Object[] 实参数组 ----
const/16  vN2, #2                                    ; 实例方法：receiver 占 index 0
new-array vArgs, vN2, [Ljava/lang/Object;
const/4   vIdx, #0
aput-object vR, vArgs, vIdx                          ; receiver
const/4   vIdx, #1
aput-object vA0, vArgs, vIdx
; ---- 调用 ----
invoke-virtual {vM, vRecv, vArgs}, Ljava/lang/reflect/Method;->invoke(Ljava/lang/Object;[Ljava/lang/Object;)Ljava/lang/Object;
move-result-object vRes
check-cast vRes, Lbar;                               ; 原返回类型；返回 Object 时省略
```

要点：

- **`invoke-*` 与 `move-result-object` 必须紧邻**：上面对 `Class.forName`、
  `Class.getMethod`、`Method.invoke` 三次调用都在紧接着的下一条 `move-result-object`
  接住结果。缺一条或中间插指令，ART 判
  `VerifyError: move-result-object not immediately after invoke`，整个类被拒。
- **`invoke-static` 的 receiver 传 `null`**（用 `const/4 vNull,#0` 后 aput），
  `Method.invoke(null, args)` 表示静态调用。
- **原 `invoke-*/range`（0x74~0x78）** 同样支持：按 3rc 的寄存器表取出全部实参寄存器，
  逐个 `aput-object` 进 `Object[]`。
- **原返回值未被使用**（无 `move-result`）：仍必须加 `move-result-object`（否则
  invoke 结果悬空，校验器要求 invoke 的 move-result 规则由方法是否使用决定；
  Dalvik 允许 invoke 后不接 move-result 表示丢弃结果——但返回类型为 Object 时，
  直接丢弃是合法的。为统一与安全，改写后一律接一条 `move-result-object` 到临时
  寄存器并忽略）。
- **寄存器编号 ≤ 15 的硬约束**：`invoke-*` 是 35c（寄存器字段 4 位）、`new-array`
  是 22c（目标与长度字段 4 位）、`const/4` 4 位。因此 `vCls/vPT/vN/vCn/vIdx/vMn/vM/vArgs/vRes`
  都必须 ≤ v15。`check-cast` 是 8 位，无此限制。

### 2.4 寄存器预算

改写一个调用点需要的临时寄存器数量随参数个数增长：
`vCls, vN, vPT, vCn(复用), vIdx, vMn, vM, vN2, vArgs, vRes, vRecv` ≈ 6~8 个。

- 与方法内已有寄存器不冲突、且 ≤ v15 的**空闲寄存器**必须足够，否则跳过该点。
- 与 A6 一样，**不得增大 `registers_size`**（入参寄存器会整体后移）。
- 空闲寄存器判定复用 A6 的寄存器扫描（扫描全部指令操作数得到 `used`）。
- 若原方法参数已经占用 v0~v15 的大部分（大方法常见），可用低位寄存器不足，
  该调用点自然被跳过——这是可接受的保守行为。

### 2.5 语义一致（含异常语义）

**正常路径**：改写后返回值经 `check-cast` 还原为原类型；参数通过 `Object[]`
原样传递（对象引用不变）；receiver 语义为 `Method.invoke` 的第一个实参。

**异常语义（必须正面处理）**：`Method.invoke` 会把目标方法抛出的异常**包装**为
`java.lang.reflect.InvocationTargetException`。若直接这样改写，调用方原本
`catch (IOException e)` 会失效（因为抛出的类型变成了 InvocationTargetException），
控制流与异常类型都改变——**不可接受**。

两种保持语义的做法：

1. **helper 解包（推荐，全 API 级别）**：把反射序列集中到一个注入的静态 helper：
   ```
   static Object call(String cls, String m, Class[] p, Object recv, Object[] args) {
       try {
           Method mm = Class.forName(cls).getMethod(m, p);
           return mm.invoke(recv, args);
       } catch (InvocationTargetException e) {
           throw e.getCause();          // 原样重抛目标异常，类型/栈保持
       }
   }
   ```
   调用点只负责建数组 + 调 helper + `check-cast`，异常从 helper 里原样抛出，
   与原直接调用的可观测行为一致（`getCause()` 的类型就是原异常类型）。
   **依赖**：注入方法必须带异常表。当前 `CodeBlob` 明确不支持异常表
   （`assemble.go` 注释：「注入的壳代码本身也不需要异常表」）。因此完整版 A7
   需要把 helper 用 `CodeItemFull`（含 `Tries`/`Handlers`）手工构造，复用
   `encodeHandlerList` 与 `CodeItemFull.Encode` 的地址修正能力。这是本项最大的
   基建改动。
2. **`MethodHandle` 替代（无异常表，但 API 26+）**：
   `MethodHandles.lookup().unreflect(method).invokeWithArguments(args)` 直接抛出
   目标异常本身，不包装，因此 helper 不需要 try/catch。代价：`java.lang.invoke`
   自 API 26 起才可用；且 `invokeWithArguments` 需要精确参数个数、性能与装箱成本
   与反射相当。按应用 `minSdk` 选择：`minSdk ≥ 26` 可用，否则走方案 1。

**最小切片（§6）** 暂时只改写**不在任何 try 区间内**的调用点，并只启用
「已知正常路径不抛异常」的白名单项（如 `SystemProperties.get` 读取失败返回默认值）。
即便如此，若目标方法仍抛出未检查异常，异常类型会变成
InvocationTargetException——这一点必须在实现里如实记录，并由 §4 的异常路径
断言（真机）兜底，不能当作已解决。

**其他语义细节**：

- receiver 为 null 时，`Method.invoke(null, ...)` 对实例方法抛
  `NullPointerException`，与原 `invoke-virtual` 在 null 上的 NPE 类型一致
  （消息可能不同，不影响控制流）。
- 目标方法返回 null：`move-result-object` 得到 null，`check-cast null` 合法。
- 目标方法是可变参数（varargs）：编译后参数就是数组类型，属对象，直接放入
  `Object[]` 的一个元素即可，无需特殊处理。
- 静态初始化：`Class.forName` 会触发目标类 `<clinit>`（默认 initialize=true），
  这与原直接调用在「首次调用时触发类初始化」的时机基本一致；但若原调用点在
  目标类已初始化之后、而 A7 首次反射发生在更早的时机，可能提前触发 `<clinit>`
  ——对副作用敏感的类需靠白名单排除（这也是「只选少量」的理由之一）。

### 2.6 性能代价与缓存

- 无缓存：每个调用点每次执行都要 `forName + getMethod + 建两个数组`，
  单次约 10~100 微秒（首次 forName 可能触发类加载）。
- 缓存（完整版）：注入一个持有类（如 `L<shell>/Rfl;`），为每个调用点分配一个
  静态 `Method` 字段或一个 `Method[]` 缓存槽，首次调用初始化、后续直接取。
  初始化需要 try/catch（`getMethod` 抛 `NoSuchMethodException`）——同样依赖
  §2.5 的异常表能力。缓存后单次开销约为反射 invoke 的 2~5 倍。
- 约束：只对白名单调用点启用；不处理循环体内的调用点（可用简单启发式：
  调用点所在块位于某条回边内则跳过），避免把热路径改成微秒级。

### 2.7 如何避免 `const-string` 变成新的可读线索

这是 A7 最容易做砸的地方：反射化本身会把「类名 + 方法名」作为明文
`const-string` 写进方法体，若不处理，等于**主动给分析者送上调用目标**。

设计：

1. **A7 注册在 A1 之后、A2 之前**（见 §3）。A7 生成的类名/方法名是普通
   `const-string`；随后 A2 的 `planStringEncrypt` 会把这些「仅被 const-string
   引用」的字符串整体替换为密文（`constOnly` 判定通过：它们不是类型名/方法名/
   字段名——反射串是 Java 二进制名 `a.b.C`，与 DEX 描述符 `La/b/C;` 不同），
   并在指令处插入解密调用。这样目标名在池里只剩密文。
2. 若用户**未启用 A2**：A3 在 A7 之后运行，会把 A7 的 `const-string` 改写为
   `fill-array-data` + 还原方法调用，明文不再出现在字符串池（但原始字节仍在
   code_item 的 payload 里，`strings` 对原始文件仍可能命中——这是 A3 的已知
   局限，README 已记录）。
3. 若 A2/A3 都未启用：A7 的目标名就是明文。**必须在产品说明与 `config.Note`
   中明确写出「单独启用 A7 不隐藏反射目标名，建议与 A2 或 B1 同用」**，避免
   使用者误以为调用目标已隐藏。
4. B1（DEX 整体加密）在 A7 之后运行，静态产物里反射串随明文 DEX 一起被加密，
   是最终的静态防护。
5. 反射串不得同时作为类型/方法/字段名出现（否则 A2 的 `constOnly` 会为保索引
   而保留明文）。A7 使用二进制名（点分隔）而非描述符（斜杠分号），天然与
   `type_ids`/`method_ids` 的字符串不同，满足该条件。

## 3. 与现有 Pass 的交互与执行顺序

**建议把 A7 注册在 `renameClass`(A1) 之后、`encryptString`(A2) 之前**：

```go
r.Register(&renameClass{})    // A1
r.Register(&reflectCall{})    // A7  ← 新增，必须在 A1 之后、A2 之前
r.Register(&encryptString{})  // A2
r.Register(&constantArray{})  // A3
r.Register(&classPad{})       // A13
r.Register(&dropDebugInfo{})  // A4
r.Register(&controlFlow{})    // A6（若同时实现，见 A6 方案）
r.Register(&fakeDex{})        // A9
...
```

理由（每条都是硬约束）：

1. **必须在 A1 之后**：A7 把目标的**最终类名/方法名**写成字符串。若排在 A1 前，
   A1 改名后这些字符串仍指向旧名，运行时 `Class.forName` 抛
   `ClassNotFoundException`（这正是 README 里 ServiceLoader 那类「两半都引用类名」
   缺陷的同构问题：改名只改索引，不改字符串字面量）。排在 A1 后，A7 读到的是
   改名后的 `method_ids`，字符串与实际类名一致。
2. **必须在 A2 之前**：让 A2 顺带加密 A7 新引入的类名/方法名字符串（§2.7）。
   若排在 A2 之后，A7 的明文串不会被 A2 处理，必须自己做字符串隐藏，复杂且易漏。
3. **相对 A3**：A3 依赖「A2 已处理的跳过」（`isStringDecryptPattern`）。A7 排在
   A2 前，A2 处理后的反射串会被 A3 正确跳过；若 A2 未启用，A3 会数组化 A7 的串。
   两种顺序结论一致——A7 在 A2 前即可。
4. **相对 A4**：A4 去调试信息，与 A7 无冲突。A7 会平移指令地址，A4 排在 A7 之后
   会把 debug_info 一并清掉；A7 不新增调试信息。顺序无强约束，保持 A7 在 A4 前
   可减少一次「带 debug 的重建」。
5. **必须在 B1/B4 之前**：与 A6 同理，B1 把明文 DEX 加密成 assets 载荷并移除
   明文条目；B4 拆分 DEX。A7 是 DEX 层改写，必须在 B1/B4 之前完成。A7 注入的
   helper 类会随主 DEX 一起被 B4 归类、B1 加密。
6. **与 A6 的先后**：A6 建议排在 A4 之后（见 A6 方案），因此 A7 在 A6 之前。
   A6 会平坦化 A7 生成的反射序列；A6 的块划分规则（不把 move-result 当块首、
   不拆 invoke/move-result 邻接）必须成立，否则会破坏 A7 的序列。若两者同时启用，
   A6 的守卫测试必须覆盖「含反射序列的方法」。
7. **与 A8/A13 注入类**：A7 注入的 helper 属于「新增类」，A8/A13 也在注入类。
   建议 A7 的 helper 类名纳入 A1/A8 的去重与保留逻辑（注入类名不应被再次混淆），
   并确保 helper 只注入主 DEX（与 A2 解密器同策略：多 DEX 场景全局唯一）。
8. **与 D1/C1 等壳代码**：A7 在 B2 之前，不碰壳 DEX；壳的 Loader/Application
   不能反射化（排障需要可读）。

**配置依赖建议**：`config.Validate` 不把 A2/B1 设为 A7 的硬依赖（A7 本身语义正确），
但应在 A7 的 `Note`/Web UI 提示「未启用 A2/B1 时反射目标名不隐藏」。若希望更强约束，
可增加软警告而非错误。

## 4. 验收标准（可自动化断言）

对齐 `branch_test.go` / `handler_test.go` / `outs_test.go` 的产物级体检风格，
新增 `reflect_test.go`。失败信息必须写明「ART/运行时会怎么报」。

### 4.1 结构性判据

| # | 判据 | 自动化做法 | 防住的回归 |
|---|---|---|---|
| 1 | **白名单调用点消失** | 扫描产物：对每个被选中的目标 `method_id`，`invoke-*`（含 `/range`）引用数 == 0；可用 `insnRefs` + `f.MethodDesc` 判定 | 「启用了 A7 但调用点还在」——功能项空转 |
| 2 | **反射调用点出现 K 次** | 统计引用 `Ljava/lang/reflect/Method;->invoke` 的指令数 == K（K = `A7.sites` 统计），且 `Class.forName` 调用数 ≥ K | 改写未真正落地、统计与产物不符 |
| 3 | **产物形态出现 N 次** | `new-array [Ljava/lang/Class;` 与 `new-array [Ljava/lang/Object;` 各 ≥ K；`getMethod` 调用数 == K | 漏建参数数组导致 `getMethod` 签名不匹配 |
| 4 | **invoke/move-result 邻接** | 扫描：每条 `invoke-*` 后紧跟的必须是合法 `move-result*`（按原方法是否使用结果判定），A7 生成的调用一律有 | ART `VerifyError: move-result-object not immediately after invoke` |
| 5 | **寄存器编号合法** | 断言 A7 生成的所有 35c/22c/11n 指令寄存器 ≤ 15；被改写方法 `registers_size` 与改写前完全相同 | 35c/22c 越界编码 → 非法 DEX；增大寄存器导致入参错位 |
| 6 | **`outs_size` 足够** | A7 新增了 invoke，必须断言被改写方法 `Outs ≥ max(invoke 参数字数)`；复用 `checkOutsOf` | ART `VerifyError`（本地解释器不检查，典型盲区） |
| 7 | **分支/异常表/描述符** | 复用 `checkBranchTargets`、`checkTryHandlers`、`dex.ValidateDescriptors`、`dex.Verify` | 偏移/类型错误 |
| 8 | **字符串隐藏** | 启用 A2 时：断言字符串池不含目标类二进制名明文（`f.String(i)` 遍历比对）；启用 A3 时：断言池中不含但 code_item 含对应 `fill-array-data`；两者都关时断言产出 `A7.plaintext=true` 统计并在报告里显式提示 | 反射目标名变成新的可读线索（本方案最核心的失败模式） |
| 9 | **异常路径真机验证** | 模拟器上跑一个受控用例：目标方法抛指定异常，断言调用方 catch 到的类型与原异常一致（验证 InvocationTargetException 已被解包）；`adb logcat` 无 `InvocationTargetException` 逃逸 | 异常语义被破坏（catch 失效、控制流改变） |

### 4.2 语义等价判据

- **解释器等价**：用 `internal/dex/interp_test.go` 的 `interp` 对改写前后执行。
  需要为 `Class.forName`/`getMethod`/`Method.invoke` 注册 mock（现有 `fakeCalls`
  机制已支持按 `Class->method(desc)` 键注入处理函数），断言：
  - 正常路径返回值逐条一致；
  - 传入 null、返回 null、数组参数等边界一致。
- **未列入白名单的调用一律不动**：断言非白名单 `invoke-*` 数量与改写前完全相同。
- **端到端**：Termux / Dhizuku / RustDesk 启用 A7 后正常运行；`go test ./...` 全绿，
  守卫在干净检出下真正执行（不静默 `t.Skip`）。

## 5. 风险与取舍

### 5.1 会破坏产物、不能做的做法

1. **反射化基本类型参数/返回值**：需要装箱拆箱，字节码复杂度成倍增长，且
   `Method.invoke` 对 `int` 参数要求 `Integer`、对 `long` 要求 `Long`，一旦
   装箱类型写错就是 `IllegalArgumentException`。最小切片一律排除。
2. **对非 public 方法用 `getMethod`**：返回 `NoSuchMethodException`；改用
   `getDeclaredMethod + setAccessible(true)` 在 Android 9+ 受隐藏 API 限制，
   可能抛 `IllegalAccessException`。一律排除非 public。
3. **忽略 `InvocationTargetException` 包装**：调用方的 `catch` 失效，异常语义被
   破坏。必须解包（§2.5）。
4. **`invoke` 后不接 `move-result-object`**：ART 判
   `move-result-object not immediately after invoke`，整个类被拒。
5. **临时寄存器 > v15**：35c 的寄存器字段是 4 位、22c 的 `new-array` 目标/长度
   是 4 位，越界即非法；必须检查。
6. **增大 `registers_size`**：入参寄存器整体后移，原引用失配（与 A6 同）。
7. **在 A1 之前改写**：嵌入的类名是旧名，A1 改名后运行时
   `ClassNotFoundException`。
8. **在 A2 之后改写却不做字符串隐藏**：反射目标名以明文留在池里，等于主动
   暴露调用目标。
9. **反射化热循环内的调用**：性能崩塌（微秒级 × 循环次数）；应启发式跳过或由
   白名单限制。
10. **反射化反射 API 自身 / helper 自身**：递归或语义错乱；必须排除
    `java.lang.reflect.*`、`java.lang.Class` 及注入 helper 类。
11. **忘记触发 `<clinit>` 的时机差异**：`Class.forName` 会初始化目标类，可能
    提前触发静态初始化副作用；靠白名单排除敏感类。

### 5.2 取舍

- **强度 vs 显眼度**：A7 越用越显眼。设计上坚持「白名单 + 少量」，宁可只改
  几个最关键调用，也不要全量替换。
- **语义完整 vs 基建成本**：完整异常语义需要注入方法支持异常表，而现有
  `CodeBlob` 不支持，必须扩展到 `CodeItemFull`。这是 A7 的主要工作量来源。
  最小切片用「不在 try 区间 + 已知不抛异常的白名单」绕开，但不等于解决。
- **性能 vs 缓存**：缓存需要静态字段 + 初始化 try/catch，进一步依赖异常表能力；
  无缓存则每次调用都慢。建议最小切片无缓存、只用于冷路径。
- **API 级别**：`MethodHandle` 方案无异常表但需 API 26+；若目标应用 minSdk < 26，
  只能走 helper + 异常表。

## 6. 最小可落地子集

**第一个可交付切片（M1）**，能独立验证、不破坏现有三个真实应用的运行：

范围：

- 只处理 `invoke-static`/`invoke-virtual`/`invoke-interface`（含 `/range`）；
- 目标方法：白名单内、public、参数与返回值全为对象/数组；
- 调用点：不在任何 try 区间内、方法内空闲寄存器（≤ v15）足够；
- 反射序列**内联在调用点**（不注入 helper、不解包 InvocationTargetException）；
- 只启用「正常路径不抛异常」的白名单项（如 `SystemProperties.get`、
  `Settings.Secure.getString`、`TelephonyManager.getDeviceId`——后者失败返回 null）；
- 不做 Method 缓存。

交付物：

1. `dex.RebuildOptions.ReflectCall` + `reflectCodeItem`（约 150~200 行 Go），
   复用 `Asm` 生成序列、`plan.resolveRef` 回填引用；
2. 白名单解析（`-reflect-only` / 内置默认表）+ 目标方法 public/参数判据；
3. `internal/passes/` 的 `reflectCall` Pass + `passes.go` 注册（A1 后、A2 前）；
4. `config.implementedIDs` 加 `A7`，`config.Note` 写明「需 A2/A3/B1 隐藏目标名」；
5. `reflect_test.go`：判据 1~8。

与完整版的差距：

- 不做 `InvocationTargetException` 解包（异常语义未完全保持，文档如实标注）；
- 不做 helper 注入与异常表（不依赖 `CodeItemFull` 扩展）；
- 不做 Method 缓存（性能代价高）；
- 不做应用类方法反射化（只做框架白名单），避免 A1 改名与可见性判断的复杂度；
- 不处理 try 区间内的调用点。

M1 能独立验证的点：白名单调用点在产物中消失、反射调用点按 K 出现、
invoke/move-result 邻接与 outs/寄存器守卫全绿、解释器正常路径等价、A2 加密后
目标名不可见、三真实应用装机正常。
