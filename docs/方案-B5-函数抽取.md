## 0. 结论先行（TL;DR）

1. **B5 的可行形态是「预留同尺寸空洞 + 运行时按类惰性回填 ART 内存映射」**，而不是
   「`code_off` 置 0 / 删除 code_item」。原因见 §2.3：把具体方法的 `code_off` 清零在
   ART 上的行为是**版本相关的**（可能 `VerifyError` / `NoSuchMethodError` / 被 `dex2oat`
   拒绝），而保持 `code_item` 结构完整、只把指令词换成等长合法 stub，可以保证
   **DEX 结构在回填前就是合法的**，把风险从「ART 拒绝加载」降到「运行到该方法时行为错误」。
2. **回填必须发生在「DEX 已被 ART mmap」之后、「该类被 define/verify」之前**。公开 API 内
   唯一可靠的这个时机是**覆写 `DexClassLoader.findClass`**（它在 `super.findClass` 之前
   被调用，而 `super.findClass` 才触发 `DefineClass` 与校验）。`剩余功能落地设计.md` 写的
   「在 B2 的 `attachBaseContext` 之前由 native 完成」是**做不到的**：那一刻载荷 DEX 还没
   被 ART 打开、根本没进内存映射，native 无址可写。详见 §2.5/§0.2。
3. **抽取出来的字节码只能放 assets（加密），不能放 native 常量**。因为
   `apkguard/internal/native/embed.go` 把 `libapkguard.so` **预编译并 `go:embed`**，全部
   APK 共用同一份 `.so`；per-APK 的字节码没有任何办法在打包期写进它（写进去就要在加固时
   调 NDK 重编，直接破坏「单二进制、零依赖」定位，与 B7 的交付冲突同源）。见 §2.4。
4. **B5 在公开 API 内做不到「内存 dump 一定是空方法体」**。回填完成后 ART 内存里就是明文
   字节码，dump 工具在回填后取即可拿到。B5 的正确卖点是「**磁盘上的 DEX 是空的**、静态
   反编译与文件级脱壳失效、按需回填把明文窗口压到最小」；真正的「内存中永不出现明文」
   是 B6（私有指令集）与 B7 的职责。见 §1.1 与 §5。
5. **依赖必须加强**：B5 不仅依赖 B1，还依赖 B2/B3（Loader 是回填的驱动方）与 C1（native
   库与桥接类由 C1 注入）。当前 `config.Validate` 里 B5 只声明依赖 B1，落地方案要求补上
   `B2/B3/C1`，见 §3.3。

### 0.1 与 B6/B7 的边界（同一方法只能被三者之一处理）

| 维度 | B5 函数抽取 | B6 VMP（`方案-B6-VMP.md`） | B7 Dex2C（`方案-B7-Dex2C.md`） |
|---|---|---|---|
| DEX 里方法体 | 原始 Dalvik 指令，但被等长 stub 覆盖 | 生成的 Dalvik 桥接 stub（调用 VM） | `ACC_NATIVE`，`code_off=0` |
| 明文 Dalvik 在哪 | assets 密文 → **回填进 ART 内存** | 从不出现（已翻译为私有指令） | 从不出现（已翻译为 C） |
| 运行时执行者 | ART 解释器/JIT（原始字节码） | 预编译 C 解释器（私有指令集） | NDK 编译的 C 机器码 |
| 是否需要 NDK | 否 | **否** | **是**（per-app 编译，见 B7 §2.5） |
| 停机内存 dump | ❌ 回填后可见明文 | ✅ 只见私有指令 | ✅ 只见 native |
| 读盘 / 静态反编译 | ✅ 空方法体 | ✅ 只剩 stub | ✅ native 声明 |
| 性能 | 回填后基本无损 | 解释执行，慢 | native，但有 JNI 边界开销 |

## 1. 目标与预期效果

### 1.1 防住什么（以及诚实地说明防不住什么）

| 攻击者手段 | B1/B3 一代壳 | **+B5** |
|---|---|---|
| `apktool`/`jadx` 静态反编译 | 只看到壳；业务 DEX 在 assets 密文里 | 只看到壳；**解密出的 payload DEX 里被抽取方法只剩 stub** |
| 从应用私有目录拉取解密后的 `d*.dex` | 拿到完整业务字节码 | 拿到**空方法体**（磁盘文件始终是 stub） |
| 内存 dump（Frida-DEXDump / BlackDex） | 拿到完整字节码 | **在回填之后 dump 仍可拿到该类的明文**；只有 dump 发生在「类尚未加载」时才拿到空体 |
| 自动化按方法定位核心算法 | 可读 | 需先脱壳并**在正确时机**抓内存，跨方法/跨类拼装成本上升 |
| Frida hook 解密后的字节码 | 可 hook | 同左（回填的字节码在 ART 内存里，可 hook） |

**必须写清楚**：B5 与 B1 的差别不是「有没有明文」——B1 的明文是**完整文件**在磁盘上，
B5 的明文只在**已加载类的 ART 内存**里、且磁盘文件恒为空。因此 B5 对**静态与文件级
脱壳**是决定性的，对**运行中内存 dump**只是提高了时机门槛，不是阻断。这与设计文档
§8 矩阵里「+L3 二代壳 → 内存 dump ✅ 阻断」的乐观描述不一致，本文按实现事实修正。

### 1.2 量化指标（全部可自动化断言，见 §4）

- **抽取覆盖率**：被抽取方法数 / 可抽取候选方法数（由 `-extract-ratio` 控制，见 §2.2）。
  产物报告必须给出「候选数、实际抽取数、各跳过原因分布」，禁止「启用了 B5 却抽了 0 个」
  仍报成功（对齐 `README.md`「不静默跳过」原则）。
- **磁盘空体率 = 100%**：对随机抽样的被抽取方法，解密落地后的 `d*.dex` 中该方法的
  指令词必须全部等于 stub（全 `nop` + 一条 `return*`），且 `insns_size` 与抽取前一致。
- **明文残留 = 0**：抽取前的原始指令序列（以方法为单位的字节串哈希）**不得**出现在
  产物任何条目、任何解密后的 payload 中（防「抽了但忘了删」）。
- **回填命中率 = 100%**：运行时 native `fill` 返回的成功改写数 == 计划抽取数；
  不一致必须 fail-fast（见 §2.5），不允许「部分回填 + 应用照跑」。
- **体积**：抽取本身几乎不改变 DEX 大小（等长 stub），只在 assets 增加一份
  `Σ(方法字节数 + 元数据)` 的密文；预计为业务 DEX 的 **10~40%**（取决于比例）。
- **性能**：回填后的稳态执行与 B1 完全相同（ART 执行原始字节码），**开机多一次性
  回填开销**（按方法字节数线性，RustDesk 量级预计 < 50 ms）。

## 2. 技术方案

### 2.1 为什么必须做成 `RebuildOptions` 的一个选项，而不是「事后按字节打补丁」

抽取的两个关键事实决定了实现位置：

1. **指令字节必须是「改名/加密之后的最终字节」**。A1 会重建索引表并改写全部池引用，
   A2/A3 会把 `const-string` 改写成解密/还原序列。若在 A1 之前抽取，存进 blob 的是旧
   索引的字节；回填后 ART 按新索引解析，轻则错值、重则 `NoSuchMethodError`。
2. **`code_off` 在重建后变化**。Rebuild 会重排数据区，`code_item` 偏移是重建时
   `builder.place` 分配的（`assemble.go` 第 3 步）。抽取 blob 必须记录**最终**的
   `code_off`，否则回填写到错误地址。

因此 B5 应当作为 `RebuildOptions` 的新字段（与 `StringEncrypt`/`ConstantArray`/
`ClassPad` 同构），在 `builder.generate` 的 code_item 循环里，在 A2/A3 改写**之后**处理：

```
// rebuild.go（设计，不落代码）
type ExtractSpec struct {
    // Select 决定某个已有方法是否被抽取（按 类描述符/方法名/原型/指令词数 判定）。
    Select func(cls, name, proto string, insnsWords int) bool
    // collect 收集「原始指令词 + 最终 code_off + 所属 DEX」，由 builder 回调。
    collect func(dexName string, codeOff uint32, cls, name, proto string, words []uint16)
}
type RebuildOptions struct {
    ...
    Extract *ExtractSpec
}
```

在 `assemble.go` 的 code_item 处理里，命中 `Select` 的方法：先把（已跑完 A2/A3 与
`remapCode` 的）最终 blob 解析成 `CodeItemFull`，取出 `Insns` 存进收集器，再把
`Insns` 替换为**等长 stub**、其余字段（`registers/ins/outs/tries/debug_info_off`）
原样保留并编码回去。这样 `codeMap[co]` 仍指向一个结构合法的 `code_item`，
后续所有偏移/索引/异常表逻辑完全不变。

> 为什么不去做独立 Pass 的「解析当前 DEX → 找 code_item → 改字节」：那条路要自己重算
> `code_off`（重建后变了）、要自己保证异常表/池引用与最终布局一致，等于把 `assemble.go`
> 已经做对的事再做一遍，风险远大于把它做成一个选项。

### 2.2 哪些方法值得抽取（判据）

抽取单位是**方法**，判据（`Select` 的实现）如下，全部满足才抽取：

**硬门槛（不满足直接跳过）**

1. 非 `abstract`、非 `native`（没有 code_item 可抽）。
2. 不是 `<init>`：B5 的 stub 无法满足 ART 对构造函数的校验规则（`<init>` 必须先调用
   父类构造器再返回），而且一旦回填失败会留下半初始化对象。
3. 不是 `<clinit>`：类初始化时机由 ART 控制且可能被框架隐式触发；即使惰性按类回填在
   理论上能覆盖它，v1 也先排除以缩小失败面。
4. `code_item.insns_size >= 8`（stub 最多 3 个字，太短的方法抽取收益为负、且更容易
   在回填失败时造成难以定位的错误返回值）。
5. stub 编码长度 ≤ 原 `insns_size`（否则没有空洞可填，跳过）。

**收益/风险权衡（按优先级打分，`-extract-ratio` 从高分往下取）**

1. **方法体越大越优先**：`insns_words` 是主要权重——抽取的价值与 blob 成本都随体量上升，
   而反编译者最想读的正是这些大方法。
2. **热路径不排除**：B5 采用一次性/按类回填，回填完成后 ART 执行的是原始字节码，
   **稳态零开销**，因此热路径不需要因性能而排除（这一点与 B6 相反：B6 是解释执行，
   必须排除热路径）。唯一要避开的，是「在回填完成之前就被执行」的方法——即壳自身与
   壳启动早期加载的框架类，它们本来就不在 payload 里。
3. **优先抽取业务核心类**（可用包名/白名单指定），跳过编译器生成的桥接方法、枚举
   `values()`/`valueOf()` 等模板代码（抽了收益低、且这些方法可能被反射按名调用）。
4. **含 `try/catch` 的方法可以抽取，但 v1 先跳过**：等长 stub 不会破坏 try 表结构
   （表字节在指令流之外、地址不变），所以 B5 在结构上**允许** try 方法；v1 跳过纯粹是
   为了缩小「stub 落在 try 区间内」这一语义面，等基础链路验证后再放开（见 §6）。
5. **确定性选择**：`hash(类描述符 + 方法名 + 原型 + seed) % 100 < ratio`，保证同一
   输入 + seed 的产物可复现（与 A1/A2 的既有约定一致）。

### 2.3 抽取后 `code_item` 留什么：等长合法 stub，绝不把 `code_off` 置 0

**结论：保留 `code_item`，`code_off` 非 0，`insns_size` 不变，指令词替换为等长 stub。**

为什么不是 `code_off=0`（设计文档原始写法是「CodeItem 指令置空或移除」）：

- DEX 规范里 `code_off == 0` 表示「该方法没有实现」，合法用途是 `abstract`/`native`。
  对**具体方法**写 0，`DexFileVerifier` 不一定拦，但 `ClassLinker` 在链接/首次调用时
  各版本行为不一致，可能：
  - 类校验期抛 `java.lang.VerifyError: Method '...' has no code`（整类被拒）；
  - 或首次调用才抛 `NoSuchMethodError`/`AbstractMethodError`（离原因很远）；
  - 或 `dex2oat` 直接 abort。
  这是**本方案最大的未知，必须用真机探针逐版本确认**（验证方法见 §2.7）。
- 更致命的是**布局**：删/清零 code_item 会让后续所有 `code_off` 平移，抽取 blob 里记录
  的偏移全部失效，且异常表、`emitClassData` 的 ULEB 变长编码都要重算。
- 等长 stub 把上述风险一次性消掉：**回填前后 DEX 结构逐字节同构，只是那一段指令词不同**，
  偏移、索引、异常表、调试信息全部保持。

stub 的编码（按返回类型，`stub_words` 必须 ≤ 原 `insns_size`，其余补 `nop` 0x0000）：

| 返回类型 | stub | 字数 |
|---|---|---|
| `V` | `return-void` (0x0e) | 1 |
| `Z/B/C/S/I` | `const/4 v0,#0` (0x12) + `return v0` (0x0f) | 2 |
| `J` | `const-wide/16 v0,#0` (0x14) + `return-wide v0` (0x10) | 3 |
| `F` | `const/4 v0,#0` (0x12) + `return v0` (0x0f) | 2 |
| `D` | `const-wide/16 v0,#0` (0x14) + `return-wide v0` (0x10) | 3 |
| `L`/`[` | `const/4 v0,#0` (0x12) + `return-object v0` (0x11) | 2 |

要点与理由：

- `const/4` 写 0 得到的是 verifier 内部的「zero」类型，对 32 位基本类型（含 F）与引用
  类型都可赋值；64 位用 `const-wide/16` 0。**这一条仍需真机 ART 校验确认**（不同版本对
  zero 类型的处理细节有差异），见 §2.7 的探针。
- `v0` 必然存在：非 void 方法为了保证有寄存器承载返回值，`registers_size ≥ 1`；
  void 方法 `registers_size` 可以为 0，此时 stub 只有 `return-void`，不引用任何寄存器。
- 补 `nop` 而非随机字节：`nop` 是 1 字无异常指令，不会与 payload 标识（0x0100/0x0200/
  0x0300）混淆，也不会引入新的分支/池引用，`remapCode` 之后不会再被处理。
- 保留 `tries` 与 `debug_info_off`：stub 长度与 try 区间/调试信息地址一一对应，结构
  仍然合法。A4 启用时 `debug_info_off` 已被置 0，无影响。

### 2.4 抽取出来的字节码放哪：加密进 assets（不能进 native）

抽取 blob 是一个**独立于 B1 载荷的新条目**，格式（明文版本，随后加密）：

```
ExtractBlob {
    u32 magic/version
    u32 count
    repeat count:
        u16 dexNameLen, bytes dexName      // 原始 DEX 条目名，如 "classes-part1.dex"
        u32 codeOff                        // 该 DEX 内最终 code_item 偏移
        u16 clsLen,  bytes cls             // 类描述符（惰性回填按类索引需要）
        u16 nameLen, bytes name            // 方法名（诊断用）
        u16 protoLen,bytes proto           // 原型描述（诊断/校验用）
        u32 wordsCount, u16 words[wordsCount]   // 原始指令词（含 payload）
    u32 checksum                            // 防止解析损坏
}
```

- **放 assets，不放 native 常量**：理由见 TL;DR 第 3 条（`.so` 是 go:embed 的共享
  预编译产物，无法承载 per-APK 数据）。若未来愿意接受「加固时用 NDK 重编一个 per-app
  `.so`」，可以改放 `.so`，但那已经是 B7 的交付约束，不建议在 B5 里引入。
- **加密方式复用 B1**：B5 Pass 只把**明文 blob**放进 `Artifact`；由 B1（它持有载荷密钥）
  用 `pack.Encrypt(blob, key, IVFromSeed(seed+"/extract/"+dexName))` 加密后作为
  `assets/<word>_<hex>.<ext>` 条目加入，并把条目名记进 `shellPayloads`（新增
  `Extracts []ExtractItem{Asset,Name,Size}` 字段）。这样密钥来源（C1 native 派生或内联）
  与载荷完全一致，B5 不需要自己碰 crypto。
- **B8 容器化必须一并搬迁**：`internal/passes/container.go` 现在只重写
  `sp.Items[i].Asset`；落地时要把 `Extracts[i].Asset` 也纳入同一套搬迁逻辑，否则启用
  B8 的产物里 blob 还留在原路径、而壳按容器路径找不到它。
- **惰性回填按类索引**：native 在 `VM`/`fill` 初始化时把 blob 解析为
  `classDesc -> []entry` 的哈希表（一次 O(count)），之后每次 `findClass` 只处理该类条目。

### 2.5 运行时如何回填，以及回填时机

**回填的是 ART 的 mmap，不是磁盘文件，也不是「换成 native 实现」。**

流程（推荐形态：按类惰性回填）：

```
B5 计划（Artifact: "B5.plan"）
   └─ B1 加密 blob 成 assets，登记进 shellPayloads.Extracts
        └─ B3 生成 Loader 时：
             1. 读取并解密全部 Extracts（复用 Loader 已有的 c(blob,key)）
             2. 调用 Native.extractInit(byte[] blobPlain, byte[] sig)   // 解析 classDesc 索引
             3. 用「自定义 DexClassLoader 子类 X」代替 DexClassLoader：
                class X extends DexClassLoader {
                    protected Class<?> findClass(String name) {
                        Native.fillClass(name);   // 回填该类的全部被抽取方法，写 ART mmap
                        return super.findClass(name);  // 此刻类才被 define/verify
                    }
                }
```

时序论证（这是本方案成立的核心）：

- `new DexClassLoader(...)` 时 ART 打开并 **mmap** 各 `d*.dex`（`DexPathList` →
  `DexFile.loadDex`）。此时映射存在但**没有任何业务类被 define/verify**。
- 之后框架或业务触发 `loadClass(name)` → `X.findClass(name)` → 我们先 `fillClass(name)`
  把该类方法的原始指令写回映射 → 再 `super.findClass(name)` 触发
  `DefineClass` + 校验。**回填严格早于校验**。
- `DexClassLoader` **不是 final**（`方案-B7-Dex2C.md` §B3 已确认；`InMemoryDexClassLoader`
  才是 final）。子类化是公开 API，不触发隐藏 API 限制。

native `fillClass(name)` 的实现（C，落在 `apkguard.c`，复用现有 `/proc/self/maps` 解析基础）：

1. 在 `classDesc -> entries` 索引里查出该类的条目；空则立即返回 0（绝大多数类走这条快路径）。
2. 对每个涉及的 `dexName`，在 `/proc/self/maps` 中找到该 `d*.dex` 的映射行，取起始地址与
   权限位；若该行 offset 非 0，则文件偏移 0 的地址 = `start - offset`。
3. `mprotect(page_start, page_len, PROT_READ|PROT_WRITE)`；把每个条目的
   `words[]` 写到 `base + codeOff + 16`；再 `mprotect(..., 原始权限)` 恢复。
   - ART 对普通 DEX 用 `MAP_PRIVATE` 映射，`mprotect` 加写权限走 COW，即便文件是
     `setReadOnly()` 后的只读文件也应成功；若某内核拒绝，回退用 `/proc/self/mem`
     在映射地址上写（private 映射同样触发 COW）。
4. 返回成功改写的 code_item 数。

**M1（先落地）用粗粒度版本**：不子类化，直接在 `new DexClassLoader` 之后一次性
`Native.fillAll()` 回填全部条目。它同样是「mmap 之后、首个业务类 define 之前」，正确性与
惰性版相同，只是明文窗口更大、实现更简单。惰性版是 M2 增强（见 §6）。

**回填时机为什么不能更早**：B2 的 `attachBaseContext` 里 Loader 还没跑，载荷文件还没落地、
更没被 ART mmap，native 没有地址可写；「在 ART 校验之前」这个条件只有在 DEX 被 mmap 之后、
`findClass` 被调用之前才同时满足。这也是对 `剩余功能落地设计.md`「挂到 B2 之前由 native
完成」的纠正。

**回填失败处置：fail-fast，绝不静默降级。** 若某方法回填失败而类被放行，ART 执行 stub 会
返回默认值（0/null），产生**静默错误结果**——比崩溃更糟。因此 `fillClass` 返回的计数与
期望不符时，走与 D1 相同的终止路径（`System.exit` / `Process.killProcess`）。`-debug-shell`
时可先弹一条不含任何「extract」字样的通用失败 Toast（避免成为定位 oracle，参考
`方案-载荷完整性.md` §2.6 的约定）。

### 2.6 回填对异常表与分支的影响

- 回填的 `words[]` 是**原样**的最终指令词，`tries`/`handler` 字节从未被改动，地址无需重算。
- stub 长度与原始长度相同，`InsnList`/`CodeItemFull` 的所有偏移假设在回填前后一致。
- 若被抽取方法内部含 `goto`/`switch payload`，payload 也属于 `insns`，一并被抽取与回填，
  不需要单独处理（这也是 B5 比 B6 简单的地方）。

### 2.7 ART 的 `Verify` 与 `dex2oat` 会不会在回填前拒绝这个 DEX（本方案最大风险，正面回答）

**会，而且这是必须逐版本实测的硬风险。** 分四层回答：

**（1）DexFile 打开期的整文件结构校验。**
`DexPathList` 打开 DEX 时会做结构校验（`DexFileVerifier`），它逐条扫描指令宽度、
`code_item` 结构、try/handler 结构，但**不校验方法体的类型安全性**。我们的 stub
（nops + return）在结构上是完全合法的，因此这一层**预期通过**。但有两个待确认点：
- 具体方法带非空 `tries` 时，stub 指令落在 try 区间内是否被结构校验器接受（v1 用
  「跳过含 try 的方法」规避）；
- stub 的 `const/4 0 → return <非 int 类型>` 是否被接受（zero 类型兼容性，见 §2.3）。

**（2）类链接/首次调用期的方法体校验。**
类型安全校验发生在类 `DefineClass` 时（按类惰性）。我们在 `findClass` 中、`super.findClass`
之前回填，因此校验看到的是**原始字节码**，不是 stub——这一层被时序规避。

**（3）`dex2oat` / JIT 提前编译 stub。**
若 ART 在回填之前就对该类做了 verify/编译（例如安装期后台 dexopt 扫到、或某版本对
动态加载的 DEX 做预编译），它编译的是 stub，之后即使内存被改也不会重编——表现是
**「应用不崩，但被抽取方法永远返回 0/null」**，这是最隐蔽的失败模式。缓解：
- 回填发生在 `findClass` 内、`super.findClass` 之前，而 ART 的 verify/编译正是由
  `super.findClass` 触发，二者不会颠倒；
- `d*.dex` 落在应用私有目录、不是安装期 APK 的一部分，通常不进入安装期 dexopt 范围；
- 仍必须在真机上用「被抽取方法返回值正确」断言来反证（见 §4 判据 6）。

**（4）vdex / oat 缓存。**
磁盘上的 `d*.dex` 每次启动都由密文重新解密生成、内容确定（恒为 stub），因此 ART 的
文件级校验值稳定，不会因「文件变了」而反复失效；而内存回填不改变文件。风险在于若某
版本把「校验结果」缓存到 vdex 并跨启动复用，缓存对应的仍是 stub 语义——所以（3）的
「返回值断言」同样覆盖此风险。回填一旦发生在缓存使用之前，缓存的行号/结构信息依然与
回填后的代码同构（等长），不冲突。

**验证方法（必须做，不接受「理论上没问题」）：**

1. 写一个不依赖本工具的独立探针 DEX/Activity：构造一个「具体方法 `code_off=0`」的 DEX
   与一个「等长 stub」的 DEX，在目标 API（至少 30 / 34 / 36）模拟器上分别 `DexClassLoader`
   加载并调用，抓 `logcat`，记录：
   - `code_off=0` 到底报什么（`VerifyError`/`NoSuchMethodError`/静默）、在哪个版本报；
   - stub 各返回类型是否被接受。
   这一步产出「禁用清单」（哪些 API 不能上 B5），也直接支撑 §2.3 的取舍。
2. 在 `-debug-shell` 排障版里，Loader 回填后回读该方法的第一个指令词并打日志，确认
   写入生效（`emitToastReg`/`Log.i` 已有模式）。
3. 用 `adb logcat` 断言无 `VerifyError`、无 `Bogus handler offset`、无
   `invalid branch target`、无 `FATAL EXCEPTION`；用「被抽取方法返回已知常量」的测试
   方法断言返回值正确（证明执行的是原始码而非 stub）。

## 3. 与现有 Pass 的交互与执行顺序

### 3.1 注册位置

`passes.Registry()` 的注册顺序即执行顺序（同层稳定排序）。B5 建议注册在
**`splitDex`(B4) 之后、`encryptDex`(B1) 之前**：

```go
r.Register(&splitDex{})       // B4
r.Register(&extractFunc{})    // B5  ← 新增
r.Register(&encryptDex{})     // B1
r.Register(&payloadContainer{}) // B8
r.Register(&appReplace{})     // B2
r.Register(&classLoader{})    // B3
```

理由（每条都是硬约束）：

1. **必须在 A1/A2/A3/A4 之后**：抽取的指令字节必须是最终字节（见 §2.1）；A2/A3 会改写
   `const-string`，A4 会清 debug_info。registry 里 A1~A4 都在 L1 块（远早于 B4）。
2. **必须在 B4 之后**：B4 按类把 DEX 拆成多份并重建，`code_off` 与「方法属于哪个
   payload」都在拆分后才定；B5 必须看到拆分后的最终布局。
3. **必须在 B1 之前**：B1 会加密并移除明文 DEX，之后没有明文可抽。
4. **必须在 B2/B3 之前**：B3 的 Loader 要消费 `"B5.plan"` 生成 `fillClass`/`fillAll`
   调用；B5 本身不改壳 DEX，只写共享状态与（经 B1）加 assets。
5. **与 B8 的顺序**：B8 在 B1 之后，负责搬迁 assets 条目名；B5 的 blob 条目必须
   （经 B1 加入后）被 B8 一并搬迁（见 §2.4）。

### 3.2 与 A1 改名、A4 去调试信息的关系

- **A1**：B5 在 A1 之后，抽取 blob 里记录的 `cls/name/proto` 都是**改名后**的名字；惰性
  回填按 `findClass` 收到的类名（也是改名后的）匹配，二者天然一致。A1 对 `native` 方法
  不改名，与 B5 无冲突（B5 不改 `ACC_NATIVE`，方法仍是普通方法）。
- **A4**：B5 在 A4 之后，被抽取方法的 `debug_info_off` 已是 0（若启用 A4），stub 保留
  该字段为 0，无额外处理。未启用 A4 时保留原 debug_info，等长 stub 不破坏其地址一致性。
- **A2/A3**：B5 在其后，因此抽取到的是 A2/A3 改写后的字节；回填后 ART 执行的就是
  字符串已加密/数组化的版本，与 A2/A3 的设计完全一致（不需要对抽取方法做特殊排除）。

### 3.3 依赖校验（`config.Validate` 需要补）

当前：`"B5": {{"B1", ...}}`。落地方案要求补为：

```
"B5": {{"B1","抽取的 DEX 必须先被加密才有防护价值"},
       {"B2","回填驱动挂在壳 Application/ClassLoader 接管链路上"},
       {"B3","回填调用由 B3 生成的 Loader 触发"},
       {"C1","回填所需的 native 库与桥接类由 C1 注入"}}
```

不支持「B5 单独注入 native 库」的另一套路径：C1 已经定义了 native 库/桥接类的唯一
来源（`nativebridge.go` + `embed.go`），B5 复用它可避免两份 `System.loadLibrary`
与两套 JNI 符号。若产品上确需 B5 不依赖 C1，则在 C1 之外单独抽一个「native 基础设施」
Pass，而不是让 B5 自己注入，但那属于额外重构。

## 4. 验收标准（可自动化断言）

对齐本项目既有守卫风格（`apkguard/internal/dex/artifact_test.go` 在**产物字节**上做
结构体检；`scripts/verify-products.py` 对功能项做产物断言）。B5 新增守卫建议命名
`extract_test.go`，全部用 `t.Errorf`/`t.Fatalf` 而非只 `Log`，失败信息必须写清
「ART 会怎么报」。

| # | 判据 | 自动化做法 | 防住的回归 |
|---|---|---|---|
| 1 | **被抽取方法 `code_item` 长度为「原长」（等长）且指令为 stub** | 解密 payload，解析每个目标方法的 `CodeItemFull`，断言 `InsnsSize` 与抽取前记录一致，且指令词等于 stub 模式 | 抽取实现写坏长度/漏补 `nop` → 结构非法或 `invalid branch target` |
| 2 | **`code_off` 非 0 且指向合法 `code_item`** | 断言目标方法 `CodeEntry.CodeOff != 0`，`ParseCodeItem` 成功 | 误用「清零 `code_off`」方案 → 具体方法无 code，`VerifyError`/`NoSuchMethodError` |
| 3 | **产物中不存在原文指令序列** | 对每个抽取方法，把抽取前指令词序列做哈希；扫描产物所有条目与解密后 payload 的字节流，断言哈希对应的字节串不出现 | 「抽了但原文还在」（blob 未加密、或旧明文 DEX 未移除） |
| 4 | **抽取 blob 与计划一致** | 解密 blob，断言条目数 == `B5.extracted` 统计、每条 `codeOff` 落在对应 payload 的 `code_item` 集合内、`words` 非空 | 偏移算错/漏记条目 → 回填到错误地址 |
| 5 | **磁盘空体率 100%** | 对抽样方法，用处理后的 DEX 指令流断言「非 stub 指令词数 == 0」 | stub 生成错误（如只替换了第一条） |
| 6 | **回填后 ART 正常执行且语义正确** | 真机/模拟器：进程存活、无 `VerifyError`/`Bogus handler offset`/`invalid branch target`/`FATAL EXCEPTION`；测试方法（被抽取）返回值与未抽取版本一致（解释器对拍 + 真机断言） | 回填时机晚于校验、回填地址错、stub 被执行 |
| 7 | **回填命中率 100%** | `fillClass`/`fillAll` 返回计数 == 计划数；不符时进程按 D1 失败路径终止 | 部分回填被放行 → 静默错误结果 |
| 8 | **`dex.Verify` + 六项结构守卫全绿** | 每次 Rebuild 后 `dex.Verify`；复用分支目标/异常处理器/`outs_size`/类标志/悬空引用/DEX 版本守卫 | 抽取破坏索引/偏移 |
| 9 | **确定性** | 相同输入 + 相同 seed，抽取集合与 blob 逐字节一致 | 无法复现、CI 无法对比 |
| 10 | **`B5` 不再是空操作** | 启用 B5 时若 `ExtractRatio` 使实际抽取为 0，必须报错或显式警告，不得静默 | 「声明已实现、退出码 0、实际没抽任何方法」 |
| 11 | **E6/minAPI 不回归** | B5 只新增 native 调用与 assets，不抬高 `injectedMinAPI`；原生库 ABI 集合仍与 APK 一致 | 误引入高版本 API 或补错 ABI |
| 12 | **B8 联动** | 同时启用 B8 时，抽取 blob 条目名也被搬迁到容器目录，且壳按容器路径能读到 | 「启用 B8 后 B5 blob 路径失配」→ 回填全部失败 |

补充：判据 1~5、8、9、12 可在 Go 单测（含 `testdata/` 固件与交付包）里跑，**不需要真机**；
判据 6、7、10 需要真机/模拟器（现有 `scripts/device-test.sh`）。

## 5. 风险与取舍

### 5.1 明确会破坏产物、不能做的做法

1. **把具体方法的 `code_off` 置 0 / 删除其 `code_item`**：ART 各版本行为不一致，可能整类
   被拒；且必然改变后续偏移、使 blob 记录失效。必须用等长 stub。
2. **在 `attachBaseContext` 里由 native 回填**：那时 DEX 还没被 mmap，无址可写。回填必须
   在 `DexClassLoader` 构造之后、`findClass`（define）之前。
3. **回填磁盘文件而不是 ART 内存映射**：写文件会让「磁盘空体」这一 B5 的核心收益消失
   （文件 dump 又能拿到明文），且与「已 `setReadOnly`、ART 已 mmap」的语义冲突。
4. **回填全部完成后不做校验就放行**：部分失败会导致方法执行 stub 返回默认值——静默错误
   结果。必须 fail-fast。
5. **把抽取 blob 放进 native 常量 / per-APK 重编 `.so`**：破坏「预编译 go:embed、单二进制、
   零 NDK 依赖」的定位（与 B7 的 NDK 冲突同源）。
6. **在 B1 之后才抽取**：明文 DEX 已被移除，无法再改。
7. **对 `<init>`/`<clinit>` 抽取**：构造函数 stub 无法通过 ART 校验；类初始化时机不可控。
8. **依赖 `dex2oat --compiler-filter=verify` 作为唯一验收**：README 已明确它对
   `handler_off`/`static_values` 类错误返回 rc=0 漏报；B5 的「stub 被执行」更是它完全
   看不到的失败。必须叠加真机返回值断言。
9. **回填后不恢复映射权限**：把 DEX 映射长期留在可写状态，既破坏 ART 的只读假设，也
   给攻击者留下可写窗口。必须写后立即恢复原权限。
10. **`mprotect` 失败时静默继续**：应走 fail-fast；否则等于没回填。

### 5.2 只在特定 Android 版本可用 / 版本相关风险

- **`DexClassLoader` 子类化**：所有目标版本可用（非 final）。
- **`mprotect` 私有映射写权限**：Linux 语义，全版本可用；但个别厂商内核/SELinux 策略
  可能限制，需真机确认并保留 `/proc/self/mem` 回退。
- **`setReadOnly` 与 targetSdk 34**：B3 已按 targetSdk 处理（`LoaderSpec.MarkReadOnly`），
  B5 不额外引入。
- **`code_off=0` 的具体方法**：**禁用**（见 §2.3，属明确不能用）。
- **vdex/oat 缓存版本差异**：见 §2.7（4），靠返回值断言覆盖。

### 5.3 取舍

- **惰性按类 vs 一次性**：惰性把明文内存窗口压到「类被加载之后、进程结束前」，代价是
  Loader 需要自定义 `DexClassLoader` 子类与按类索引；一次性实现简单、窗口大。M1 用
  一次性，M2 切惰性（§6）。
- **覆盖率 vs 安全**：v1 跳过含 try 的方法、`<init>`/`<clinit>`、过小方法，覆盖率会低于
  「按指令数全抽」。这是为通过 ART 校验与缩小失败面的必要取舍。
- **强度 vs 复杂度**：公开 API 内做不到「内存 dump 永远为空」。若必须达成该目标，应转向
  B6（私有指令集，内存里从无原始字节码），而不是在 B5 上叠加 ART 内部 hook——后者每
  一个大版本都要重新适配，与本项目「版本归一化 + 产物级守卫」的稳健路线冲突。

## 6. 最小可落地子集

**目标：独立验证、不破坏现有三个真实应用的运行。**

**M1（第一个可交付切片，一次性回填）**

范围（全部满足才抽取）：

- 方法非 `abstract`/`native`，不是 `<init>`/`<clinit>`；
- `insns_size >= 8`，stub 能放下；
- `tries_size == 0`（v1 跳过异常表）；
- 由 `-extract-ratio`（已有 `config.Options.ExtractRatio`）从「大方法优先」里确定性选；
- 只对 payload DEX 生效（壳 DEX、注入类天然不参与）。

实现：

1. `dex.RebuildOptions.Extract` + `assemble.go` 里等长 stub 替换 + blob 收集（约 100~150 行 Go）；
2. `passes/extract.go` Pass + registry 注册（B4 与 B1 之间）+ `B5.plan` 共享状态；
3. `pack`/B1：加密 blob 成 assets，`shellPayloads.Extracts` 字段；B8 搬迁联动；
4. `NativeBridgeSpec`/`Native` 增加 `extractInit([B[B)V` 与 `fillAll()I`（native；
   `<clinit>` 已 loadLibrary，无需新库）；
5. Loader：在 `new DexClassLoader` 之后调用 `Native.fillAll()`，失败即终止；
6. `extract_test.go`：判据 1/2/3/4/5/8/9/12。

M1 能独立验证的点：解密 payload 里目标方法为 stub 且等长、原文不残留、真机启动正常且
被抽取方法返回正确值、现有功能性测试全绿。

**M2（增强，惰性按类回填）**：注入 `DexClassLoader` 子类（在壳 DEX 内生成），覆写
`findClass` 先 `fillClass(name)` 再 `super.findClass`；blob 按 `classDesc` 建索引。
不改变 M1 的产物格式，只把「一次性」换成「按需」，缩小明文窗口。

**M3（远期，可选）**：ART 内部 hook 实现「方法首次调用回填 + 用后擦除」，才能对内存
