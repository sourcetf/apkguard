# 方案：A1 包合并（把多个原包合并进同一个新包）

> 状态：设计方案，**本文件不修改任何代码**。
> 目标读者：实现 A1 包名压缩的工程师。
> 相关文件：`apkguard/internal/passes/rename.go`（`pkgAlias`/`keptPkgs`/`classPkgOf`）、
> `apkguard/internal/passes/shrink_test.go`、
> `realworld/实测记录-三应用全选项.md` §「-package-shrink 把所有类压进默认包」、
> `APK加固功能设计文档.md` §A1/§A13。

## 1. 目标与预期效果

### 1.1 现状

CLI 的 `-package-shrink`（`cmd/apkguard/main.go`）在 `passes/rename.go` 里做的是
**「按包压缩」**：

- 每个原包整体映射为一个无意义短包名 `Lpa/`、`Lpb/`……（`pkgAlias`）；
- **含保留类的包整体保持原包名**（`keptPkgs`），因为把可改名类搬离该包会让原本同包
  的 package-private 访问变成跨包访问，实测报
  `IllegalAccessError: Illegal class access: 'ac' attempting to access 'com.termux.app.utils.CrashUtils$1'`。

效果：**类名读不出原包名，但包边界被完整保留**；默认包类比例基本不变（原本有包的类
压缩后仍在新短包里，不进默认包）。

### 1.2 参考样本的水平

参考样本（`APK加固功能设计文档.md` §样本分析）的 loader：

| DEX | 可解析类数 | 默认包（无包名）类数 | 比例 |
|---|---|---|---|
| classes.dex | 655 | 466 | **71.1%** |
| classes2.dex | 638 | 489 | **76.7%** |
| 合计 | 1293 | 955 | **73.9%** |

即样本把**七成以上的类放进默认包**（`LA;`、`La0;`、`LZ3$j$a;`），这是「类名里读不出
任何结构」的最强形态，也是混淆器的强信号。当前我们做 `-package-shrink` 时默认包
类比例是 **0%**（对原本有包的类而言）。

### 1.3 目标

| 指标 | 当前（-package-shrink） | 目标 |
|---|---|---|
| 可改名类的默认包比例 | 0% | **≥ 70%**（对齐样本 71%~77%） |
| 可改名类所在包数 | 原包数 N（每个原包一个短包） | **1 个**（默认包，或退而求其次一个短包） |
| 含保留类的包 | 原样保留 | 原样保留（不变式） |
| 三个真实应用 | 运行正常 | 仍运行正常（本方案唯一硬约束） |

量化口径：加统计项 `A1.packages_before`、`A1.packages_after`、
`A1.classes_default_pkg`、`A1.default_pkg_ratio`，用三个真实应用在 CI 里断言。

> 注意：这里要区分「默认包比例」和「单包比例」。合并进**一个短命名包**就能让
> 「可读结构 = 0」，而默认包还有额外收益（Java 源码层面无法表达）与额外风险
> （`Class.getPackage()` 返回 null，见 §5）。§6 建议分两步走。

## 2. 技术方案

### 2.1 现有算法回顾

```
第一轮：对每个可改名类，记录其原包 classPkgOf(desc)；
        枚举每个类的 plan，未出现在 plan 里的类 = 被保留类 -> keptPkgs[原包]=true。
包别名：对每个「不含保留类」的原包，分配 alias = "Lp"+encodeShortName(i)+"/"，
        并确保不与 existingPkgs 冲突。
类名分配：可改名类的包前缀 = keptPkgs 命中 ? 原包 : pkgAlias[原包]。
```

要点：**粒度是「包」**，从不把一个包的类拆到两个新包（拆分正是历史崩溃原因）。

### 2.2 关键洞察：合并与拆分是不对称的

| 操作 | 对 package-private 的影响 | 会不会崩 |
|---|---|---|
| **拆分**：把一个原包里的部分类搬到别的新包 | 原本同包的访问变跨包 | **会**（`IllegalAccessError`）；这就是当前不敢用默认包、且 `ShrinkPackage` 库 API 被弃用的原因 |
| **合并**：把多个**整包**搬进同一个新包 | 原本跨包的访问变同包（访问权限**变宽**） | **不会**因访问权限崩；真正的风险是「凭空造出覆写」等语义变化（见 §2.3.3） |

因此「合并」在访问权限维度是安全的，前提是**整包粒度**。这给了我们向默认包推进的
理论基础：把所有「不含保留类」的原包整包合并进默认包即可。

但合并有一个必须处理的副作用：**两个原本在 Java 源码里跨包的类，合并后彼此同包，
package-private / protected 的成员可能从「不构成覆写」变成「构成覆写」**。

### 2.3 安全判据

#### 2.3.1 整包与保留类（继承现有不变式）

S1. **整包粒度**：一个原包要么整体移到目标包，要么整体保持原包名，绝不拆开。
S2. **含保留类的包不动**：沿用 `keptPkgs`。理由不仅是访问权限，还有：
    - `$` 内部类与外层类被一起保留，包必须一致；
    - 入口组件类（Manifest 引用）被保留，包保持；
    - native 类被保留（JNI 符号含包名），包保持。
S3. **内部类**：`Outer$Inner` 只要外层与内层都在同一个包里（S1 保证），二进制名与
    包无关，安全。

#### 2.3.2 目标包名不与框架 / 库 / 既有包冲突

S4. 目标包名（默认包为「无包名」；短包形如 `Lp/`）必须：
    - 不等于任何 DEX 中已存在的包前缀（`existingPkgs` 检查已有）；
    - 不等于任何「被引用但未在本 APK 定义」的平台 / 三方库类所在包前缀。
      实现上取**全部 DEX 的 type_ids**（含未定义的外部类型）的包前缀集合做避让；
      现有代码只登记了 `NType` 全部类型用于 `used`，但 `existingPkgs` 只从
      `isClassDesc` 收集——落地时确保把外部类型包也纳入避让集合。
    - 绝不使用 `java/`、`android/`、`androidx/`、`kotlin/` 等前缀（`javaPrefixes`
      已有白名单，可直接复用）。
    默认包（空前缀）天然不会与任何命名包冲突，但仍要防「新类描述符与既有默认包类
    重名」（`used[desc]` 已保证）。
S5. 默认包里的类**不能**被命名包中的 Java 源码直接按简单名引用——但 DEX/ART 按描述符
    解析，不看源码，无影响。唯一现实风险是反射 / `getPackage()`（§5）。

#### 2.3.3 覆写安全（合并引入的唯一语义风险，必须逐一证明）

定义「危险对」：类 `A` 与类 `B`，`B` 通过 super 或 interface 与 `A` 有继承关系，
`A`、`B` 原本在**不同**包，且两者都声明了同名同原型的方法 `m`，`m` 的可见性为
package-private 或更宽，且**至少一方是 package-private**（protected/public 的跨包
覆写本来就已经成立，合并不改变；只有 package-private 才会「跨包不覆写、同包才覆写」）。

- S6. 对每个危险对，合并后 `A.m` 与 `B.m` 会构成覆写。**如果这不是本次改名有意为之，
  就禁止合并这两个包（或禁止把它们放进同一目标包）。**
- S7. 但本方案与《方案-成员名覆盖率.md》协同：A1 的全局命名器给**不同虚方法族**分配
  **全局唯一**的新名。因此只要 `A.m`、`B.m` 原本不是同一个虚方法族，改名后它们名字
  不同，**不会构成覆写**，危险对自动消解。
   - 唯一残留：`A.m` 或 `B.m` 因反射 / 白名单等原因**被保留原名**，且恰好重名同原型。
    此时必须先做 S6 检查，命中的包不进同一组。
   - 实现：复用成员名方案的「虚方法族」并查集；对危险对检查「两族是否会被赋成同名」。
    因为新名全局唯一，实际只需检查**保留名集合**里是否存在跨包的同名同原型父子成员。
- S8. 接口同理：接口 `I` 与实现类 `B` 跨包时，`I.m` 若为 package-private 不可能被
  外部实现（合法 Java 不允许），所以接口方法实际都是 public（或同包）。合并不会新增
  接口覆写，因为接口方法 public 的跨包覆写原本就成立。
- S9. **字段无虚派发**：字段隐藏不改变行为；且跨包引用 package-private 字段在合法
  Java 中不存在，S1 保证不产生非法引用。
- S10. **不可见父类**：`B` 继承框架类 `F`（如 `View`）时，`B` 的 package-private
  方法原本就不覆写 `F` 的 package-private 方法（不同包）。合并**不改变 `F` 所在包**
  （`F` 不在我们的 type_ids 定义集里，包前缀已避让，见 S4），所以关系不变。
  `hasInvisibleSuper` 的保守保留规则不受影响。

#### 2.3.4 类名唯一性

S11. 合并后同一目标包内的类简单名必须唯一：现有 `seq` + `used[desc]` 全局分配机制
    已保证新描述符唯一；合并只是让更多类共享同一个包前缀，`used[desc]` 会自然去重。
    注意 `encodeShortName(seq)` 是全局递增的，不会因包合并而碰撞。
S12. 不得与既有默认包类 / 保留类重名（`used` 已包含全部 `type_ids`）。

### 2.4 合并分组算法

把「包」当节点建图：

- 对每个「不含保留类」的原包 `P`，若与另一个同组候选包 `Q` 之间存在 §2.3.3 的
  **危险对且无法由唯一命名消解**（即涉及保留名重名同原型），则 `P`、`Q` **不可合并
  到同一目标包**。
- 由于 A1 的全局命名器让绝大多数危险对自动消解，实际做法可以简化为：

```
1. 收集 candidates = { 不含保留类的原包 }。
2. 计算「保留名危险边」集合 E：跨包父子成员中，两边名字都在 Keep/白名单/反射集合里
   且同名同原型的。
3. 把 candidates 按 E 做连通分量（有边的包不能同组）。
4. 对每个连通分量分配一个目标包：
   - Phase 1：一个短包 "LpN/"（全局唯一，先到先得），分量内所有原包合并进它；
   - Phase 2（可选）：默认包（无前缀）。
5. 含保留类的包保持原包名（S2）。
```

Node: 也可以更简单——**先合并进一个包，遇到保留名危险边时把这些包各自拆到独立短包**
（退化到「每个原包一个短包」的现状）。但连通分量更干净。

### 2.5 与类改名 / 成员改名的关系

- 包合并改的是**类描述符**，仍在 A1 第一轮类名分配里完成，不新增一层。
- 成员名方案（另一份文档）让危险对大幅减少（全局唯一命名），两者应一起实现；
  若只做包合并不做成员命名，则要严格跑 §2.3.3 的 S6 检查。
- 反射保类（`reflectedClasses` / `passiveClassRefs`）会让类**保留**，其包因 S2 保留，
  **不会**被合并——这天然保护了「被布局 / 资源按名字引用的自定义 View 所在的包」。

## 3. 与现有 Pass 的交互与执行顺序

**不改变顺序，A1 仍是第一个注册的 Pass。** 理由：

1. 包合并是类描述符的一部分，必须在任何消费最终类名的 Pass 之前：A2/A3（字符串 /
   字节码改写）、A4（去调试）、A8/A13（注入类需避让既有类名）、B1/B8（加密载荷后
   DEX 不可解析）、B2/B3/C1/D1（壳与注入）。
2. **B4（多 DEX 拆分）在 A1 之后**：合并后的包名已分配到类描述符上，B4 只按类切分。
   需要指出一个正向交互：**合并让跨 DEX 的 package-private 访问更安全**——ART 判定
   package-private 依据的是运行时包名而非 DEX，同一包名分散在不同 DEX 仍算同包；合并
   减少了包的数量，也就减少了「同包名跨 DEX 是否一致」的组合数。B4 之后不得再改包名。
3. **A5/A11 资源混淆 / 扁平化**：独立于代码包名；资源按名字引用类的地方由
   `passiveClassRefs` 保类（进而保包），无交互。
4. **A14/A15**：与包无关。
5. **E1 签名 / E2 对齐 / E6 自检**：在最后，无交互。

## 4. 验收标准（可自动化断言 + 回归保护）

**产物合法性**

- R1 `dex.ValidateDescriptors(out) == nil`（每个 DEX）。
- R2 `dex.Verify(out) == nil`。
- R3 全 APK 类描述符唯一（含默认包 / 短包内）。

**包结构不变式**

- R4 **整包性**：对每个原包 `P`，其所有可改名类映射到的目标包必须是**同一个**
  `newPkg(P)`；`P` 到新包的映射是一个函数（没有「同包被拆到两个新包」）。
  断言方式：遍历产物，按「原描述符 -> 新描述符」逐类记录，检查 `P` 的像只有一个。
- R5 **保留包原样**：含保留类的原包，其可改名类仍在该原包内（名称变短、包不变）。
  对应现有 `TestPackageShrinkKeepsPackagesWithKeptClasses`。
- R6 **默认包比例**：`A1.classes_default_pkg /（可改名类数 + 保留类数）>= 0.70`
  （Phase 2；Phase 1 断言「单包比例 = 1」）。
- R7 **框架避让**：产物中不存在新包名等于任何既有 / 外部类型包前缀，或命中
  `javaPrefixes`。

**覆写与访问安全（回归保护）**

- R8 **package-private 不跨包化**：对原始 APK 中每个「引用方 C 的静态类型 -> 解析到
  定义类 D」且 `C`、`D` 原本同包的成员引用，断言产物里 `C'` 与 `D'` 仍在同一包。
  因为 S1 只做整包移动，这条应恒成立；用于抓「未来有人改成拆分」。
  参考 `rename_inherited_test.go` 的 `resolvesVisibly` 思路。
- R9 **未新建覆写**：对产物中任意可见父子 / 接口关系 `(A,B)`，若产物里 `B.m` 与
  `A.m` 同名同原型、且二者在原始中**不同包**（即原本不覆写），则失败。
  这是 §2.3.3 的落地断言。与《方案-成员名覆盖率.md》R7 共用实现。
- R10 **保留类/入口类可解析**：Manifest 组件类、native 类、被资源引用的自定义 View
  类在产物中仍以原文类名（或合法改名后仍可被 Manifest/资源找到）存在；包名不被合并
  破坏。

**回归测试**

- R11 `passes/shrink_test.go` 全部通过。若新增合并模式改变默认行为，必须**新增开关**
  （见 §6）而不是改这三个测试的断言；`TestPackageShrinkCompressesPackageNames`
  明确断言「两个原包 -> 两个不同短包」，只有在新开关关闭时才成立。
- R12 三个真实应用 + `testapp` 全选项复验：进程存活、主界面 resume、logcat 零
  `IllegalAccessError` / `AbstractMethodError` / `NoSuchMethodError` / `VerifyError`。

**新增建议测试**

- `internal/passes/package_merge_test.go`：三个包，其中两包各有父子类且存在
  package-private 同名方法（保留名），断言这两个包不被合并；第三个包被并入目标包。
- `internal/passes/package_merge_default_test.go`：断言默认包比例达到阈值、
  且产物里没有残留原包名。
- `internal/passes/package_merge_kept_test.go`：含保留类的包整体不动，其余合并。

## 5. 风险与取舍（哪些做法会破坏产物，为什么不能做）

| 禁止的做法 | 后果 | 原因 |
|---|---|---|
| **拆分**一个包（部分类搬家） | `IllegalAccessError` | 历史实测 Termux `CrashUtils$1`；package-private 变跨包 |
| 把含保留类的包整体合并走 | 保留的外层 / `$` 内部类留在原包，访问断裂 | 同上 |
| 目标包名撞上框架 / 库包名 | 同名类解析歧义、链接错乱 | 必须避让全部既有与外部类型包 |
| 合并时让两个**保留名**的跨包父子成员同包 | 凭空生成覆写，派发目标改变 | §2.3.3；需 S6 检查 |
| 依赖 `getPackage()` 应用的类进默认包 | `getPackage()` 返回 `null`，NPE | Java 默认包没有 Package 对象 |
| 合并后仍按原简单名引用 | DEX 按描述符，不存在此问题；但反射按旧包名会失效 | 反射拼包名不可穷尽（残余风险） |
| B4 之后再改包名 | 跨 DEX 包名不一致 | B4 已按类切分，改包名需同步全部引用 |

**残余风险（如实记录）**

- **默认包 + `Class.getPackage()`**：这是把比例推到 71%~77% 的最大障碍。应用若调用
  `getClass().getPackage().getName()`、`Package.getPackage(...)`、
  `getResourceAsStream("/com/foo/...")` 之类，会 NPE / 找不到资源。
  缓解：默认包模式做成**显式开关**（默认关闭），并在文档 / README 说明风险；
  Phase 1 先用「合并进一个短命名包」拿到几乎等价的结构隐藏效果。
- 反射拼接的旧包名（`"com."+"foo."+...`）无法静态穷尽；
  与类改名方案的残余风险同源。
- 三方库通过 `Class.getPackage().getName().startsWith("...")` 做分支判断的场景，
  会因包改名行为改变（类改名早已有同类风险）。

## 6. 最小可落地子集

**切片：新增开关 `-package-merge`，把「不含保留类」的多个原包合并进**一个**短命名包
`Lp/`（不默认进默认包）。**

为什么这样选：

- 不改变现有 `-package-shrink` 的语义与回归测试（`shrink_test.go` 三个测试原样通过），
  新行为由新开关启用，风险可控、可回退。
- 短命名包 `Lp/` 与默认包在「类名读不出结构」上几乎等价，且**不触发 `getPackage()`
  为 null** 的问题。
- 不涉及覆写风险的最大来源：先不做成员改名也能合并，只要跑 §2.3.3 的 S6 检查；
  配合成员名方案后 S6 几乎总是通过。

**实现要点**

1. 在 A1 第一轮把 `pkgAlias` 从「每包一个 alias」改为「每组合一个 alias」：
   按 §2.4 连通分量分组，`-package-merge` 时所有安全包共用一个 `Lp/`。
2. 保留 `keptPkgs` 与 `classPkgOf` 逻辑不变。
3. `existingPkgs` 的避让集合扩为「全部 `type_ids` 的包前缀」，防撞外部库。
4. 加 §4 R1~R10 断言与 `A1.default_pkg_ratio` 统计（此时 ratio 仍为 0，
   另加 `A1.single_pkg_ratio`）。
5. 自检通过后真机跑三个应用。

**Phase 2（可选，目标默认包）**：把目标包从 `Lp/` 换成默认包，开关另设
（如 `-package-merge=default`），并在 README 明确 `getPackage()` 风险。

**预期提升**

| | 当前 | Phase 1（合并短包） | Phase 2（默认包） |
|---|---|---|---|
| 可改名类所在包数 | N | 1 | 1（无包名） |
| 默认包比例 | 0% | 0% | **≥ 70%**（对齐样本 71%~77%） |
| 结构可读性 | 包名无意义但边界可数 | 边界=1 | 边界=1，且源码无法表达 |

**不破坏三应用的信心来源**：整包移动不产生 `IllegalAccessError`；覆写危险由 S6 检查
兜底；框架包避让；保留包不动；全程真机复验。回退开关即关闭 `-package-merge`。
