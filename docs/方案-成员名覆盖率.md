## 1. 目标与预期效果

### 1.1 当前实测基线

以下数字是用**当前 HEAD 的二进制**、命令
`apkguard.exe -in <app>.apk -out <tmp>.apk -ks test.p12 -ks-pass apkguard -enable A1`
在三个真实应用上复现出来的（`-enable A1` 是在默认开启项之上追加 A1；A1 是注册表里
第一个 Pass，其统计只反映 A1 自身，后面的 A2/A3/A4/A14/E1/E2/E3 不影响 A1 的数字）：

| 应用 | 版本 | 可解析 DEX | 重命名类 | 重命名方法 | 重命名字段 |
|---|---|---|---|---|---|
| Dhizuku | 2.12.0（单 DEX） | 1 | 3047 | **53** | **0** |
| Termux | 0.118.3 x86_64 | 29 / 30 | 325 | **637** | **0** |
| RustDesk | 1.5.0 universal（Flutter） | 2 | 2613 | **10** | **0** |

与 `realworld/实测记录-三应用全选项.md` 记录的「全选项」数字（RustDesk 类 2785 /
方法 15 / 字段 0）相比，方法量级一致（都是个位数~十位数），差异来自版本与选项集，
不影响结论。**最关键的两个事实**：

1. **三个应用的字段改名都是 0**。字段名（`TAG`、`mInstance`、`VALUE` 之类）在 DEX
   字符串池里与框架 / 被保留类共用，于是被整体保留。
2. **单 DEX 应用（Dhizuku / RustDesk）的方法改名只有 10~53 个**，真正的业务方法
   几乎没动；类改名完全不受影响（数千个）。

### 1.2 目标（量化口径）

先定义两个可被脚本计算的比率，避免「覆盖率」含糊：

- **定义覆盖率** `= 被改名的方法（字段）定义数 / 全部「应用自定义」的方法（字段）定义数`。
  「应用自定义」= 定义在本 APK 的某个 DEX 里、且不属于平台 / 三方库前缀、且类本身在
  保留集之外的成员定义。
- **引用覆盖率** `= 被改写的 method_id/field_id 引用数 / 全部指向应用自定义成员的引用数`。

目标（Phase 3 完成时）：

| 指标 | 当前 | 目标 | 依据 |
|---|---|---|---|
| 字段定义覆盖率 | 0%（三个应用） | **≥ 60%** | 私有 / 静态字段在多数应用里占字段总数一半以上，且天然不参与覆写 |
| 方法定义覆盖率 | Dhizuku 个位数%、Termux 个位数%、RustDesk <1% | **≥ 70%** | 私有 / 静态 / 继承链完全可见的实例方法占应用方法绝大多数 |
| 方法绝对数（估计） | 53 / 637 / 10 | Dhizuku 6k~12k；Termux 8k~15k；RustDesk 3k~6k | 见 §2.6 的候选统计口径；须先用 Phase 0 统计真实候选数再钉死 |
| 字段绝对数（估计） | 0 / 0 / 0 | 每家 2k~8k | 同上 |

> 说明：上表「绝对数」是**估计值**，落地第一步必须先加候选统计
> （`A1.method_candidates` / `A1.field_candidates` / `A1.method_renamed` /
> `A1.field_renamed` / `A1.kept_by_*`），用真实数字替换估计值，再作为验收线。
> 这是为了满足「可自动化断言」的要求——没有候选数就无法断言覆盖率。

### 1.3 预期效果的定性描述

- 反编译后方法名 / 字段名不再可读，切断「按名字找核心逻辑」的路径；
- 字段不再是 0，`javap`/jadx 里结构信息大幅减少；
- 与 A2（字符串加密）叠加后，`strings` 里既看不到敏感串，也看不到业务语义名；
- 代价：字符串池里旧名字仍保留（见 §5），产物可能因此**略微变大**——当前实测
  `A1.saved` 已经是负数（-68 / -16360 / -5776 字节），本方案会让这个负数更大，
  属于可接受取舍。

## 2. 技术方案

### 2.1 为什么现在这么保守（根因）

**当前实现是按「名称字符串」全局决策的，而不是按「(类, 名字) 引用」决策。**

链条如下：

1. DEX 字符串池去重：方法名 / 字段名以**字符串索引**存在 `method_ids` / `field_ids`
   里，**多个类的多个成员引用可以指向同一条字符串**。例如 `get`,
   `getString`, `TAG`, `run` 这些名字，业务类与框架类（`android.content.Context`、
   `java.lang.Object`……）的 `method_ids` 共用同一个字符串索引。
2. 重建层 `RebuildOptions.Rename` 是 `map[旧字符串值]新字符串值`，在
   `buildPlan` 里按**字符串值**统一替换（`rebuild.go` 第 277~291 行：
   `values[i]` 被整体改写）。也就是说，**一旦改名，字符串池里所有引用该字符串的
   method_id/field_id 会一起被改**。
3. 于是 `planMethods` / `planFields` 只能对**每个名称字符串索引**做「全票通过」
   判定（`rename.go` 第 489~570 行）：取出 `method_ids` **全表**中引用该字符串的所有
   `(类, 原型)`，要求
   - 每个引用所在类都在 `classRename` 里；
   - 每个引用都能在可见继承链里找到声明（`resolvesVisibly`）；
   - 每个引用都不「可能覆写看不见的方法」（`mayOverrideInvisible`）；
   - 没有命中 `Keep` / `MemberKeep`。

   **只要有一个引用者不同意，整个名字就得全局保留。**
4. 多 DEX 更严：`passes/rename.go` 第二轮把每个名称交给所有用到它的 DEX「表决」，
   只要有一个 DEX 不同意，就写入 `MemberKeep` 全局保留（`passes/rename.go`
   第 282~313 行）。

**后果**：

- 一个名字只要与框架方法 / 被保留类 / 反射字符串 / 任一 DEX 的保守判据沾边，
  所有类的同名成员一起陪葬。字段名与框架 / 库的共用尤其严重，所以字段是 0。
- 「私有方法 / 私有字段」这种**根本不参与覆写、也不可能被外部类按名字调用**的成员，
  因为只是「恰好和别人同名」而被误伤。
- 判据粒度是 O(名称数)，不是 O(成员定义数)，精度天然差。

### 2.2 根本路线：按 (类, 名字) 引用决策 + 为改名引用追加字符串

核心思想一句话：**把改名单位从「名称字符串」换成「成员定义 / 虚方法族」，为每个要
改的引用在字符串池里新增一条字符串，只在目标 `method_id`/`field_id` 上把名字索引
指向新字符串，旧字符串原样保留给其他引用者用。**

本项目的重建流程**本来就支持追加字符串与新条目**（`Addition.Types` / `NewStrings` /
`buildPlan` 里 `extra` 集合与 `poolSet` 的合并），所以这条路是可行的，不需要重写 DEX
编码。

#### 2.2.1 定义解析（definition resolution）

对每个 `method_id` 引用 `R = (staticClass, name, proto)`（`staticClass` 是调用点写的
静态类型，可能不是声明类），沿**原始**继承链（super + interfaces，传递地，深度上限
沿用 32）解析出**声明类**：

```
resolveMethod(classDesc, name, proto) ->
    BFS/DFS over (byDesc[class].Super, byDesc[class].Interfaces)
    命中某可见 ClassInfo 声明了 (name, proto) -> 返回该类的描述符
    走到 java/lang/Object 且 objectHasMember(name, proto) -> 返回 Object（视为外部）
    走到 byDesc 里不存在的类（不可见父类型） -> 返回 INVISIBLE
    都找不到 -> 返回 NOT_FOUND（调用点静态类型上无可见声明）
```

字段同理（`resolveField(classDesc, name, type)`，字段类型参与 identity）。
`INVISIBLE` / `NOT_FOUND` 一律视为**不可改名**（这正是 `resolvesVisibly` 保护的
`dalvik.system.PathClassLoader.loadClass` 场景）。

#### 2.2.2 虚方法族（virtual family）——唯一会崩溃的地方

Java/ART 的虚方法是**按名字 + 原型动态解析**的。若子类 `B` 覆写父类 `A.m`，
则 `A.m` 的引用在运行时可能派发到 `B.m`；因此 `A.m` 与 `B.m` 必须**改成同一个新名**，
否则派发断裂（`AbstractMethodError` / `NoSuchMethodError`）。所以真正的改名单位不是
单个定义，而是**虚方法族**：

> 族 = 在「可见继承图」中，名字、原型相同、且以 super/interface 边相连的
> 非私有、非静态、非构造方法的等价类。

- 私有方法、静态方法、`<init>`/`<clinit>` **不属于任何族**，各自独立（它们不参与
  虚派发）。
- 族内所有成员在**所有 DEX 里**必须得到同一个新名。
- 接口方法也是族成员。若族里任何一个节点落在 DEX 之外（不可见），或实现了一个不可见
  接口，整族保留（继承链不完全可见就无法证明它没有覆写看不见的方法）。
- 注意：`isKeptMember` 的 Keep 规则能命中族成员时，整族保留。

#### 2.2.3 全局三轮结构（替换现有的「第一轮类名 + 第二轮成员名」）

```
第一轮   类名全局决策：基本沿用现有逻辑，产出全局 ClassMap。
第一轮半 成员图全局汇总：
          ① 每个 DEX 遍历 method_ids / field_ids 全表，做 §2.2.1 定义解析；
          ② 建全局注册表 Registry：键 = (旧声明类描述符, kind, 名字, 原型/类型)
             -> 定义记录（含可见性、native、类是否在改名集、族 id）；
          ③ 用 super/interface 边做并查集，把定义合并成全局虚方法族；
          ④ 汇总全局「保留证据」：所有 DEX 的 const-string 名字集合、注解字符串、
             passive 成员引用、native 类、入口类、Keep 规则。
第二轮   全局决策 + 统一命名：
          对每个族 / 独立定义判定可改名性（§2.3）；可改名的从**单一全局生成器**
          取新名（保证跨 DEX、跨族全局唯一，且不与任何既有字符串/passive token 碰撞）；
          产出 MemberRenameByDef: (defKey) -> newName。
第三轮   各 DEX 应用：
          对每个 method_id / field_id 索引 i，若其解析到的定义可改名，
          则 MethodNameByID[i] = MemberRenameByDef[def]（字段同理）；
          连同 ClassMap 一起调用 Rebuild。
```

关键点：**决策与命名都必须在所有 DEX 汇总后做一次**，否则会重演
`NoSuchFieldError: No field TERMUX_HOME_DIR ...`（各 DEX 各自取名不一致）。

#### 2.2.4 重建层配合：按索引覆盖成员名

现有 `RebuildOptions.Rename`（值键）继续只用于**类描述符**（描述符唯一，无去重共享
问题）。成员名改用**索引键**的新选项（设计）：

```go
type RebuildOptions struct {
    // ... 现有字段 ...

    // MethodNameByID / FieldNameByID：旧 method_id / field_id 索引 -> 新名字。
    // 与 Rename 的区别：Rename 按字符串值生效（改一个字符串会波及所有引用它的条目），
    // 本表只改写指定索引那一条，旧字符串保留给其他引用。
    MethodNameByID map[uint32]string
    FieldNameByID  map[uint32]string
}
```

`buildPlan` 需要做三件事（概念性描述，落地时按现有代码风格实现）：

1. 构造 method/field entry 时，`name := values[ref.NameIdx]`；若索引命中覆盖表，
   `name = 覆盖值`。**去重键、排序键、`pl.methodIdx` 都使用覆盖后的 name**，
   否则会产生两条相同 (class,name,proto) 的条目或漏改引用。
2. 把全部覆盖新名加入 `extra` 字符串集合（已存在的字符串会自然复用到同一池项，
   无需去重代码）。
3. 不要尝试删除旧名字字符串。它可能同时被 const-string、注解、其他未改名引用使用，
   删了就是行为改变。旧名留在池里只是体积代价。

> 兼容性：新选项默认 nil 时行为与现状完全一致，现有测试（`shrink_test.go`、
> `rename_*_test.go`）不受影响；老的值键成员改名路径可作为「退化模式」保留，直到
> 新路径稳定。

### 2.3 可安全改名的判据（照着实现即可）

按优先级从外到内。**任一判据不满足 => 保留**（保留永远安全，改名才可能崩）。

#### A. 类级前置条件（先过关再看成员）

A1. 声明类不能命中现有 `keepReason`（native、入口类、注解类、反射类、passive 引用、
    Keep 规则、平台/库前缀、内部类强耦合……）。
A2. **Phase 1 硬性要求：只改「声明类本身也在 `classRename` 里」的成员。**
    被保留的类（含入口组件、native 类、反射类）其成员一律不动。这一条在早期阶段能
    一刀切掉 JNI/反射/组件回调的大部分风险。
A3. 不在本 DEX 定义的引用（`resolveMethod` 返回 INVISIBLE/NOT_FOUND）一律不改。
A4. `declaresNative(ci)` 为真的类，**其全部成员**都不改（JNI 可能通过
    `GetMethodID`/`GetFieldID` 按名字回调，DEX 里没有对应 `method_id`，扫不到）。

#### B. 覆写安全（唯一会导致运行时崩溃的判据）

B1. 构造族（§2.2.2）。
B2. 族可改名的**充分条件**（全部满足）：
   - 族中每个成员所在类的**传递继承闭包**（super + interfaces，直到
     `java/lang/Object`）**全部可见**（每跳都能在 `byDesc` 找到，或终点是 Object）；
   - 族中无 native 方法；
   - 族名不命中 `keepMethodNames` / 以 `<` 开头 / `-$$Lambda$`、`-$$Nest$` 等
     lambda/desugar 合成名；
   - 族名不命中反射 / passive 保留（§C）；
   - 族可整体改名（不存在「部分成员所在类被保留」）。
B3. 族**不可改名**的情形（保守兜底）：
   - 闭包里出现不可见节点（`hasInvisibleSuper` 的精细版）——无法证明没有覆写框架方法；
   - 实现了不可见接口（框架回调 `onViewAttachedToWindow` 这类）；
   - 接口方法名与某不可见接口中的方法可能重名（无法枚举不可见方法，所以只要
     闭包不可见就整族保留）。
B4. **非族成员的宽松处理**（本方案新增能力）：
   - `ACC_PRIVATE` 方法：不参与覆写，**只要满足 §C 的反射判据即可改名**，
     即使所在类的父类不可见。
     这直接救活「继承 `PathClassLoader` 的类里那些真正私有的辅助方法」。
   - `ACC_STATIC` 方法：不参与覆写，同上。
   - 字段：字段没有虚派发。字段引用的解析是「沿父链找最近声明」，按定义独立改名是
     安全的；同样只需满足 §C。
B5. `ACC_BRIDGE` / `ACC_SYNTHETIC` 桥方法：默认**保留**（编译器生成的桥接与
    lambda 目标名被别处按名字引用，收益低风险高）。
B6. 接口方法：若接口可见且在改名集，可与实现类一起成族改名；若接口不可见，整族保留。
B7. `ACC_FINAL` 不构成障碍（final 方法一样可改名，只要族一致）。
B8. **不得新建覆写**：全局新名互不相同（§2.2.3 的全局生成器），因此两个原本不同名的
    方法改名后不会撞成同名，不会凭空创造一条新的覆写链。这是用「全局唯一命名」换来的
    硬保证，必须保持。

#### C. 反射 / 字符串引用判据（名称级，全局）

C1. 该**原始名字符串**只要在**任一** DEX 的字符串池里被 `const-string` 引用
    （`StringUsage.Const`），该名字全局保留。
    理由：`Class.getDeclaredMethod("foo")` / `getField("foo")` / JNI `GetMethodID`
    用的是字符串；我们无法区分它是反射还是普通文案，只能保守。
    当前实现已有这条（`planMethods` 里的 `usage.Const[idx]` 检查），本方案必须保留，
    且升级为「所有 DEX 的并集」。
C2. 名字出现在注解（`Anno`）、静态值（`Anno` 同时覆盖 encoded_array）里 -> 全局保留。
C3. 名字作为 **passive 成员引用**出现在非 DEX 内容里 -> 全局保留。需要在
    `passiveClassRefs` 旁边新增 `passiveMemberRefs`：
    - **布局 XML 的 `android:onClick` / `android:onLongClick` 属性值就是方法名**，
      由框架反射调用，漏掉必崩（这是当前完全没覆盖的一类）；
    - Manifest 属性值、`res/**`（含 `res/raw` 等非 XML）、`assets/**`、
      `resources.arsc` 字符串池里出现的、与某个待改名成员名相同的 token；
    - `META-INF/services/` 只含类名，不需要处理成员。
    - 实现沿用 `classLikeTokens` 的扫描思路，但匹配「成员名」而不是「类名」。
C4. `debug_info` 里的字符串（参数名、局部变量名）不构成运行时风险，可忽略；
    若 A4 关闭也无所谓。
C5. 反射拼名字（`"ge"+"tFoo"`）无法穷尽——见 §5 残余风险。

#### D. 特殊语义

D1. **枚举**：类带 `ACC_ENUM`(0x4000) 或父类是 `Ljava/lang/Enum;` 时，
    - 静态字段是枚举常量，`name()` / `valueOf()` / switch map 都依赖字段名 -> **不改**；
    - 方法整体保守**不改**（枚举里常有机密方法、`values()` 等）。
D2. **Serializable**：实现 `java/io/Serializable` 的类，字段按名字序列化
    （`ObjectOutputStream` 默认行为），**字段不改**；`readObject`/`writeObject`/
    `readResolve`/`writeReplace` 已在 `keepMethodNames` 里，其余方法可改。
D3. **Parcelable**：`CREATOR` 已在 `keepFieldNames`；`writeToParcel`/
    `describeContents` 已在 `keepMethodNames`；其余可改。
D4. **注解类**（`ACC_ANNOTATION`）：注解元素名被反射读取，**全部成员不改**。
    （类本身已被保留，命中 A2 后自然不动。）
D5. 现有 `keepFieldNames`（`CREATOR`/`INSTANCE`/`serialVersionUID`/`Companion`/`TAG`）
    与 `keepMethodNames` 白名单继续生效，且**升级为名称级全局保留**。

#### E. Keep 规则

E1. 现有 `-keep-rules` 的 `类.成员` 通配（`isKeptMember`）继续生效；
    新决策对命中的定义整族保留。实现时注意 `Keep` 规则命中要参与族合并
    （族里任一成员被 Keep => 整族保留）。

### 2.4 改名后如何保持引用一致性

1. **只在目标引用上覆盖名字**：`MethodNameByID` / `FieldNameByID` 按旧索引键控，
   重建时只改这一条 entry 的 `name_idx` 指向的字符串值；同一旧字符串的其他引用完全
   不受影响。
2. **类描述符仍走 `ClassMap`（值键）**：类描述符唯一，且 `Plan()` 已处理
   「非本 DEX 定义但要跟着改的引用」与数组描述符派生，保持不变。
3. **跨 DEX 一致**：族是全局的、新名由单一生成器分配，所有 DEX 对同一族拿到同一个
   新名（`rename_crossdex_member_test.go` 的风格做成回归）。
4. **冲突检查**：
   - 类内方法 `(name, proto)` 唯一、字段 `(name, type)` 唯一（现有
     `checkConflicts` 升级为按覆盖后的名字检查）；
   - 因为新名全局唯一且不等于任何既有字符串，冲突在理论上不可能出现，但仍要在重建后
     复查（§4 的 R3/R4）。
5. **旧字符串保留**：新名用 `extra` 加入池；旧名不删。若新名恰好等于某个已有字符串，
   自然复用同一池项（无害）。
6. **与 A2/A3 的顺序**：A1 必须仍在 A2 之前（§3）。新增的成员名字符串只被
   method_ids/field_ids 引用，不会被 A2 的「仅 const-string 引用才加密」逻辑选中，
   但要在测试里显式断言 A2 不会改这些新名（R9）。

### 2.5 如何避免破坏覆写关系：可证明的不变量 + 兜底

**不变量（必须写进代码注释与测试）**

> 对任意方法引用 `R=(C,n,p)`：设改名前的虚方法族为 `F`，则改名后
> `R'=(rename(C), familyName(F), p)` 必须解析到与 `F` 对应的新族 `F'`；
> 且 `familyName` 在 `F` 的所有成员与所有指向 `F` 的引用上取同一值。

满足不变量需要：

1. **族内同名**（§2.2.2/§2.2.3）：实现为「先并查集，再按族赋名」，不是按定义赋名。
2. **不新建覆写**：全局新名唯一，且不等于任何未改名的成员名（生成器预占所有既有
   成员名字符串 + passive token）。因此 `F1` 的新名不可能和 `F2` 撞成同签名同名的
   关系。
3. **不可见闭包不动**：闭包不可见的族整族保留，不变量退化为恒等，自动成立。
4. **重写所有指向该族的引用**：包括子类静态类型写的引用（`B.m` 解析到 `A.m` 的情况），
   按解析出的**定义/族**而不是按静态类型决定新名。这是 `resolvesVisibly` 的升级：
   从「是否可见」升级为「解析到哪个族」。

**兜底策略（保守到极致也不会错）**

- 任何一条判据无法证明时，**整族保留**（不是部分保留）。保留是恒等变换，永远保持
  原有覆写关系。
- 「保留」具有传递性：只会让改名的族变少，不会让留存的族之间的关系改变。
- 重建后立刻做**结构自检**（§4 R6/R7）：在产物里重新解析，确认每个族的成员名字仍然
  相同、每条旧引用仍解析到对应族；一旦不符，**让 A1 返回错误而不是写出坏产物**
  （沿用 `ValidateDescriptors` 的「宁可失败也不产出非法 DEX」风格）。
- 最终兜底：真机复验（三个应用 + `testapp`）通过才算完成。

### 2.6 实施阶段与候选统计

- **Phase 0（统计）**：加候选计数与保留原因直方图，产出真实候选数，替换 §1.2 估计值。
  `A1.method_candidates_by_reason`、`A1.field_candidates_by_reason`。
- **Phase 1（最小子集）**：私有方法、私有字段、静态方法、静态字段（不含族改名）；
  见 §6。
- **Phase 2（族改名）**：继承闭包完全可见的实例方法族（public/protected/包内）。
- **Phase 3（放宽 + 特殊语义完善）**：passive 成员引用、枚举/Serializable 精确排除、
  Keep 规则族合并。

## 3. 与现有 Pass 的交互与执行顺序

**本方案不改变 A1 是第一个注册 Pass 的顺序**（`passes/passes.go` 第 30 行），
也不改变它相对于 A2/A3/A8/A9/A10/A12/A13 与 B1 的位置。理由：

1. **A1 必须在 A2/A3 之前**：A2 的 `planStringEncrypt` 按「仅被 const-string 引用」
   判定加密集合，必须在最终名字确定后运行；A3 改写方法体里的 `const-string`，同理。
   若 A2 先跑，它会看到旧名，改名后可能出现「密文与名字混用」的边界情况。
2. **A1 必须在注入类 Pass（A8/A13/B2/B3/C1/D1）之前**：这些 Pass 往壳包注入类/方法，
   名字由各自模块分配；A1 先跑完，注入器只需避免与已分配名冲突，逻辑最简单。
   我们的新成员名**只作用于原有类的 method_ids/field_ids**，注入类是新增 entry，
   天然不受影响。
3. **A1 必须在 B4（多 DEX 拆分）之前**：B4 把 DEX 切分。A1 需要在「所有 DEX 都完整」
   时才能看到全部定义、做全局族合并。当前顺序已经满足；**绝不能**把 B4 提前到 A1
   之前，否则跨 DEX 定义不可见，本方案的族合并与 `ClassMap` 都会失准。
4. **A1 在 B1/B8 之前**：B1 把明文 DEX 加密成载荷，之后 DEX 不再可解析。任何
   DEX 级改写都必须在 B1 前完成。
5. **A4（去调试信息）在 A1 之后**：无影响；我们的新名字会被写到 method_ids 的
   `name_idx`，与 debug_info 无关。注意新名不要写进 debug_info（我们不碰它）。
6. **A5/A11（资源混淆）独立于代码包名**：资源里按名字引用类的地方由
   `passiveClassRefs` 保类，这次只动成员名，无交互。新增的 `passiveMemberRefs` 只是
   读取资源，不修改资源。
7. **B4 的跨 DEX 包内访问**：拆分后同一运行时包名跨 DEX 仍算同包，包内访问不受影响
   （详见《方案-包合并.md》§3）；本方案不涉及包。

一句话：**顺序不变，且必须保持不变**；改动全部局限在 A1 内部（全局决策扩为三轮、
重建层加索引覆盖）。

## 4. 验收标准（可自动化断言 + 回归保护）

所有断言都做成 `go test`，并挂到真实 APK 的冒烟脚本上。

**通用（每个产物都要过）**

- R1 `dex.ValidateDescriptors(out) == nil`（每个 DEX）。
- R2 `dex.Verify(out) == nil`（校验和 / 签名自洽）。
- R3 全 APK 类描述符唯一：不存在两个 DEX 定义同名类（MultiDex 重复定义会崩）。
- R4 类内唯一：每个类的方法 `(name, proto)` 无重复、字段 `(name, type)` 无重复
  （改名后重新解析产物断言）。
- R5 跨 DEX 引用一致：对每个 DEX 的每个 method_id/field_id，按全局映射后，在某个
  DEX 的类定义里存在匹配的 `(类, 名字, 原型/类型)`；外部引用（框架/库）不受影响。
  参考 `rename_crossdex_test.go`、`rename_crossdex_member_test.go`。

**覆写关系未被破坏（本方案的核心断言）**

- R6 **保留原有覆写**：对原始 APK 中每一对可见的 `(A super/iface, B sub)` 且
  `B.m` 原本覆写 `A.m`（同名同原型、非 private/static）的组合，断言产物里
  `B` 与 `A` 的对应方法**名字 + 原型仍然相同**（要么都改一致，要么都没改）。
  实现：用 `ClassInfos()` 读原始与产物，建立「产物新描述符 -> 原始描述符」的反查，
  按类成员表逐对比较。
- R7 **未新建覆写**：对产物中任意可见父子/接口关系 `(A,B)`，若产物里 `B.m` 与
  `A.m` 同名同原型且非 private/static，但原始里它们并不同名 -> 失败。用来抓
  「全局命名碰撞导致凭空生成覆写」。
- R8 **族内同名**：对原始每个虚方法族，断言产物中所有成员的方法名相同。
- R9 **反射保护**：原始名字出现在 const-string / passive 成员引用里的成员，产物中
  该名字未被改动（`isAlwaysKeep` 的等价断言）。
- R10 **A2 不误伤新名**：启用 A2 后，产物里新增的成员名字符串仍以明文出现在
  method_ids 中（不被加密）。

**回归保护（已有测试必须原样通过）**

- R11 `rename_override_test.go`（不可见父类方法不改）、`rename_inherited_test.go`
  （继承框架父类的成员不改）、`rename_crossdex_test.go`、`rename_crossdex_member_test.go`
  （跨 DEX 一致）、`rename_defaultpkg_test.go`、`passes/shrink_test.go`
  （包压缩语义）、`internal/dex/rename_test.go` 全部不改动地通过。
  若因新能力导致某测试的「保守断言」不再成立（例如某成员现在能被改），必须
  新增对照组而不是删断言，保持「正对照 + 负对照」结构。
- R12 三个真实应用 + `testapp` 全选项复验：进程存活、主界面 resume、
  logcat 零 `AbstractMethodError` / `NoSuchMethodError` / `NoSuchFieldError` /
  `IllegalAccessError` / `VerifyError` / `UnsatisfiedLinkError`。

**新增建议测试文件（风格对齐现有）**

- `internal/dex/rename_family_test.go`：构造「A 定义 m，B 覆写 m，C 定义同名但无关」
  的三类 DEX，断言 A/B 同族同名、C 独立改名或保留。
- `internal/dex/rename_private_test.go`：继承不可见父类的类里，私有方法 / 静态方法
  被改名，公有实例方法保留。
- `internal/dex/rename_rebuild_byid_test.go`：同一个名字字符串被两个 method_id 共享，
  只覆盖其中一个索引，断言产物里另一个引用名字不变。
- `internal/passes/rename_passive_member_test.go`：布局 `android:onClick="onFoo"`
  时 `onFoo` 不被改名。

## 5. 风险与取舍（哪些做法会破坏产物，为什么不能做）

| 禁止的做法 | 后果 | 原因 |
|---|---|---|
| 通过**删除 / 替换旧名称字符串**来改名 | 所有共用该字符串的引用一起被改，框架/保留类崩 | 字符串池去重；`RebuildOptions.Rename` 是值键的 |
| 把成员名放进值键 `Rename` 表 | 同上 | §2.1 |
| 单独改「不可见父类实例方法」 | `AbstractMethodError` / `NoSuchMethodError` | 可能覆写框架接口；实测 Dhizuku `onViewAttachedToWindow` |
| 改「引用自不可见父类的成员」 | `NoSuchMethodError: loadClass` | 实测 Termux hiddenapibypass |
| 改 native 方法名 / native 类成员 | `UnsatisfiedLinkError` / JNI `GetMethodID` 失败 | JNI 符号按类名+方法名推导，且回调名不可见 |
| 改枚举常量字段 / 注解元素 | `valueOf`/`name()` 语义变化、注解读取失败 | 名字即语义 |
| 改 Serializable 类的字段 | 反序列化字段丢失 | 默认按字段名序列化 |
| 改命中 const-string 的名字 | 反射 `getDeclaredMethod` 找不到 | 无法区分反射与文案 |
| 改 lambda/`-$$Nest$` 合成方法 | 反序列化 lambda / nest 访问失败 | 编译器生成的名字被框架按名引用 |
| 按「静态类型」而不是「定义/族」决定新名 | 覆写派发断裂 | §2.5 |
| 局部（部分 DEX / 部分成员）改名一个族 | 跨 DEX 族不一致 | Termux 30 DEX 已踩过同名不一致的坑 |
| 改名后不做产物结构自检就写出 | 坏产物上线才发现 | 沿用「宁可失败不产坏 DEX」的既有原则 |

**残余风险（必须如实写进 README / 文档，无法自动消除）**

- 反射名字是运行时拼出来的（`"ge"+"tFoo"`），任何静态扫描都穷尽不了；
  只能靠 `-keep-rules` 让使用者兜底。
- 三方框架用注解 / 代码生成（Room、Hilt、Gson with `@SerializedName`）时，字段名可能
  被生成代码按名引用；现有 `@SerializedName` 的**值**不是字段名，但生成代码可能带
  字段名字符串 -> 若它出现在 const-string 里会被 §C1 保住；否则有风险。
- 体积：旧名全部保留，池会变大；实测当前 A1 已让产物增长，本方案会加剧。用
  「安全性 >> 体积」解释。
- 性能：全局定义图是 O(所有 method_ids + field_ids)（Termux 30 DEX 十万级），
  需要控制内存与耗时（预计 < 数秒）。

## 6. 最小可落地子集（第一个能独立验证、且不破坏三应用的切片）

**切片内容：只改「私有方法、私有字段、静态方法、静态字段」**

为什么选它：

- 这四类成员**根本不参与虚方法族**（private/static 不进入虚派发），因此完全不需要
  实现 §2.2.2 的族并查集，也不需要 §2.3 B 的覆写证明，风险面最小。
- 只需实现：§2.2.1 定义解析（判断引用解析到哪个定义，确认它是 private/static）、
  §2.2.3 的全局汇总与统一命名、§2.2.4 的索引键重建覆盖、§2.3 C 的反射/passive 保留、
  §2.3 A2/A4/D 的类级与特殊语义门禁。
- 严格保持「只增不改」：对每个 name 仍可继续用现有值键路径，索引覆盖只是**额外**
  增加可改的引用；绝不会比现在更激进地改到不该改的。

**实现要点（照抄）**

1. 重建层先加 `MethodNameByID`/`FieldNameByID` 与 `NewStrings` 联合使用，
   写一个合成 DEX 的单测证明「同名字符串的两条引用只改其中一条」。
2. `passes/rename.go` 里新增「成员覆盖」轮次：
   - 汇总每个 DEX 的 const-string 名字并集（已有 `MemberNameStrings`，扩成含 Const）。
   - 对 `ACC_PRIVATE|ACC_STATIC` 的方法定义、`ACC_PRIVATE` 或 `ACC_STATIC` 的字段定义，
     解析其全部引用，逐个建立旧索引 -> 新名覆盖。
   - native 类、枚举、注解、Serializable、被动引用、Keep 命中一律跳过。
3. 自检：跑 §4 的 R1~R10。

**预期提升（估计，Phase 0 后校正）**

| | 当前 | 切片后估计 |
|---|---|---|
| Dhizuku 字段 | 0 | 1k~4k |
| Dhizuku 方法 | 53 | 2k~4k |
| Termux 字段 | 0 | 1k~5k |
| Termux 方法 | 637 | 2k~4k |
| RustDesk 字段 | 0 | 0.3k~2k（R8 已混淆，名字短、撞车多） |
| RustDesk 方法 | 10 | 0.5k~1.5k |

**不破坏三应用的信心来源**：private/static 不参与覆写；反射 / JNI / 枚举 /
Serializable 全部走名称级保留；类级门禁沿用现有 `keepReason`；且必须通过真机复验
（R12）才算完成。若真机出现问题，回退开关应为「关闭成员覆盖，退回当前值键路径」。
