# 方案：资源内容加密

> 状态：设计稿（未实现）。
> 关联代码：`apkguard/internal/passes/resources.go`（A5/A11 资源改名）、
> `apkguard/internal/arsc/arsc.go`（resources.arsc 字符串池）、
> `apkguard/internal/pipeline/sink.go`（`storeResourceTable` 强制 STORED）、
> `apkguard/internal/passes/container.go`（B8 载荷容器化，assets 命名先例）、
> `apkguard/internal/dex/loader.go` / `internal/dex/shell.go`（壳字节码注入先例）。
> 设计依据：`APK加固功能设计文档.md` §2 A5/A11、§4 C2（对照）。

---

## 1. 目标与预期效果

### 1.1 防住什么

| 攻击手法 | 现状（无本方案） | 加密后 |
|---|---|---|
| `unzip app.apk assets/*` 直接拿到业务数据 | 有效 | 只能拿到高熵密文 |
| 提取 `assets/` 里的配置文件、证书、离线数据、词库、模型、脚本 | 有效 | 失效（密文） |
| 通过 `strings assets/xxx` 找密钥/URL/协议 | 有效 | 失效 |
| 用资源名定位敏感界面（`res/layout/pay_*.xml`） | A5/A11 已改名缓解 | **本方案不涉及**（见 §2.1 边界） |
| 静态提取 `res/raw/` 里的敏感数据 | 有效 | 见 §2.1：`res/raw` 是系统资源，最小方案**不加密** |

**边界要写清楚**：本方案**不是**「加密全部资源」。`resources.arsc` 与
`AndroidManifest.xml` 必须保持明文；`res/` 下由系统解析的资源也必须保持明文；
`res/raw` 因带资源 ID、由 `arsc` 定路径，默认也不加密。本方案的现实目标只有
**`assets/` 下由应用自己读取的文件**（以及可选的、经审计确认的所有读点都能
接管的 `res/raw`）。这与设计文档里「资源内容加密」的直觉预期有差距，
但这是平台约束决定的，见 §2.1 / §2.2。

### 1.2 效果量化

- 被加密的 `assets/` 条目：明文在产物中**全部消失**；新增等量密文条目
  （路径与原名不同，避免「按名读密文」）。
- 体积增量 ≈ 0（AES-SIV 无填充、密文与明文等长，只多 16 字节标签；若原以 Deflate 压缩存放，
  密文按 STORED 存，体积可能略增）。
- 运行时开销：每个被加密文件多一次「读 assets + AES 解密 + 落盘（或内存返回）」，
  典型 < 5 ms/文件；可在首次读取后缓存。
- 防住的攻击面：所有「静态解包 assets 后 grep/strings/读文件」的自动化与人工分析。

## 2. 技术方案

### 2.1 哪些能加密、哪些必须保持明文

**必须保持明文（硬约束，违反即装不上/起不来）**：

| 条目 | 为什么必须明文 |
|---|---|
| `resources.arsc` | ① 系统在安装/启动期直接解析它（资源 ID → 值的映射）；加密后 `Resources` 完全不可用。② Android 11+（targetSdk ≥ 30）要求它**未压缩（STORED）且 4 字节对齐**，否则安装直接失败（Failure [-124]）。`pipeline/sink.go` 的 `storeResourceTable` 与 `passes/resources.go` 的注释都钉死了这一点。③ A5/A11 也正是通过改写它的**全局字符串池**来改资源路径（`arsc.Table.ResPaths`/`Replace`），加密会彻底破坏这条链路。 |
| `AndroidManifest.xml` | 系统在任何应用代码运行**之前**就要读它（确定 Application 名、组件、权限、minSdk）；加密后无法安装/启动。B2 的 Application 替换也必须在明文 Manifest 上做。 |
| `res/` 下由系统解析的资源（drawable/layout/xml/mipmap/…） | 系统按资源 ID 经 `AssetManager` 从 APK 读取并解析；应用进程内无法拦截 `AssetManager` 的原生读取，进程外（如 launcher/system_server 读图标、通知）更无法拦截。 |
| `res/raw/`（默认） | 它在 `resources.arsc` 里有资源 ID，路径由 arsc 固定。即使加密，`openRawResource(R.raw.x)` 仍会按 arsc 里的原路径去读密文 → 返回密文；要让它返回明文，必须改写**所有**读取调用点或替换 `Resources`，见 §2.2。 |
| `lib/*.so` | 归 C2 管（见 `docs/方案-C2-SO加壳.md`），不属于资源内容加密。 |

**可以加密（本方案的对象）**：

| 条目 | 为什么可以 | 运行时怎么读 |
|---|---|---|
| `assets/**` | 对系统是**不透明字节流**，不在 `resources.arsc` 里，系统从不解析；应用通过 `AssetManager.open` / `Resources.getAssets()` 读 | 把解密后的同路径副本暴露给应用的 `AssetManager`（§2.3），或改写读点 |
| `res/raw/**`（可选，需审计） | 应用读它，但系统也认它；只有把**所有读点**接管才能安全加密 | 调用点改写（`openRawResource(id, value)` → 自定义解密） |
| 应用自定义的其它目录（如 `res/raw` 之外的 `assets` 子目录） | 同上 | 同 assets |

### 2.2 两条路线的对比与推荐

#### 路线 A：反射替换 `Resources` / `AssetManager`，让系统级资源读取也解密

**设想**：加密 `res/` 下的图片/XML，运行时用一个「解密代理」替换应用持有的
`Resources`/`AssetManager`，在读取时透明解密。

**逐条评估——结论：不可行，不推荐。**

1. **`AssetManager` 是 `final` 类**（`public final class AssetManager`），
   无法子类化去覆写 `open`/`openNonAssetFd` 等原生方法。
2. **`Resources` 替换是隐藏 API 操作**：需要通过反射改
   `Resources.mResourcesImpl`/`mAssets` 等私有字段，这些字段名跨版本变动，
   且 Android 9+ 的隐藏 API 限制会拦截非 SDK 访问——失败代价是应用直接崩。
   这与 B3 已经踩过并明确放弃的「反射改 `DexPathList` 内部字段」是同一类风险
   （见设计文档 §B3 与 `realdex/实测记录`）。
3. **系统会在应用进程之外读资源**：launcher 读应用图标、`system_server` 读
   通知/壁纸/快捷方式资源、`PackageManager` 读元数据。这些读取发生在系统进程，
   应用的任何 hook 都无效。加密这些资源 = 图标丢失、通知异常、被商店/系统判定
   非法。**这是路线 A 的根本死穴。**
4. **`resources.arsc` 无法加密**（§2.1），所以资源 ID → 路径的映射始终可读，
   攻击者仍能定位每个资源文件的位置；加密单个 `res/` 文件只是让内容不可读，
   而 `AndroidManifest.xml` 里还会残留 Activity 主题、图标等引用。

因此**路线 A 只能用于「应用自读的 assets/raw」，对系统级资源无能为力**，
而它为此付出的反射/隐藏 API 代价与崩溃风险，远高于下面路线 B 的做法。
**明确写出：路线 A 不做。**

#### 路线 B：只加密应用自己读的文件（推荐）

**做法**：只加密 `assets/`（可选 `res/raw/`），且加密后**从原路径移除**，
改放到一个应用代码不会主动读的密文路径；运行时由壳把解密后的**同路径副本**
暴露给应用的 `AssetManager`。

**为什么这是现实可行的最小方案**：

1. **系统只对 `res/` 与 `resources.arsc` 做资源解析**，`assets/` 对系统完全透明
   ——不解析、不索引、不跨进程读取。所以 `assets/` 的内容可以任意变形。
2. **应用读 assets 的入口是可接管的**：`AssetManager` 支持**追加资源路径**
   （`addAssetPath` / `Resources.addLoaders`），可以让我们把「解密后的镜像目录」
   追加进去。追加后 `AssetManager.open("原路径")` 会从这个镜像目录返回明文，
   而原 APK 里的明文已被移除，只剩无关的密文条目——**静态拿不到明文，运行时
   应用行为不变**。
3. **不需要替换 `Resources`/`AssetManager` 对象**，只需要「加一条搜索路径」，
   对应用透明，也不涉及系统跨进程读取。
4. **资源 ID 完全不变**：`assets/` 没有资源 ID；`resources.arsc` 一个字节不改，
   A5/A11 的「资源 ID 逐条不变」判据天然继续成立。

**代价与限制**：

- 只保护 `assets/`（及可选 `res/raw`），不保护系统解析的 `res/` 图片/XML。
  这是防护范围的缩小，必须如实告知使用方。
- 追加资源路径的 API 在低版本上是隐藏 API（`AssetManager.addAssetPath`），
  高版本有公开的 `Resources.addLoaders(ResourcesLoader)`（API 30+）。
  需要分版本处理（§2.3）。
- 若应用**枚举** `assets/`（`AssetManager.list()`）或按 APK 路径自己解 zip 读
  assets（如 Flutter 引擎、部分游戏引擎），镜像方案可能对不上；这类文件必须
  经审计排除。

### 2.3 运行时如何让应用读到解密后的资源

有三种可选机制，推荐「按 Android 版本择优 + 降级」：

| 机制 | API | 说明 | 推荐度 |
|---|---|---|---|
| `Resources.addLoaders(ResourcesLoader)` + 自定义 `AssetsProvider` | 30+ | **公开 API**。`AssetsProvider.openAsset(path)` 可按路径返回自定义字节流，我们在这里解密。不依赖隐藏 API，最稳。 | ★★★（新设备） |
| `AssetManager.addAssetPath("<私有镜像目录>")` | 全版本，但隐藏 | 把解密后的镜像目录当成一条 assets 搜索路径追加。**注意** `addAssetPath` 接受目录或 zip。Android 9+ 隐藏 API 限制可能拦截。 | ★★（老设备降级，需实测） |
| DEX 调用点改写 | 无（纯改写） | 把 `AssetManager.open(<字面量>)` / `openRawResource(R.raw.x)` 改成调用我们注入的 `decrypt(name)`。覆盖字面量调用点，漏掉动态/反射读点。 | ★（可选补强） |

**时序**：镜像必须在**任何应用代码读 assets 之前**准备好。最自然的时机是
B2 壳的 `attachBaseContext`（与 Loader 相同的时点），即：
「解密所有被加密 assets 到 `<dataDir>/app_ag/res/` 并构好镜像树 →
把镜像追加进 `AssetManager`/`Resources` → 再委托原 Application」。
由于 assets 可能被原 `Application.attachBaseContext`/`onCreate` 或任意 SDK 读取，
必须在委托原 Application **之前**完成追加。若文件很多/很大，可只解密「被读到时」
按需解密（`AssetsProvider` 天然适合按需）。

**镜像树的构造**：镜像目录下的相对路径必须与原名一致，例如原
`assets/config/settings.json` → 密文存 `assets/<容器>/<hash>.bin`，
运行时解密写到 `<dataDir>/app_ag/res/config/settings.json`，然后
`addAssetPath("<dataDir>/app_ag/res")`。这样 `open("config/settings.json")`
命中镜像。注意 `AssetManager` 的路径是**相对 assets/**，与
`loader.go` 的 `assetKey()` 去掉 `assets/` 前缀的约定一致。

**为什么不做成「原地加密 + 透明读取」**：`AssetManager` 的原生读取无法拦截
（final 类），只能靠「换一个能被搜到的明文副本」。所以「移除明文 + 追加镜像」
是唯一不碰系统资源解析的可行形态。

### 2.4 数据流

```
加固期（新增资源内容加密 Pass，LevelZip，注册在 A5/A11 之后、B4/B1 之前）：
  候选 = 审计选择出的 assets/ 条目
  for each e in 候选:
      data = e.Data()
      blob = pack.Encrypt(data, key, IVFromSeed(seed+"/res/"+e.Name))
      assetName = "assets/<容器>/" + hash(e.Name) + ".bin"   // 与原路径无关
      pipeline.Add(art, zipx.NewStored(assetName, blob))
      pipeline.Remove(art, e.Name)
      记录 ResItem{ MirrorPath = 原相对 assets 的路径, Asset = assetName, Size }
  把 ResItems + 解密镜像目录名 存入 Artifact.Shared（键如 "RES.items"）

运行期（壳在 attachBaseContext 中，委托原 Application 之前）：
  mirrorDir = base.getDir("ag/res", 0)          // 私有目录
  for each ResItem:
      blob = read assets[ResItem.Asset]
      data = decrypt(blob, key)                  // 复用 loaderDecryptCode / pack 语义
      writeFile(mirrorDir, ResItem.MirrorPath, data)
  am = base.getAssets()
  am.addAssetPath(mirrorDir.getAbsolutePath())   // 或 Resources.addLoaders(...)
  // 之后应用所有 AssetManager.open("原路径") 命中镜像，返回明文
```

**注意**：镜像目录里的文件是**明文**，落在应用私有目录。这带来一个取舍：
root/备份可能读到明文（与 B3 落地明文 DEX 是同一性质）。若不可接受，
可改成「镜像目录只放壳能读的加密文件 + `AssetsProvider` 按需内存解密」
（API 30+），但复杂度和版本门槛都更高。最小方案接受「私有目录明文」这一取舍，
并复用 B3 已有的「私有目录 + 只读」约定。

## 3. 与现有 Pass 的交互与执行顺序

### 3.1 注册位置

`internal/passes/passes.go` 的 `Registry()` 里，**资源内容加密 Pass 应注册在
A5/A11 之后、B4/B1 之前**（L1 区块尾部，例如 `resourceFlatten` 之后、
`splitDex` 之前）。

理由：

1. **必须在 A5/A11 之后**：A5/A11 会改写 `res/` 与 `resources.arsc`
   （`arsc.Table.Replace`），并同步改名 ZIP 条目；本 Pass 需要看到最终的资源
   布局。更重要的是，本 Pass **只处理 `assets/`**（或经审计的 `res/raw`），
   与 A5/A11 改写的 `res/` 路径集合互不重叠，放在其后可避免 A5/A11 的
   `used` 集合与新增密文条目互相干扰。
2. **必须在 B2/B3 之前（或至少让壳能拿到清单）**：运行时解密需要壳提供时机，
   壳由 B2 建、Loader 由 B3 注入。清单必须在此之前准备好。参照 C2 的方案：
   注册在 B1/B4 之前，把清单存入 `Artifact.Shared`，由 B2/B3 消费。
   - 若沿用「B2 在 `checks` 里登记、后续 Pass 注入类体」的现有模式
     （D1/C4/C5/C6 的做法），则本 Pass 可以排在 B2 之后，通过
     `injectShellClass` 把解密类注入壳 DEX。两条路都行，但都需要 B2 知道
     「存在资源解密入口」——即需要改 B2 的 `checks` 组装（新增分支）。
   - **推荐**：与 C2 一致，把「资源解密」也并入 B3 的 Loader 初始化流程
     （`Loader.a` 里先解密 SO、再解密资源并追加路径、最后构造 ClassLoader），
     这样只扩展 B3 一处，B2 不动。
3. **必须在 B1/B8 之前（或排除其载荷）**：B1/B8 会往 `assets/` 加密文载荷。
   若本 Pass 排在它们之后，必须把 B1/B8/C2 的载荷加入排除名单，否则会把
   已加密的载荷再加密一次（浪费且破坏）。排在它们之前则天然不需要排除。
   **推荐排在 B1/B8 之前**。
4. **必须在 A14 之前**：A14 统一全部条目的时间戳，新增的密文条目要一并被统一。
5. **必须在 A9/A10/A12/A13 之后或不受其影响**：这些 Pass 会往 ZIP 注入垃圾/
   伪条目。本 Pass 的候选来自**原始 `assets/` 条目**，不会选中它们；但若候选
   集合是「全部条目」，必须显式限定在 `assets/` 前缀内。注册在 A9/A10/A12/A13
   之前/之后均可，只要选择逻辑正确。
6. **与 E2/E1/E3 的关系**：E2/E1/E3 在 Sink 里，晚于所有 Pass，天然在之后；
   本 Pass 只在 APK 内移动字节，不影响签名/对齐的正确性（新增条目由
   `zipx.Write` 统一处理对齐）。E3 自检只校验 `resources.arsc`/DEX/Manifest，
   不受影响。
7. **与 E6 的关系**：E6 检查 DEX 版本、ABI 覆盖、关键条目。本 Pass 不改 DEX、
   不改 `lib/`，只动 assets，E6 不受影响。可在报告中新增一条
   「已加密资产数 / 跳过资产数」的统计。

### 3.2 与 A5/A11 的边界

- A5/A11：改 `res/` 路径名 + `resources.arsc` 字符串池；**不碰 assets**。
- 本方案：改 `assets/`（可选 `res/raw`）；**不碰 `res/` 路径名、不碰 arsc**。
- 两者正交。若同时启用，顺序为 A5/A11 → 本 Pass（保证 arsc 已定稿，本 Pass
  不会看到半改状态）。**资源 ID 逐条不变的判据由 A5/A11 负责，本方案不引入
  新的 arsc 改动，因此该判据继续成立。**

### 3.3 与 B1/B8/C2 的载荷命名空间隔离

B1/B8/C2 的载荷都在 `assets/` 下。建议：

- B1/B8：`assets/<word>_<hex>.bin` 或 `assets/<容器>/...`（现状）。
- C2：`assets/<容器>/lib/<abi>/...`（见 C2 方案）。
- 本方案：`assets/<容器>/res/<hash>.bin`。

各用独立子命名空间，避免互相误选。本 Pass 的候选选择应显式排除
「已由 B1/B8/C2 生成的条目」（按命名空间前缀），即使注册顺序保证了它们
尚不存在，也留作防御。

## 4. 验收标准（可自动化断言）

| # | 判据 | 断言方式 | 防住的回归 |
|---|---|---|---|
| 1 | `resources.arsc` 仍为**明文且 STORED**，能被 `aapt2` 正常解析 | 复用 A5/A11 的 aapt2 复核；`entry.IsStored()==true` | 误加密 arsc / 改成 DEFLATE 导致 Android 11+ 装不上 |
| 2 | 资源 ID **逐条不变** | `aapt2 dump resources` 对比加固前后 ID 与名称集合 | 本 Pass 误改 arsc |
| 3 | `AndroidManifest.xml` 仍为明文可解析 | `axml.Parse` 成功；B2/E6 正常 | 误加密 Manifest |
| 4 | 被加密的 assets 条目在产物中**不存在明文** | 对每个原路径断言 `pipeline.Find(orig)==nil`；且产物中不存在内容等于原明文的条目 | 「加密了但明文还在」；只改名不加密 |
| 5 | 新增密文条目数量 == 被加密资产数，且均非原路径 | 对比清单；断言每个密文条目不等于任一原 assets 路径 | 命名冲突/覆盖 |
| 6 | 密文可被 `pack.Decrypt` 还原为原字节 | 单测逐字节比对 | 密钥/IV/填充错误 |
| 7 | 设备上应用正常启动，且被加密的资产能被读到**明文** | 装机实测：三应用启动无 `FileNotFoundException`/`Resources$NotFoundException`；`-debug-shell` 或探针读回原资产并校验 | 镜像未追加、时序错、路径不匹配 |
| 8 | 未加密条目一字未动 | 对比加固前后未加密资产的字节 | 误伤 |
| 9 | 公开 API 路径可用的设备上用 `ResourcesLoader`，老设备降级到 `addAssetPath` 且不崩 | 分版本单测 + 设备实测 | 隐藏 API 被拦截导致崩溃 |
| 10 | 审计报告存在：列出每个资产的「读法判定」与「加密/跳过」 | 产物报告字段 | 盲目加密高危机型（Flutter assets 等） |

## 5. 风险与取舍

### 5.1 会破坏产物的做法（明确禁止）

1. **加密 `resources.arsc`**：系统无法解析资源；Android 11+ 还会因非 STORED
   拒绝安装。
2. **加密 `AndroidManifest.xml`**：无法安装/启动。
3. **加密系统解析的 `res/` 图片/XML**（路线 A）：图标丢失、通知异常、
   跨进程读取失败。
4. **把加密后的 assets 留在原路径**：应用读到的就是密文（`open` 成功但内容是
   垃圾），表现为「文件打不开/解析失败」而非缺文件，更难排查。必须
   **移除原路径 + 换密文路径 + 运行时追加镜像**。
5. **在委托原 Application 之后才追加镜像**：SDK/原 Application 在
   `attachBaseContext`/`onCreate` 早期就可能读 assets，时序晚一步就拿到
   `FileNotFoundException`。
6. **加密被 native 从 APK zip 直接读取的 assets**（Flutter 的
   `flutter_assets/**`、部分引擎）：这些读取不走 `AssetManager`，镜像追加无效。
   必须审计排除。
7. **加密被 `AssetManager.openFd` 使用的资源而不准备真实文件**：`openFd` 需要
   可 mmap 的文件描述符；镜像目录是真实文件目录，可以支持，但若是
   `ResourcesLoader`+`AssetsProvider`（字节流）则不提供 fd——这类文件要么走
   目录镜像，要么排除。
8. **加密后仍依赖 `AssetManager.list()` 的枚举结果**：原路径消失、镜像路径出现，
   枚举结果会变；依赖枚举的代码可能失败，需审计。
9. **旧设备上用被隐藏 API 拦截的 `addAssetPath` 且不降级**：直接崩。

### 5.2 取舍说明

- **为什么只做 assets、不做全部资源**：平台约束。系统只解析 `res/`+`arsc`，
  应用读 `assets` 的入口可接管；`res/` 的读取入口不可接管（final 类 + 跨进程）。
  这不是实现偷懒，而是「可行的最大集合」。防护范围缩小必须如实告知使用方。
- **为什么最小方案不加密 `res/raw`**：它是带 ID 的系统资源，路径由 arsc 固定，
  要安全加密必须改写**全部**读取调用点，工作量大、漏点风险高。列为可选后续。
- **为什么接受私有目录明文镜像**：与 B3 落地明文 DEX 是同一取舍——私有目录
  只有应用自己与 root 可读，且系统不解析；换取实现简单与全版本可用。
  若需更强（镜像也不落明文），改用 API 30+ 的 `AssetsProvider` 内存解密。
- **为什么不做透明 `Resources` 替换**：见 §2.2 路线 A，反射 + 隐藏 API +
  跨进程读取三座大山，投入产出比极差。

## 6. 最小可落地子集

**目标**：第一个能独立验证、且**保证不破坏** Termux / Dhizuku / RustDesk 的切片。

> 现实约束：这三个应用的 assets 里，RustDesk 的 `flutter_assets/**` 由 Flutter
> 引擎经 APK zip/native 读取，属「加密即坏」的高危资产；Termux/Dhizuku 的
> assets 组成也需先审计。因此「一上来就加密真实应用的 assets」不可能保证不破坏。

**切片 R1（推荐的第一步，零破坏风险）**：

1. 实现 `assets/` 加密的**完整机制**（Pass + 壳侧镜像追加 + 降级策略），
   但候选集合限定为**加固工具自己注入的一个自检资产**（例如
   `assets/<容器>/selftest.bin`，内容为随机标记 + 校验值）。
2. 严禁候选选择器命中任何应用原有资产（白名单/前缀强约束）。
3. **独立验证**：
   - 产物中 `selftest.bin` 的明文不存在，密文条目存在；
   - 设备上壳解密并将镜像追加成功后，用 `-debug-shell` 或探针从
     `AssetManager.open("<原相对路径>")` 读回**与注入内容逐字节相等**的明文；
   - 三应用装机启动正常（因为没动它们的资产，属纯回归验证）。
4. 这一步把「Pass + 运行时镜像 + 版本降级」整条链路验证到位，且**不可能**
   破坏三个应用——满足「独立验证 + 不破坏」的硬要求。
5. 单测：加密→解密往返、镜像路径映射、原路径被移除、arsc/Manifest 不变、
   资源 ID 不变（aapt2）。

**切片 R2（紧随其后，逐步放开真实资产）**：

1. 实现**资产读法审计**：扫描 DEX 中 `AssetManager.open`/`openFd`/
   `openNonAsset*` 的字面量调用点；识别框架特征（`flutter_assets`、
   `libapp.so`、`*.dex`/`*.jar`/`*.so`、`*.apk`、`*.obb` 等）；命中高危
   一律跳过。
2. 只加密「审计判定为 Java `AssetManager` 读取、且非枚举/非 fd 依赖」的资产。
3. 按应用逐个放开验证：
   - **Dhizuku**：资产少，先跑（no-op 或小集合）；
   - **Termux**：审计后放行安全资产，装机验证；
   - **RustDesk**：默认**跳过 `flutter_assets`**；只加密审计确认安全的少量资产，
     并做「加密后启动正常」回归。
4. 端到端：`scripts/e2e.sh` 加一组含资源加密的功能集 + 产物断言
   （原路径消失、密文存在、arsc 不变）。

**不包含**：路线 A（系统级资源代理）、`res/raw` 加密、`ResourcesLoader`+
字节流内存解密（先做目录镜像，API 30+ 的 provider 作为后续增强）。
