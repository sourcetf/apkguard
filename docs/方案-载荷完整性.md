# 方案：载荷完整性（B1 载荷的 MAC / AEAD）

> 状态：设计稿（不含代码改动）
> 相关代码：`apkguard/internal/pack/pack.go`、`apkguard/internal/passes/pack.go`（B1）、
> `apkguard/internal/passes/container.go`（B8）、`apkguard/internal/passes/shell.go`（B3）、
> `apkguard/internal/dex/loader.go`（壳侧解密 `c(blob,key)`）、`apkguard/internal/dex/sigcheck.go`（D1）、
> `apkguard/internal/native/derive.go`（C1）、`apkguard/internal/config/config.go`。

---

## 1. 目标与预期效果

### 1.1 现状与问题

`internal/pack/pack.go` 的 `Encrypt` 产出 **`IV(16B) ‖ AES-256-CBC(PKCS#7)`**，没有任何
MAC/AEAD。包注释明确写了取舍：

> 「完整性校验由外层 APK 签名（E1）保证，载荷本身不额外做 AEAD。」

这条取舍在 **E1 启用 v2/v3 时**基本成立：载荷是 APK 内的一个 `assets/*` 条目，改动它就会
破坏 v2/v3 签名，安装/校验阶段即失败。但它留下三类空档：

1. **CBC 可延展性（bit-flipping）**：CBC 只校验 PKCS#7 填充，而填充校验不是完整性校验。
   翻转密文第 *i* 块的某一位，会让明文第 *i+1* 块对应位发生可预测的翻转；只要最后一块的
   填充仍合法（攻击者可通过对齐/cut-and-paste 构造），解密就会「成功」并加载被改动过的
   DEX。这是当前唯一**不需要密钥、却能定向改写明文**的路径。
2. **载荷间可互换 / 块级剪切粘贴**：同一把密钥、同一套格式，攻击者可以把 A 载荷的密文块
   搬到 B 载荷（或把两份载荷整体对调），CBC 解密与填充校验都可能通过。
3. **E1 弱化或 D1 被绕过的场景**：只签 v1 时 `assets/` 不在保护范围（v1 只保护
   `META-INF/MANIFEST.MF` 列的条目，且历史上可被剥离）；启用 D1 时的校验是**纯检测逻辑**，
   可被 Hook `System.exit` / patch 检查分支绕过。此时没有第二道密码学防线。

另外 `-payload-mac` 这个 CLI 开关**已经存在**（`cmd/apkguard/main.go:130`，映射到
`config.Options.PayloadMAC`），但没有任何 Pass 读取它——也就是说当前启用它是**静默空操作**。
这与本项目「启用未实现项必须报错、不能静默什么都不做」的一贯原则相冲突，本方案同时修掉这一点。

### 1.2 本方案要防住的攻击（具体化）

| 攻击 | 是否由 MAC 防住 | 说明 |
|---|---|---|
| 重签名后篡改载荷（换签名证书 + 重打包） | ❌ 基本防不住（见 1.4） | C1+D1 已覆盖；MAC 的 key 若与加密 key 同源，攻击者拿到 key 即可重算 MAC |
| 中间人替换载荷（传输途中替换 assets） | ❌ 不适用 | 载荷在 APK 内，不单独走网络；若真是运行时下发，应另设 HTTPS+签名，不是本方案 |
| **密文单字节/单比特篡改（CBC 延展）** | ✅ **本方案主要目标** | 这是当前无 MAC 时的真实缺口 |
| **部分字节篡改、块级剪切粘贴、载荷互换** | ✅ | MAC 绑定载荷身份后，互换会失配 |
| 降级替换（换成同 key 的旧版载荷） | ⚠️ 仅当 MAC 输入绑定构建上下文时 | 若 key 与 MAC 输入跨版本不变，旧版本载荷 MAC 仍合法；见 2.6 |
| 非对抗性损坏（下载/落盘截断、位翻转） | ✅ | 从「解密后随机崩溃」变为「确定性、可定位的启动失败」 |
| 内存中已解密 DEX 被改写（root/Frida 落盘目录） | ❌ 不覆盖 | MAC 只覆盖密文入口；该场景属 D4/B5 范畴 |
| CBC 填充 oracle | ✅ 消除 | encrypt-then-MAC + **先验 MAC 再解密**，攻击者拿不到「填充错」这一区分信号 |

### 1.3 与 E1（签名）、D1（运行时签名校验）的分工与重叠

| 维度 | E1 v2/v3 签名 | D1 运行时校验 | 载荷 MAC（本方案） |
|---|---|---|---|
| 作用对象 | 整个 APK（含 assets 载荷） | 已安装 APK 的签名证书指纹 | 单个载荷密文的字节 |
| 时机 | 安装/校验 | 壳 `attachBaseContext`，**早于** Loader 解密 | Loader 解密前，逐载荷 |
| 密钥依赖 | 签名私钥（不在产物里） | 内置指纹（在壳 DEX 里） | 载荷派生的 MAC key |
| 抗 Hook/绕过 | 系统层，强 | 弱（Java 检测可被 hook） | 中（先于解密，且可下沉到 native） |
| 覆盖 CBC 延展 | ✅（前提 v2/v3 且未被绕） | ❌ | ✅ |
| 覆盖载荷互换 | ✅ | ❌ | ✅ |
| 覆盖降级替换 | ✅（v2/v3 覆盖整个 APK，换旧载荷即签名不符） | ❌ | ⚠️ 需绑定构建上下文 |

**重叠**：在「E1 v2/v3 已启用且未被绕过」的前提下，MAC 对 1.2 里的多数攻击与 E1 完全重叠。
**增量**：① 防住 CBC 延展（E1 只在签名被校验时防，MAC 在解密点防）；② 在 v1-only / D1 被
hook 时提供密码学第二防线；③ 消除填充 oracle 面；④ 把偶发损坏变成确定性失败。

### 1.4 诚实的增量价值判断

- **当 C1 + C6 + D1 + E1(v2/v3) 同时启用时，MAC 的增量价值较小**：C1 已把密钥与签名证书
  绑定（重签名 → 密钥不同 → 载荷解不开），C6 防止 native 被改，E1/D1 防止重打包。此配置下
  MAC 主要价值是 ①防 CBC 延展 ③消 oracle，而非防重打包。
- **当 C1 关闭时，MAC 也基本防不住「有 key 的攻击者」**：C1 关闭时 AES key 以常量内联在壳
  DEX 中（`loaderDecryptCode` 里逐字节构造）。攻击者 dump 出 key 后，可解出载荷、植入代码、
  用同一 key 重新加密并重算 MAC——**HMAC 用的是同一份密钥材料，MAC 对持有 key 者无效**。
- 因此 MAC 的正确定位是「**纵深防御 + 消除 CBC 结构性弱点**」，不是「防二次打包的主防线」。
  主防线仍是 E1(v2/v3) + D1 + C1/C6。**默认关闭、按需开启**是合理默认。
- **最该做 MAC 的场景**：只能出 v1 签名（老设备兼容）的产物、或威胁模型包含「攻击者能绕过
  Java 层 D1 但不能改 native」。此时把校验下沉到 native（见 2.7）价值最大。

## 2. 技术方案

### 2.1 算法选型：HMAC-SHA256（保留 CBC）vs 改用 AES-GCM

先复核 `pack.go` 给出的「选 CBC 不选 GCM」理由在今天的 minSdk 下是否仍成立：

- 历史理由：「`AES/GCM/NoPadding` 在 Android 早期版本存在兼容问题」。实际上
  `javax.crypto` 的 GCM 自 **API 19（Android 4.4）** 起由 Conscrypt/BouncyCastle 提供，
  API 21（5.0）已稳定。当前工具 E6 的 `injectedMinAPI = 1`，但真实样本 minSdk 普遍 ≥ 21。
  **所以「5.0+ 不兼容 GCM」的说法今天已不成立**。
- **但 GCM 有一个更致命的冲突：IV 复用。** 现在 IV 由 `IVFromSeed(seed+"/"+dexName)`
  **确定性派生**（为了产物可复现），同一 seed 下每次加固 IV 完全相同。GCM 在同一 key 下
  重复使用 IV 会灾难性地泄漏认证密钥（GHASH 密钥可被恢复），比 CBC 延展更糟。改用 GCM
  必须改成**每份载荷随机 IV 并把它存进载荷**，这会打破「可复现产物」的既有承诺（seed 固定
  也不再可复现），与项目多处刻意的确定性设计冲突。
- GCM 还会：改变磁盘格式（tag 12/16B）、抬高 `injectedMinAPI` 到 19、需要重写
  `loaderDecryptCode`（`GCMParameterSpec` + `"AES/GCM/NoPadding"`），并重新验证所有
  旧版兼容路径。收益是「一次到位拿到 AEAD」，但要动的东西多、回归面大。

**结论：采用 encrypt-then-MAC，保留 AES-256-CBC，MAC 用 HMAC-SHA256。**

- `javax.crypto.Mac` 的 `"HmacSHA256"` 自 **API 1** 起可用，不抬高 `injectedMinAPI`。
- 保留 `IVFromSeed` 的确定性（HMAC 对 IV 可预测不敏感，只要 IV 被 MAC 覆盖）。
- 不改动现有 CBC 加解密字节码，只在前面加一段校验。

（若将来目标明确为 minSdk ≥ 21 且愿意放弃产物可复现，可另立议题切 GCM；本方案不采用。）

### 2.2 MAC 放在哪：密文尾部，encrypt-then-MAC

**方案：把 32 字节 HMAC tag 追加到载荷末尾**，格式变为

```
Blob = IV(16B) ‖ Ciphertext(nB) ‖ Tag(32B)
```

理由：

- 载荷仍然是**一个 assets 条目**，`LoaderItem.Size` 继续等于 `len(Blob)`，B8 的容器改名
  只改条目名、不动字节，天然兼容。
- 相比「独立清单条目」：少一个条目、少一次 `AssetManager.open`、少一处需要被保护的元数据
  （独立清单本身也得被 MAC/签名保护，否则攻击者改成空清单即绕过）。
- 选择 **encrypt-then-MAC**（而非 MAC-then-encrypt）：可以先验 MAC 再解密，从而**不向攻击者
  暴露「填充是否合法」**，消除 CBC 填充 oracle。
- 恢复时：`tag = blob[len-32:]`，`body = blob[:len-32]`，`iv = body[:16]`，
  `ct = body[16:]`，对 `(name ‖ body)` 验 MAC 后再走现有 `c(body, key)`（`body` 仍是
  合法的 `IV‖ct`，`c` 无需改动）。

### 2.3 密钥来源与 key separation

**不使用加密 key 直接做 HMAC key**，而是从同一密钥材料做域分离派生：

```
macKey = SHA-256(key ‖ "apkguard/payload-mac")
```

- **C1 开启**：`key` 是运行时由 `Native.derive(Native.sig(ctx))` 得到的 32B，壳在
  Loader 里用 `MessageDigest("SHA-256")` 对 `key ‖ 常量域串` 现算 `macKey`。
  **不需要新增 JNI 符号、不需要重编 `.so`**，与 `sigDigestCode` 复用同一套字节码模式。
- **C1 关闭**：`key` 是内联常量，`macKey` 同样可在 Loader 里现算（与 C1 走完全相同的
  代码路径），无需内联第二份密钥。
- 派生的域串是 `const-string`，可被静态读到，但这只说明「MAC key 由 key 域分离而来」，
  不泄漏 key；在 C1 下 key 本身不在 DEX 里。

> 说明：域分离是密码学最佳实践；对本威胁模型（攻击者若无 key，HMAC 不可伪造）不是决定性
> 的，但它让「MAC key 与加密 key 无关」，避免将来把 AES key 换用途时牵连。

### 2.4 壳侧如何校验：`javax.crypto.Mac` 的字节码生成

在 `internal/dex/loader.go` 的 Loader 里新增一个私有静态方法（名字沿用现有单字母风格，如 `v`），
签名 `v([B[B[BLjava/lang/String;)Z`（blob、key、name），并在 `a(...)` 的每份载荷循环里
**先 `v`、通过后再 `c`**。

Java 等价：

```java
static boolean v(byte[] blob, byte[] key, byte[] name) {
    if (blob.length < 16 + 32) return false;
    byte[] macKey = SHA256(key, "apkguard/payload-mac"); // MessageDigest
    Mac m = Mac.getInstance("HmacSHA256");
    m.init(new SecretKeySpec(macKey, "HmacSHA256"));
    m.update(name);
    m.update(blob, 0, blob.length - 32);
    byte[] got = m.doFinal();
    byte[] want = new byte[32];
    System.arraycopy(blob, blob.length - 32, want, 0, 32);
    int diff = 0;
    for (int i = 0; i < 32; i++) diff |= (got[i] ^ want[i]);  // 常量时间
    return diff == 0;
}
```

字节码要点：

- 新增描述符常量：`descMac = "Ljavax/crypto/Mac;"`；`SecretKeySpec`、`MessageDigest` 已有。
- 需要的方法引用：`Mac.getInstance(String)Mac`、`Mac.init(Ljava/security/Key;)V`、
  `Mac.update([B)V`、`Mac.update([BII)V`、`Mac.doFinal()[B`、
  `MessageDigest.getInstance(String)`、`MessageDigest.update([B)`、`MessageDigest.digest()[B`、
  `System.arraycopy`（已有）。
- 与 `loaderDecryptCode` 一样，接口/抽象类形参必须按 `Ljava/security/Key;` 书写，
  否则会被 ART 校验器拒绝。
- 逐个载荷把 `Name`（原始 DEX 名，如 `classes.dex`）以 `ConstString` 内联进字节码（B3 生成时
  已能拿到；`pack.Payload.Name` 在 B8 改名时**不变**，见 2.7）。
- 寄存器数会超出现有 `c` 的 8 个（预计 12~14），需相应上调 `CodeBlob.Registers`，并让
  `dex.Verify` / 解释器测试覆盖。
- `outs` 必须 ≥ 任一 invoke 的参数字数（`arraycopy` 5 字、`Mac.update([BII)` 4 字）。

**可选强化（阶段二）**：把 `v` 下沉到 native：新增 JNI `verify([B[BLjava/lang/String;)Z`，
key 从 native 种子+sig 内部派生、tag 比对在 native 完成。优点是 macKey/比对逻辑不在 Java 层、
可抗 Java Hook；代价是要改 `apkguard.c` 并重编 3 个 ABI 的 `.so`（`build_native.py`），
且依赖 C1。建议作为 C1 用户的增强，不替代阶段一的 Java 实现。

### 2.5 失败处置：直接崩溃 vs 静默假路径

两种处置的取舍：

**（A）硬失败：调用与 D1 相同的终止路径（`System.exit(1)` / `Process.killProcess`）**

- 优点：语义清晰；与 `sigFailCode`（`sigcheck.go` 的 `f()`）行为一致，壳里已有失败通道；
  注入字节码无异常表，显式退出比抛异常更好定位；不给「catch 后继续」留口子。
- 缺点：崩溃/退出是可观察的——攻击者改动一字节后能观察到「启动失败」，构成一个**存在性
  oracle**（知道「这里有校验」）。但注意：即便知道存在校验，没有 key 也无法伪造 MAC，
  这个 oracle 不能帮他改出可通过校验的载荷。

**（B）静默假路径：失败时不退出，改为走一段「看似正常」的路径**

- 例：把解密结果替换成一段内置的垃圾 DEX、或返回原类名以触发后续的「资源不存在」，
  让失败在很久以后以模糊方式暴露。
- 优点：干扰定位；不给「这里就是校验点」的直接信号。
- 缺点（更重要）：
  1. **复杂度与误伤**：注入字节码没有异常表，构造「假路径」本身要额外的类/数据；一旦假路径
     与被保护逻辑耦合，合法环境下的偶发失败会变成难以复现的诡异崩溃，伤害真实用户。
  2. **可能帮到攻击者**：若假路径让应用「继续跑」，攻击者获得一个可观察的、以不同方式运行的
     环境，反而方便差分分析。
  3. **边际收益低**：MAC 的不可伪造性不依赖「隐藏校验点」。攻击者知道校验存在也改不出合法
     载荷。

**结论：默认采用（A）硬失败。** 但必须附加「不可作为 oracle」的约束（见 2.6）。静默假路径
（B）不实现；若未来确要反定位，应做成「与 D1 共用同一个终止函数、不打印任何专属日志」，
而不是「继续运行」。

### 2.6 校验失败行为必须不能成为 oracle（硬约束）

1. **常量时间比较**：MAC 比对用「逐字节 XOR 累加、最后判 0」的循环，不能一旦不等就提前返回
   （避免逐字节定时侧信道泄漏 tag）。
2. **先验 MAC 再解密**：绝不允许「解密后再比对明文」，否则重新引入填充 oracle。
3. **失败的日志/Toast 与 D1 完全一致**：不出现 `MAC`、`HMAC`、`payload` 等专属字样；
   `-debug-shell` 排障版也不得为 MAC 失败加专属提示（否则 `logcat` 成为免费 oracle）。
4. **失败路径不依赖密钥内容做分支**：分支只依赖公开信息（长度、固定 tag 长度）。
5. **长度处理公开且一致**：`blob.length < 48` 直接按失败处理，不做差异化行为。
6. **不在失败前解密**：确保「MAC 错」与「key 错」在外部观察上不可区分（都走同一条终止路径）。

> 注意：本方案里 MAC 校验发生在 D1 **之后**（D1 在壳的 checks 阶段，见第 3 节），所以重签名
> 产物通常先被 D1 拦下、根本走不到 MAC。这避免了「先观察 MAC 行为再推导 key」的路径。

### 2.7 新字段怎么加：`sharedKeyPayloads` 的传递链

现有链路（`passes/pack.go`）：

```go
type shellPayloads struct {
    Key     [pack.KeySize]byte
    Items   []pack.Payload
    Removed []string
}
// B1: art.Put(sharedKeyPayloads, &shellPayloads{...})
// B8: sp := payloadsOf(art); 改 sp.Items[i].Asset; art.Put(sharedKeyPayloads, sp)
// B3: payloads := payloadsOf(art); 用 len(p.Blob) 填 LoaderItem.Size
```

改动（设计，不落代码）：

1. `shellPayloads` 增加 `MAC bool`（本批次是否带 tag）。
2. `pack.Payload` 的 `Blob` 在启用 MAC 时**含尾部 tag**，`Plain` 仍为明文长度；
   可加 `Payload.Tagged bool` 便于报告与断言（不必再存一份 tag）。
3. `pack.Make` 增加一个 MAC 参数/选项：对每份载荷按 `(Name ‖ body)` 计算 tag 并追加；
   同时新增参考实现 `pack.DecryptMAC(blob, key, name)` 供测试与跨语言对拍。
4. `LoaderSpec` 增加 `MAC bool`；`LoaderItem` 增加 `Name string`（MAC 输入需要原始 DEX 名）。
5. `B3` 在构造 `items` 时填 `Name: p.Name`、`Size: len(p.Blob)`（自动含 tag 长度），
   并设 `ls.MAC = payloads.MAC`。

**关键顺序约束**：B1 在 B8 之前执行，B8 会改 `Payload.Asset`。因此 MAC 输入**必须用
`Payload.Name`（原始 DEX 名，B8 不改）**，不能用 `Asset`。否则容器化后壳算出的 MAC 与
打包时不一致，合法产物会启动失败。

**长度变化**：每份载荷 +32 字节；总量 `TotalBlob` 增加 `32 * len(Items)`。这一点要写进验收
断言（见第 4 节），可自动发现「忘了追加 tag」「追加两次」等实现错误。

## 3. 与现有 Pass 的交互与执行顺序

### 3.1 Pass 注册位置

本功能不是新的顶层功能项，而是 **B1 的子开关**（与现有 `config.Options.PayloadMAC` 对应）。
不新增 Pass，只在现有 Pass 内按 `opts.PayloadMAC` 分叉，理由：

- 加密与 MAC 必须原子完成（同一份 `Pack.Make` 的产物、同一份密钥），拆成两个 Pass 会产生
  「A 做完 B 没做」的不一致窗口与产物状态。
- 现有 `config.Options` 已有字段、CLI 已有开关，接线成本最低。

### 3.2 与 B1/B2/B3/B4/B8 的顺序

- **B4（拆 DEX）在 B1 之前**（不变）：拆分先把业务 DEX 分片，MAC 对「每一份分片」各自生效。
- **B1（加密+MAC）**：`payloadKey` 不变；新增 `macKey = SHA-256(key ‖ 域串)` **仅用于 Go 侧
  计算校验参考**；真正运行时 macKey 由壳现算（2.3）。B1 填充 `shellPayloads.MAC` 与带 tag 的 Blob。
- **B8（容器化）在 B1 之后、B3 之前**（不变）：只改条目名，`Name` 与 `Blob` 不动，MAC 不受影响。
- **B2（壳 Application）**：不变；其调用的检测顺序（D1 等）在 Loader 之前。
- **B3（Loader 注入）在 B8 之后**（不变）：读取 `shellPayloads`，据 `MAC` 生成 `v` 方法并
  在每个分片前插入校验；`LoaderItem.Name` 来自 `p.Name`。
- **B2 壳的 checks 在 Loader 之前**：因此 **D1 先于 MAC 校验**。这是刻意的——重签名产物
  应在 D1 处就被终止，而非走到 MAC 才暴露差异；也避免 MAC 成为重签名的「探针」。

### 3.3 与 C1、E1 的顺序/依赖

- **C1**：C1 的 `Run` 在 B2 之后注入桥接类，`payloadKey` 由 B1 自行复算（注释已说明两者
  不依赖执行顺序）。MAC key 的运行时派生发生在 Loader 内、依赖 `key` 的来源（native 或
  内联），所以 **MAC 对 C1 无顺序依赖**；两者组合时，key 与 macKey 都只在运行时存在。
- **E1**：签名在流水线 `Sink` 收尾阶段，覆盖带 tag 的载荷；MAC 不改变 E1 流程。
- **crypto 参数一致性**：`loader.go` 的 `keyLen/ivLen/cipherAlg` 常量与 `pack.go` 必须保持
  一致；新增 `tagLen = 32`、`macAlg = "HmacSHA256"`、`macDomain = "apkguard/payload-mac"`
  必须两处对拍（建议加一条与现有载荷常量对拍同风格的守卫测试）。

## 4. 验收标准（可自动化断言）

| # | 判据 | 防住的回归 |
|---|---|---|
| 1 | 篡改密文任意一个字节（非 tag 区）后，`pack.DecryptMAC` 返回错误；设备上进程**不存活**（与 D1 失败同样表现为启动即终止） | 「MAC 没被真正校验」或「校验被优化掉」 |
| 2 | 篡改 tag 任意一字节 → 同上失败 | tag 未被比对（比如只算不比较） |
| 3 | 篡改 IV 任意一字节 → 失败（IV 被 MAC 覆盖） | IV 未纳入 MAC 输入 |
| 4 | 用正确 key、但错误 macKey / 错误 name 解密 → 失败 | MAC 未绑定身份/密钥，载荷可互换 |
| 5 | 对调两份载荷的 Blob → 各自失败（name 绑定） | 块级剪切粘贴 / 载荷互换 |
| 6 | 合法产物正常启动：`testapp` 11 产物 + 三个真实应用（Termux/Dhizuku/RustDesk）全选项回归通过 | 「校验过严 / Loader 字节码写坏导致合法包也起不来」 |
| 7 | 启用 MAC 后 `TotalBlob` 恰增加 `32 × len(Items)`；每份 `len(Blob) % 16 == 0` 且 ≥ 48 | 「忘了追加 tag / 追加两次 / 破坏了 CBC 分块对齐」 |
| 8 | `go test ./...` 全绿；`dex.Verify` 对含 `v` 方法的壳 DEX 通过；解释器执行 `v` 的判定与 Go 参考实现逐例一致 | 字节码生成错误（寄存器/outs/描述符）在真机才暴露 |
| 9 | `-payload-mac` 不再是空操作：启用且未满足前置（如需 C1 的可选强化）时必须报错而非静默 | 回归到「启用未实现项静默无效果」 |
| 10 | 产物中不出现专属失败日志：对 MAC 失败与 D1 失败抓 `logcat`，两条路径可见信息一致 | oracle 回归 |
| 11 | E6 `injectedMinAPI` 保持 1（`Mac`/`MessageDigest` 均为 API 1） | 误抬高最低 API 导致低版本装不上 |

补充：判据 1~5 可在 Go 单测里用 `pack.DecryptMAC`（纯函数）验证，**不需要真机**——这保证
CI 上就能钉住密码学语义；判据 6 仍需真机（现有 `scripts/device-test.sh`）。

## 5. 风险与取舍

**明确不能做 / 会破坏产物的做法：**

1. **不能把 MAC 放在独立清单条目里却只保护载荷**：清单本身必须也被保护（签名或 MAC），
   否则攻击者删空清单即关闭校验。若做独立清单，必须同时把它纳入 E1 覆盖并校验其存在性。
2. **不能在 `Payload.Asset` 上绑定 MAC**：B8 会改名（B1 早于 B8 执行），绑定 Asset 会让
   启用 B8 的合法产物启动失败。必须绑定 `Payload.Name`。
3. **不能对「解密后的明文」做 MAC 比对**：会重新引入填充 oracle，且失去 encrypt-then-MAC
   的先验优势。
4. **不能用非常量时间的比较**：逐字节提前返回会泄漏 tag 前缀的定时信息。
5. **不能在 MAC 输入里引入运行时会变的量（时间戳、build id）而不把它传给壳**：壳无法复算，
   合法产物必失败。
6. **不能默认开启**：在 C1+C6+D1+E1(v2/v3) 全开时增量价值小（1.4），默认开启只会增加
   Loader 复杂度与失败面。保持 `PayloadMAC` 默认 false。
7. **不能只改 Go 侧而不同步壳侧格式常量**：`pack.go` 与 `loader.go` 的算法/长度常量必须
   一致，否则密文与校验对不上。需要新增对拍守卫。

**其他风险：**

- 确定性 IV + 同 key 跨构建 → **降级替换（旧版载荷）不在覆盖范围**，除非把「构建上下文/
  版本号」纳入 MAC 输入并同样传给壳。本方案 v1 不做（会引入运行时需知版本的问题）；
  若需覆盖，建议在 MAC 输入加入 `expectedSigDigest`（D1 已有该值，但需在 Loader 可访问）。
- Java 层 macKey 可被 Hook 读取 → 校验可被 patch。C1 用户建议用 native 强化（2.4）。
- `LoaderItem.Name` 内联的 DEX 名是 `const-string`，会暴露原始 DEX 命名；这对 B1 已经暴露
  的信息量很小（载荷名本就由 DEX 名派生）。
- 每个载荷多 32B 与一次 HMAC，启动开销可忽略（RustDesk 16 分片约 512B 额外数据）。

## 6. 最小可落地子集

**切片目标**：用最小改动、独立可验证，且**不破坏现有三个真实应用**。

1. **只做非 C1 路径的 Java `Mac` 校验**（阶段一）：
   - `pack`：新增 tag 追加与 `DecryptMAC` 参考实现（纯函数，可单测）。
   - B1：`opts.PayloadMAC` 时追加 tag、填 `shellPayloads.MAC`。
   - B3/Loader：新增 `v(blob,key,name)` 与失败终止；每份载荷先验后解。
   - 不新增 JNI、不动 `.so`、不改 GCM、不改 IV 派生。
2. **默认关闭**；先用 `testapp`（单 DEX）验证：合法启动 + 篡改任一字节失败 + 长度断言。
3. **跑通后**再用一个真实应用（建议 Dhizuku，1 DEX、无原生库，回归面最小）做全选项回归；
   最后再跑 Termux/RustDesk。
4. **同时修掉空操作**：给 `PayloadMAC` 加依赖/前置校验，避免「启用却无效果」。
5. **阶段二（可选）**：C1 用户加 native `verify`，需重编 `.so`，单独排期。

此切片不触碰 A5/A11/资源、不触碰签名，风险集中在 Loader 字节码一处，符合「先在最小样本
验证、再上真实应用」的既有做法。

## 7. 工作量估计

> 依据：Loader 的 asm 字节码是本项目最易错、最耗时的一环（历史缺陷多在此），
> 但本方案的密码学部分是纯 Go、可快速单测。以熟悉本项目 asm 的开发者计。

| 工作项 | 人日 | 依据 |
|---|---|---|
| `pack`：tag 追加、`DecryptMAC`、常量对拍守卫、单测（篡改/互换/长度） | 0.5 | 纯 Go，模式成熟 |
| `shellPayloads`/`Payload`/`LoaderSpec`/`LoaderItem` 字段接线；B1/B3 改动 | 1.0 | 跨 4 个文件，但改动机械 |
| Loader `v` 字节码：`Mac`+`MessageDigest`+`arraycopy`+常量时间比较+寄存器/outs | 2.5 | 参照 `loaderDecryptCode`/`sigDigestCode`，但引用更多、需反复 `dex.Verify` |
| 测试：解释器对拍、壳产物结构断言、E6/minAPI 不回归 | 1.0 | 现有测试框架可直接扩展 |
| 真机回归（testapp → Dhizuku → Termux/RustDesk 全选项） | 1.5 | 依赖模拟器与现有 `device-test.sh` |
| 修掉 `-payload-mac` 空操作 + 文档/报告文案 | 0.5 | 小改动 |
| **阶段一合计** | **约 7 人日** | |
| 阶段二（native `verify` + 改 C + 重编 3 ABI + 回归） | +3 人日 | 需 NDK、`.agexpect`/16KB 对齐校验流程 |
| 阶段三（若确定切 GCM 并接受随机 IV） | +4~6 人日 | 影响格式/可复现性/旧版验证，不建议本方案内做 |

**不确定性最大的地方**：Loader 中 `Mac`/`MessageDigest` 的 asm 生成与常量时间比较循环
（判据 8）。建议先用一条「编译期把 Java 等价类编译成 DEX、与本工具生成的字节码逐指令对拍」
的方式预演，或在解释器里先跑通 `v` 再进 Loader 集成。
