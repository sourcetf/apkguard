# 样本逆向：加固手法清单（逐项附证据 + 我们的落地状态）

> 对象：仓库根目录的 `sample.apk`（15,100,869 字节，2418 个条目，构建时间 2026-09-19 22:01）。
> 分析方式：5 路并行子分析（外壳/嵌套载荷、resources.arsc、DEX、Manifest+ZIP、边角全量扫描）+ 模拟器装机实测，
> 全部结论都有字节级证据（自写 Python/Go 解析器、aapt2 回读、`adb` 实测）。
> 本文档记录**已被证据证实**的手法，以及**我们（apkguard）是否已对齐**；未证实的放在末尾「存疑」区。

---

## 0. 总体结构：宿主 + 外挂插件 APK（最重要的一条）

样本**不是**「把原应用的 DEX 加密」那种加壳，而是**两层独立的应用**：

```
[宿主 APK]  包名 nu.pyokn.yyqfzjtrpk.scz（15 MB，即 sample.apk 本身）
   ├ 作用：一个「强制更新」外壳。装机后显示 New Version Available / Update Now
   ├ 真身：WebView 页面 + 插件装载器；本身几乎没有业务功能
   └ assets/nupyoknyyqfzjtrpkscz.zip
        ├ nupyoknyyqfzjtrpkscz.dat   14,398,474 B，**单字节 XOR 0x5A**
        └ nupyoknyyqfzjtrpkscz.json  {"packageName":"dummy.installed.check",
                                      "appName":"河马短剧","apkFileName":"…dat"}
                                      ↓ XOR 0x5A
                            【完整的真 APK】3029 条目 / 9 个 DEX / arsc / 894 个 res
                                      ↓ 运行时点「Update Now」
        /sdcard/Android/data/<宿主包名>/files/plugins/nupyoknyyqfzjtrpkscz.apk
```

**模拟器实测证据**（Android 16 / API 36，`scripts/wsl-sample-*.sh`）：

1. 样本能正常安装、启动，前台 Activity 是 `EntryAlias → PortalActivity`，无崩溃。
2. 点一下「Update Now」，宿主在 `getExternalFilesDir()/plugins/` 下**落地了一个 14,398,474 字节的 APK**（连同一个 118 字节的 json）。
3. 把落地文件拉回来与解密出的内层 APK 比对：**sha256 完全一致**（`090fb519fb5a75a1…c4082`）。
4. 宿主 DEX 里的能力字符串与之吻合：`getExternalFilesDir`、`AssetManager`、`getDeclaredMethod`、
   `setAccessible`、`ZipInputStream`、`FileProvider`、`application/vnd.android.package-archive`、`VJ5`、`AES`。
   `SoftUtil.unpack` 的反汇编里能看到 `xor-int/lit8 v8, v8, #90`（90 = 0x5A）——**解密键与实现一致**。
   两个 shell DEX 的 method_ids 里**没有任何 `dalvik/system/*` 引用**（无 DexClassLoader）→ 是「双 APK 投放器」，
   不是替换 ClassLoader 的壳。

**我们的差异（有意保留的架构差异）**：我们的 B1/B2/B3 是「进程内解密 DEX + Application 替换 + ClassLoader 接管」，
真应用的 Manifest、资源、代码仍在已安装的 APK 里。样本把整个真 APK 搬到壳外，代价是宿主必须自带插件框架
（资源注入 + 组件代理），收益是静态分析面被清空。**这不是能力缺口，是产品定位差异**（我们加固「已有应用本身」，
不做双应用投放）；我们的同类收益由 B8（载荷容器化）+ A17（嵌套假 APK 诱饵）部分覆盖，且我们的载荷加密强度远高于样本。

## 1. Manifest：369 MB，真实内容只有 9 KB

`AndroidManifest.xml` 解压后 **369,623,060 字节**，Deflate 后仅 367,318（压缩比 0.001）。逐 chunk 走完：

| 偏移 | type | headerSize | size | 内容 |
|---|---|---|---|---|
| 0 | `0x0003` RES_XML | 8 | 369,623,060 | 顶层，size = 整个文件 |
| 8 | `0xB4A7`（未知） | 8 | 1,572,872 | 假 chunk #1，载荷 1,572,864 字节**全 0** |
| 1,572,880 | `0x0001` 字符串池 | 28 | **315,611,976** | **合法字符串池**：168 条串、UTF-16、`stringsStart=700`；**第 167 条是一条 157,800,394 个 'K' 的合法长字符串**（4 字节长串前缀 `67 89 CA D7`），数据 `4B 00`×157,800,394 顶到池声明末尾 |
| 317,184,856 | `0x9D1E`（未知，**与 #1 不同**） | 8 | 52,428,800 | 假 chunk #2，载荷 52,428,792 字节全 0 |
| 369,613,656 | `0x0180` 资源映射 | 8 | 136 | 真实内容开始 |
| 369,613,792 | `0x0100/0x0102…` | — | — | 真节点（178 个子 chunk，9,404 字节）到 EOF |

**关键真相（曾被我误判）**：369 MB 里 **85.4% 不是零**，而是**藏在合法字符串池内部的一条巨串**；
零只占 14.6%（两段未知 chunk）。按 chunk 遍历的解析器（AOSP `ResXMLTree` / aapt2 / androguard）都能正常读到真
Manifest —— 未知类型走 `default` 跳过，字符串池是合法的，只是多了一条没人引用的巨串。

真实 Manifest 的语义（aapt2 一致）：`package="nu.pyokn.yyqfzjtrpk.scz"`（**由构建 token 派生的随机包名**）、
`application=…Cpjamimvxhllg`（随机类名）、launcher 是 **`activity-alias`**（`EntryAlias`→`PortalActivity`）、
minSdk 24 / targetSdk 36、权限含 `REQUEST_INSTALL_PACKAGES`/`QUERY_ALL_PACKAGES`、
服务 `GuardService` 继承 `android.net.VpnService`（含 `foregroundServiceType=0x40000000` + specialUse property）、
**18 个诱饵组件**放在主题化包 `vault.monitor`（名族 `Core*/Signal*/Quiet*`，DEX 里真实存在但方法体全空）、
**36 个 meta-data**（13 条 `cfg_mark_<UTC 时间戳>_<序号>_<随机>` 水印；**同名不同值四组**
`cfg_nonce`/`build_lane`/`seq_mark`（**int 类型**）/`compile_ms`（毫秒时间戳，与 ZIP 时间戳同一时间线）；
9 条 `com.<随机>.<随机>`）、`<queries>` 里放 `dummy.query.placeholder`。
另有第二份 382 字节的明文 `ANDROIDMANIFEST.XML`（`package=com.zip.decoy.abcb2191`、`label=ZipDecoy7a320a`、
`debuggable=true` + `SYSTEM_ALERT_WINDOW`）用于毒化按文件名归因的工具。

## 2. DEX 层

- 外层 `classes.dex`(655 类) / `classes2.dex`(638 类)，`dex\n037`；`CLASSES.DEX`（大写，87,415 B，`dex\n035`）
  头部字段与文件长度不自洽（`file_size=3334168591`、`endian_tag=0x769f7bed` 非法）、熵 7.998 → **纯诱饵**。
- **字符串加密**：每个 DEX 自带一份解密器（`Lcom/rjurepzl/cf/iimlqh;` / `Lcom/wd/cphz/eb/wkpbmcnlx;`，
  **类名不同、代码与 32 字节 AES-256-GCM 密钥完全相同**，**跨 DEX 零引用**）。密文布局
  `Base64( IV[12] ‖ AES-GCM(明文) ‖ tag[16] )`，密钥是池内 Base64 常量（明文躺在池里）。
  实测两个 DEX 的 424 处调用点**全部解出**；**选择规则是「仅 1 个 const-string 引用且解密后 ≥8 字节」，
  但只加密了其中 ~40-45%**（463 选 206、557 选 218），多引用串一律不加密 —— 样本的 **C2 上报地址
  `https://hollywdb.top/api/report`、AES 密钥本身、`android.app.ActivityThread` 都是明文**。
- **反射成员名走字符串加密**：`addFontFromAssetManager`、`mMainThread`、`performStopActivity`、
  `asyncTraceBegin`、`isTagEnabled` 等全部是密文；但 `Class.forName` 的目标类名保持明文。
- **控制流**：**没有** CFF、没有不透明谓词、没有指令替换、没有死代码（逐方法全量分析，0 命中）。
  唯一的反分析痕迹是 **nop-before-return 花指令**：单发 nop 2862+3539 条（占指令字 3.7~4.0%），
  **99.65%/99.86% 的后继指令是 `return*`**。
- **命名**：466/489 个类落默认包、1~2 字符短名（`LA0; LA1$a;`）；方法名 1678/2164 个长度为 1；
  R 类被彻底混淆（`LB7;` 的 45 个 `static int` 字段改成 `A..z` 短名，`static_values` 里的
  `0x7f08xxxx` 资源 ID **原样保留**）。
- **运行时防护：没有**。反 Root / 反调试 / 反注入 / 反模拟器 / 签名自校验 / 完整性自校验**全部 0 命中**
  （精确串检索 + 解密后的 327 条明文 + 方法引用扫描）；`su` 的 62 次命中全是 `result/super/...` 子串。
  唯一的环境检查是功能性的（`isMiFamily`、无障碍服务开关、目标包是否已安装）。
- **无 VMP / Dex2C**（`ACC_NATIVE` 0 个，无 `.so`）；无类膨胀；`SourceFileIdx` 97% 保留 R8 的 `r8-map-id-…`。

## 3. 资源层（`resources.arsc` 与 `res/`）

`resources.arsc` 206,772 字节，**STORED**，结构**完全自洽**（aapt2 完整读取；315 个 `res/...` 文件引用
**315/315 全部存在**，不是诱饵表）：

- 字符串池 1533 条 + 单 package(`0x7f`)；`typeStrings` 里出现 **`?15` 占位名**，恰对应未被使用的 typeId 15
  （内层 APK 同样有 `?12`/`?16`）—— 推断表被自定义工具**重建**过，但无法确定工具。
- **路径全量改名**：315 条 `res/<单字母>/<单字母>.<ext>`。
- **资源条目名（keyStrings）也随机化**：1216 条 key 里 546 条纯随机 token（`acjrw38`），
  **163 条带类型前缀**（`vx_s_`/`vx_c_`/`vx_d_`/`vx_i_`/`vx_b_` = string/color/dimen/integer/bool），
  ~507 条 AppCompat/AndroidX 库名保持原名；**key 与文件名解耦**。
- **资源值零宽多份化**：20 个逻辑值在池里出现 2~4 份，差异只在 U+200E/U+200F（LRM/RLM）的数量
  （0/1 前缀/1 后缀/**93~97 前缀+6 后缀**）—— 用于打散「按字符串内容做签名/去重」的规则。
- **`res/` 内容本身没有加密**：采样全是合法 PNG（含标准 9-patch chunk `npTc/npLb/npOl`）与合法 AXML。
- 89 条 `res/` 诱饵条目使用 aapt2 常见源文件名当目录前缀（`res/values/anims.xml////\.png` 这类）。

> 我曾误判「字符串池每条串有两个长度字节 = 额外加固」，核对后确认那是 **AOSP UTF-8 池的标准布局**
> （`u16 字符数` + `u8 字节数`），是解析器写错了。

## 7. 存疑 / 未解出

1. **样本是否可安装**：外层 Manifest 的首个子 chunk 是未知类型 `0xB4A7`，而 AOSP `ResXMLTree::setTo` 要求该位置必须是
   字符串池；样本的 v2 摘要与当前字节**不匹配**（签名后被改写）。但**模拟器实测安装成功、启动正常** —— 所以
   「严格 AOSP 校验会拒绝」这个推断**与实际不符**，说明平台路径的校验比源码读起来宽松（或 vendor 分支不同）。
   我们因此没有照抄「首个子 chunk 用未知类型」这一条（我们的 A15 把假 chunk 放在字符串池**之后**也一样生效）。
2. `com.qelt.stat` 是三方 SDK 还是宿主自建模块，未确认（DEX 里是真实实现，18 个方法）。
3. 样本加密串的**采样比例**（463 选 206）没有找到确定性判据，最可能是工具端配置的 ~40% 采样。
4. 内层 APK 的 8~9 个 DEX 类数异常均匀（2793~2794 类/个），怀疑内层也部分由工具批量生成，未做逐类语义闭环。
5. `dummy.installed.check` 既是样本里唯一的假包名，又恰好等于本仓库早先的 `defaultDecoyPkg` 默认值 ——
   无法从样本自身判定是「厂商诱饵被我们抄走」还是「样本与本仓库同源」。**本仓库该默认值已不再使用**
   （A8 现在全部由 seed 派生），但这条线索值得留意。
6. `cfg_mark_20260919220102_*` 等构建水印与 `r8-map-id-e9426407…`、证书 notBefore `2026-09-19 13:57:14Z`
   构成完整时间线；样本的构建工具链仍未知。
