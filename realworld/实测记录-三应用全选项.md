## 本轮修复的缺陷（全部在真机上复现过，并补了回归测试）

### 1. `android:appComponentFactory` 未处理 → 启动即 `ClassNotFoundException`

**现象**（三个应用都有这个属性，全部启动即死）：

```
E LoadedApk: java.lang.ClassNotFoundException:
    Didn't find class "androidx.core.app.CoreComponentFactory"
```

**根因**：该工厂类由 `LoadedApk.makeApplicationInner` 实例化，时机在壳的
`attachBaseContext`（我们接管 ClassLoader 的地方）**之前**；那时业务 DEX 还在
加密载荷里，工厂类根本不存在。

**修法**（`passes/shell.go`）：把 `android:appComponentFactory` 指向框架默认实现
`android.app.AppComponentFactory`。保留「按类名实例化组件」的标准语义，丢失的只有
androidx 的 `CompatWrapped` 包装特性。

---

### 2. A1 分配新类名时把「默认包」算成空前缀 → 非法描述符

**现象**：Dhizuku 加固后 DEX 被官方工具判非法：

```
dexdump E: Failure to verify dex file 'classes.dex': Invalid type descriptor: '[[auo;'
```

**根因**（`passes/rename.go`）：新名由 `包前缀 + 短名 + ";"` 拼成，而包前缀取
`LastIndex('/')` 之前的部分——**默认包**的类（混淆过的应用里极常见，如 `Lkf;`）
算出空串，于是生成 `auo;`（**缺开头的 `L`**），数组形式更会变成 `[[auo;`。

**修法**：`classPkgOf()`，默认包返回 `"L"`。回归测试：
`internal/passes/rename_defaultpkg_test.go`。

---

### 3. A1 的 `handler_off` 在类型索引跨 ULEB 边界时算错 → 整个 DEX 被 ART 丢弃

**现象**：

```
dexdump E: Failure to verify dex file: Bogus handler offset: 6
```

**根因**（`internal/dex/insn.go`）：`Encode` 用「把内存里的 handler 重新编码一遍」
来推算旧偏移，但那时**捕获类型的索引已经被改名改写**；索引跨过 ULEB128 的
127→128 边界时，重编码得到的布局不再是文件里的布局，映射查不到就**静默沿用旧
偏移**。索引小的应用（如本项目测试应用）永远碰不到这个边界。

**修法**：解析时记录每个处理器在原始字节里的真实偏移（`CodeItemFull.HandlerOffs`），
映射的键始终取字节事实；查不到时**直接 panic** 而不是静默产出非法 DEX。
同时把守卫改成用「解析出的字节事实」校验（此前它用同一个编码器重算，等于自己
校验自己，恒为真）。回归测试：`TestEncodeHandlerOffAfterTypeIndexGrowth`。

---

### 4. A1 不重写跨 DEX 引用 → `NoClassDefFoundError`

**现象**（Termux：原生就有 30 个 DEX）：

```
NoClassDefFoundError: Failed resolution of: Lcom/termux/shared/termux/TermuxConstants;
    ... DexPathList[[dex file ".../d0.dex", ... "d74.dex"]]
```

**根因**：A1 的改名计划只由「**本 DEX 定义**的类」构成。于是「A 定义、B 引用」的
类在 B 里仍写着旧名。RustDesk 一直没暴露这个问题，是因为它是**单 DEX**，那 16 份
分片是 B4 在**改名之后**才拆出来的。

**修法**：`Plan()` 把 `ClassMap` 中「非本 DEX 定义」的条目（纯引用）也纳入计划，
并为它们派生数组描述符。回归测试：`rename_crossdex_test.go`。

---

### 5. A1 的成员改名在跨 DEX 时不一致 → `NoSuchFieldError`

**现象**：

```
NoSuchFieldError: No field TERMUX_HOME_DIR of type Ljava/io/File;
    in class Lcom/termux/shared/termux/dt;
```

**根因**：成员改名按「名称字符串」生效，而各 DEX 各自决策、各自生成新名：
定义方改成 `a`、引用方仍是 `TERMUX_HOME_DIR`。

**修法**：成员改名也做成**全局决策**——① 每个 DEX 先各自表态；
② 只保留「所有用到它的 DEX 都同意改」的名称；③ 由一份全局生成器统一命名；
④ 对「有 DEX 不同意」的名称**显式全局保留**（`MemberKeep`，只排除在
`MemberMap` 之外是不够的：那样同意的一方仍会自行改名）。回归测试：
`rename_crossdex_member_test.go`。

---

### 6. A1 改名了「覆写框架方法」的方法 → `AbstractMethodError`

**现象**（Dhizuku）：

```
AbstractMethodError: abstract method "void android.view.View$OnAttachStateChangeListener
    .onViewAttachedToWindow(android.view.View)" on receiver ...
```

**根因**：框架接口的实现在本 DEX 里**没有调用点**（调用方是系统），
「引用者是否都在改名集合里」这条判据看不见它；而 `onViewAttachedToWindow`
也不在硬编码白名单里。

**修法**：新增判据——类若（沿本 DEX 内的继承链传递地）继承了**本 DEX 之外**的
父类型，则它的非私有实例方法「可能覆写看不见的方法」，不改名
（`hasInvisibleSuper` + `mayOverrideInvisible`）。
回归测试：`rename_override_test.go`。

---

### 7. A1 改名了「引用自不可见父类的成员」 → `NoSuchMethodError`

**现象**（Termux 的 `hiddenapibypass` 库）：

```
NoSuchMethodError: No virtual method aez(Ljava/lang/String;)Ljava/lang/Class;
    in class Lorg/lsposed/hiddenapibypass/nc; or its super classes
    at org.lsposed.hiddenapibypass.nc.loadClass(Unknown Source:15)
```

**根因**：`nc` 继承 `dalvik.system.PathClassLoader`，它调用 `loadClass` 时**静态
类型是自己的类**，于是 method_ids 里写的是 `Lnc;->loadClass(String)Class`——看起来
像应用内部方法，实际是**从框架父类继承来的**，改名后解析不到。

**修法**：引用若在**可见继承链**里找不到声明，就说明声明在看不见的父类型里，
该名称必须保留（`resolvesVisibly`）。回归测试：`rename_inherited_test.go`。

---

### 8. A1 改名了被布局 XML 按名字引用的类 → `InflateException`

**现象**（Termux）：

```
InflateException: Binary XML file line #8 in com.termux:layout/activity_termux:
    Error inflating class com.termux.app.terminal.TermuxActivityRootView
```

**根因**：自定义 View 以**字符串**形式写在布局里，与 DEX 的类型引用无关；
改类名不会同步改到它。

**修法**：新增「被动引用扫描」——把 `AndroidManifest.xml`、`res/**/*.xml`、
`resources.arsc` 字符串池与 `assets/**` 里**确实存在对应类**的类名加入保留集
（`passiveClassRefs`）。只保留真实存在的类，避免把普通字符串误当类名。

## D5 设备标识的正确采集方式（实测）

`adb shell settings get secure android_id` **取不到**应用内看到的那个值：
Android 8.0 起 `ANDROID_ID` 按「应用签名 + 用户 + 设备」作用域化。实测同一设备：

| 取值方式 | 值 |
|---|---|
| `adb shell settings get secure android_id` | `2ad89c08d44767b6` |
| 应用内 `Settings.Secure.getString(cr, "android_id")` | `32a023838d4d9174` |

因此 D5 的绑定值必须**由应用自己报出来**：用 `-debug-shell` 出排障版，在目标设备上
跑一次，`adb logcat -s APKGUARD-D5` 打印的就是要绑定值（本轮已加入该日志）。
作用域是按**签名证书**的，所以同一张密钥库签的多个应用取到同一个值。

## 剩余限制（如实说明）

- **A1 在成员改名上偏保守**：多 DEX 应用里，跨 DEX 共用的成员名会被一致保留；
  继承链含框架类型的类，其非私有实例方法也不改名。**类改名不受影响**
  （Dhizuku 3047 / Termux 372 / RustDesk 2785 个类），但方法/字段改名比例下降
  （RustDesk 仅 15 个方法、0 个字段）。这是「宁可少改，不可改错」的取舍：
  真实混淆器（R8/ProGuard）靠**库方法表**判断覆写关系，本工具没有该信息，
  只能用保守判据替代。
- 上述判据仍可能漏掉「通过字符串名反射调用」与「assets 里拼出来的类名」等
  被动引用形式；已覆盖 XML / 资源表 / assets 的类名扫描，但无法穷尽。

> A9/A10/A12 的垃圾条目质量提升。

### 新增缺陷与修法

#### 1. 注入类的 `<clinit>` 缺 `ACC_CONSTRUCTOR` → ART 每次加载都告警

**现象**：

```
W/...: <clinit> didn't have expected constructor access flag
       in class com.apkguard.nativebridge.Native in dex file .../base.apk
```

**根因**（`internal/dex/assemble.go`）：生成入口只给 `<init>` 补了
`ACC_CONSTRUCTOR`（0x10000），`<clinit>` 漏了。**修法**：两个名字都补；
回归测试 `TestInjectedClinitHasConstructorFlag`。

#### 2. `-package-shrink` 把所有类压进默认包 → `IllegalAccessError`

**现象**（Termux，启动即崩）：

```
java.lang.IllegalAccessError: Illegal class access: 'ac' attempting to access
    'com.termux.app.utils.CrashUtils$1' (declaration of 'ac' appears in .../d39.dex)
```

**根因**：A1 的保留规则把 `$` 内部类（`CrashUtils$1`）连同其外层类留在原包，
而 `-package-shrink` 把其余可改名类统统压进**默认包**。于是原本同包的
package-private 访问变成了跨包访问。

**修法**（`internal/passes/rename.go`）：改为**按包压缩**——每个原包整体映射为
一个无意义短包名（`Lpa/`、`Lpb/`…），原来同包的类压缩后仍然同包；**含保留类的包
整体保持原包名**（否则搬走的类再也访问不到留下的 `$` 内部类）。
回归测试：`TestPackageShrinkCompressesPackageNames`、
`TestPackageShrinkKeepsPackagesWithKeptClasses`。
> 注：`internal/dex` 里的 `ShrinkPackage`（单 DEX 粗粒度开关）保留为库 API，
> 但其注释已明确写出这个坑，CLI 不再使用它。

#### 3. ServiceLoader 的两半类名只存在于资源里 → `Main dispatcher is missing`

**现象**（RustDesk 1.5.0，Flutter，UI 首次 attach 即崩）：

```
java.lang.ExceptionInInitializerError
Caused by: java.lang.IllegalStateException: Module with the Main dispatcher is
  missing. Add dependency providing the Main dispatcher, e.g.
  'kotlinx-coroutines-android' ...
```

**根因**：`META-INF/services/` 有**两半**引用，都只写在资源里、DEX 中没有对应
字符串常量，因此 `reflectedClasses` 看不见：

| 位置 | 本例的值 | 含义 |
|---|---|---|
| 文件**名** | `META-INF/services/j3.t` | 服务接口类名（R8 混淆后的 `j3.t`，即 `kotlinx.coroutines.internal.MainDispatcherFactory`） |
| 文件**内容** | `f3.a` | 提供者类名（`AndroidDispatcherFactory`） |

改任意一半，`ServiceLoader.load` 都会加载不到实现。

**修法**（`internal/passes/rename.go` 的 `passiveClassRefs`）：新增
`META-INF/services/` 分支，把**文件名**与**每行内容**（跳过 `#` 注释）都加入
保留类；顺带把 `res/` 下的非 XML 资源也纳入类名扫描。
回归测试：`TestServiceLoaderProviderIsNotRenamed`。

#### 4. A10 注入假 `MANIFEST.MF` → v1 签名校验失败

**现象**（RustDesk 1.5.0，`ServiceLoader` 读 `META-INF/services` 时）：

```
java.lang.SecurityException: Invalid signature file digest for Manifest main attributes
  at sun.security.util.SignatureFileVerifier.processImpl
  at java.util.jar.JarVerifier.processEntry
  at libcore.io.ClassPathURLStreamHandler$ClassPathURLConnection.getInputStream
  at java.util.ServiceLoader$LazyClassPathLookupIterator.parse
```

**根因**：A10 曾注入 `META-INF//MANIFEST.MF`、`META-INF/./MANIFEST.MF`、
`meta-inf/MANIFEST.MF`。ZIP 条目名在 Android 的 `JarFile`/`ZipUtils` 里是
**大小写不敏感**地比较 `META-INF/MANIFEST.MF`，于是校验器读到了**假 manifest
的主属性**，`.SF` 里的摘要自然对不上。触发链是「ServiceLoader 经 JarFile 读资源
→ 触发 v1 校验」——**只有同时用到 ServiceLoader 的应用才会暴露**。

**修法**（`internal/passes/passes.go`）：新增 `manifestCollision(name)` 守卫，
把条目名归一化（折叠重复斜杠、消解 `.`/`..` 段、统一大小写）后，拒绝任何
`META-INF/MANIFEST.MF` 或 `META-INF/*.{SF,RSA,DSA,EC}`；A10 与 A12 的注入
一律过这道守卫，畸形名改用 `.MFx` 之类不撞名的形态。
回归测试：`TestManifestCollisionGuard`、`TestJunkEntriesNeverInjectManifestCollision`。

### 本轮收口：A8 诱饵组件已落地；B3 内存加载经实测判定不可行

**A8 诱饵组件（已完成）**：给 `axml` 增加了元素插入能力（在 `<application>` 的
结束块前插入新的 start/end element 块对），A8 现在把 6 个诱饵类真的声明成
`<receiver>` / `<service>`：

```
SecurityMonitor(receiver)  IntegrityChecker(receiver)  RootGuard(receiver)
ThreatDetector(service)    LicenseValidator(service)   AntiTamper(service)
```

两条硬约束：**绝不声明 `<provider>`**（它会在应用启动时被 ActivityManager 主动
实例化），**不加 intent-filter**（没有过滤器时系统永不实例化，声明只对静态分析可见）；
被声明的类都继承正确的框架基类并实现其抽象方法（`onReceive` / `onBind`），
即使被实例化也只是「什么都不做」。三个应用复验通过。

**B3 内存加载（经实测判定不可行，已放弃）**：设计文档原本设想用
`InMemoryDexClassLoader` 让明文 DEX 不落盘。在 Android 16（API 36）上逐条撞墙：

| # | 尝试 | 结果 |
|---|---|---|
| 1 | `new InMemoryDexClassLoader(bb, parent)` | 应用自己的 `.so` 找不到：`UnsatisfiedLinkError ... couldn't find "librustdesk.so"`——二参数版本没有 `librarySearchPath`，`nativeLibraryDirectories` 只剩系统目录（RustDesk/Termux 复现；Dhizuku 无原生库所以看不出） |
| 2 | 改用三参数 `(bb, parent, libDir)` | `NoSuchMethodError`——该构造器在 AOSP 里是 **private**，公开 API 里不存在 |
| 3 | 注入子类覆写 `findLibrary` | `VerifyError: Superclass dalvik.system.InMemoryDexClassLoader of com.apkguard.shell.MemLoader is declared final`——它是 **final** 类，不能继承 |

剩下只有反射改写 `DexPathList` 的内部字段：那些字段名在 API 29~36 之间变过、
且属非 SDK 接口会被隐藏 API 限制拦下，可靠性无法保证，失败代价是应用加载
自己的 `.so` 时崩溃。**因此 B3 保持落盘的 `DexClassLoader`**（第三个参数传
`nativeLibraryDir`）——明文 DEX 落在应用私有目录，只有应用自己与 root 可读，
这也是主流加固方案的通行做法。相关取舍与证据已写进设计文档 §B3。

副产品：测试里 `DexClassLoader` 的模拟此前**只校验 `dexPath`**，
「库搜索路径悄悄变成 null」这类缺陷在测试里完全看不见；现已补上
`librarySearchPath` 非空校验，并让 `ApplicationInfo.nativeLibraryDir` 真的
挂在模拟实例上（壳代码是用 `iget-object` 读它，此前模拟返回的是空对象）。

## 第三轮：对照 sample.apk 补齐加密/混淆强度

> 起点：把 `sample.apk`（一个真实加固样本，外层薄壳 + 内层完整 APK）与我们逐条对照，
> 找出加密与混淆上落后于它的地方。样本实测档案：载荷是**单字节 XOR（密钥 0x5A 通篇固定）**，
> 一条命令即可解出内层完整 APK（3029 条目 / 8 个 DEX / 22366 类）；样本**完全没有 native 层**
> （0 个 native 方法、0 个 `.so`）。因此本轮的着力点是：补齐样本比我们强的地方，
> 并把我们本就强于样本的部分（AES 载荷、native 派生密钥、C1/C4/C5/C6）保持住。
>
> 环境不变：Android 16（API 36）x86_64 模拟器，已 root；D2/D3 按设计排除。
> **结论：三个应用在「全选项 + 载荷 MAC」与「全选项 + C2」两种配置下均正常运行。**

### 本轮修掉的缺陷

#### 1. A2 的密钥流形同虚设（安全缺陷）

**现象**：`internal/dex/strenc.go` 的密钥流是 `key + i*17`，密钥只有 **1 字节**。

**根因**：仿射密钥流 + 单字节密钥 ⇒ 攻击者拿到**任意一组** (明文, 密文)（例如
`"UTF-8"`、`"Android"` 这类必然存在的常量）即可解出 `key`，随后一次性解出全部字符串。
等于没有加密。

**修法**：密钥扩到 32 字节；密钥流改为
`keystream(i) = SHA-256(secret ‖ 0x01 ‖ nonce ‖ LE32(i))[0]`，其中
`nonce = SHA-256(secret ‖ 0x00 ‖ 明文)[0:8]`，密文为 `Base64(nonce ‖ 逐字节异或)`。
每个字符串带独立 nonce，因此不同字符串在相同下标处的密钥流相互独立，
单点已知明文既推不出 secret、也解不出别的字符串。
回归测试：`TestKnownPlaintextCannotRecoverKey`、`TestKeyStreamNotAffine`、
`TestEncryptStringDeterministic`，外加用真实解释器跑的往返测试。

#### 2. A1 成员名覆盖率过低（与样本差距最大的一项）

**起点**：RustDesk 只改了 15 个方法、0 个字段，而类名改了 2785 个。样本的类名混淆
覆盖率是 71%~77%（默认包短名）。

**根因**：改名按「名称字符串」全局决策——DEX 字符串池去重，一个名字被多个
`method_ids` 共用，只要有一个引用者不同意改名就全局保留。

**修法**（`internal/dex/rename.go` + `internal/passes/rename.go`）：改名单位改为
「(声明类, 名字, 原型/类型) 引用」；为改名引用**追加新字符串**并只覆盖目标
`method_id`/`field_id`（新增 `RebuildOptions.MethodNameByID` / `FieldNameByID` 通道），
旧名字字符串原样留给其它引用。本轮先做**可证明安全**的三类：私有成员、静态成员、
继承闭包完全可见时的可证明非覆写成员；不可见闭包一律整族保留。

**效果**（A1-only 基线对比）：

| 应用 | 类 | 方法 | 字段 |
|---|---|---|---|
| Dhizuku | 3047 | 53 → **764** | 0 → **872** |
| Termux | 325 | 637 → **1204** | 0 → **963** |
| RustDesk | 2607 | 10 → **147** | 0 → **209** |

#### 3. `const-string` 索引越界（A1 追加字符串触发）

**现象**（Termux）：加固直接失败

```
错误: 功能项 A1（名字混淆）执行失败: 重建 classes.dex 失败:
  dex: 指令 0x1a @word 23 引用索引 65592 超出 16 位，需要指令加宽
```

**根因**：重建按 UTF-16 序**重排**字符串池，新下标与旧下标无关；Termux 的
classes.dex 有 **65866** 个字符串（本身就超过 16 位，原 DEX 用 jumbo 表达高位串），
一旦我们追加字符串（成员改名要追加新名字），排序位移就可能把某个原本合法的
`const-string`（16 位索引）推到 65536 以上。

**修法**：正确处理是「把越界的 `const-string` 加宽为 `const-string/jumbo`」，
那属于要做长度变化并重算偏移的改动，本轮未做；先**保守降级**——只要有一个 DEX
的池接近上限（`> 65535 - 1024`），就整体放弃「追加字符串」的改名通道
（值键通道不新增字符串，保持原行为），并把原因与池大小写进 Note。Termux 触发该降级。

> 附带否掉一个方案：曾尝试「把被 const-string 引用的字符串排到池前部」来避开越界，
> 但 DEX 要求 `string_ids` **有序**，ART 会校验并直接拒绝整个 DEX：
> `Failure to verify dex file: Out-of-order string_ids: 'V' then ''`。该方案已回退。

#### 4. A15 用量子级体积做同等的防御（对齐样本）

样本的 Manifest 是 **369,623,060 字节解压 / 367,318 字节压缩（比值 0.001）**，
证明系统接受压缩存储的 Manifest。我们原先用 STORED，16 MB 填充就实占 16 MB。
改为压缩后，e2e 的 7-packed 产物从 **17,058,818 字节降到 297,530 字节**（约 1/57），
防御效果（解析器仍要面对 16 MB 解压内容）不变。

#### 5. A3 重复包装 A2 注入类的常量 + 统计翻倍

A2 与 A3 是两次**独立**的 Rebuild，A2 写回的 DEX 里解密器已是「既有类」，
于是 A3 把解密器自己的 `"SHA-256"` 常量也数组化了——既白增体积，又让解密器
反向依赖还原器。（旧版解密器只有 `"UTF-8"`，恰好与 A3 自己注入类用到的串同名
而被连带跳过，把这个缺陷掩盖了。）统计方面，`ca.count` 在多次布局迭代中累加，
1 次被记成 2 次。

修法：`dex.DecryptorStrings()` 暴露解密器常量集合，A3 的 Pass 用它构造 `Skip`
（这类跨 Pass 知识只能在 Pass 层传递——A3 那轮 `StringEncrypt` 为 nil，dex 层无从知晓）；
A3 计数在每轮 `generate` 开头清零。

#### 6. `collectAdditionStrings` 不遍历注入代码的补丁表（潜伏缺陷）

`expandAdditionRefs` 明确把 `RefString` 留给 `collectAdditionStrings` 处理，
而后者只遍历 `Types/Protos/Methods/Fields`、**不看代码补丁**，于是注入代码里的
`ConstString` 从未登记——只靠「这些串恰好已存在于输入 DEX 池里」侥幸成立
（`"UTF-8"`、`"SHA-256"` 恰好都在样本池里）。输入池里没有时会直接报
「字符串密文未进入字符串池」。已修。

#### 7. C2 的落地目录名含路径分隔符 → 一装上就崩

**现象**（Termux，开启 C2）：

```
java.lang.RuntimeException: Unable to instantiate application com.apkguard.shell.App
  package com.termux: java.lang.IllegalArgumentException:
  File app_ag/lib contains a path separator
```

**根因**：`Context.getDir(name, mode)` **拒绝**含路径分隔符的名字，而 C2 传的是
`loaderTempDir + "/lib"`。崩在壳的 `attachBaseContext` 里，表现为「一装上就崩」。
改为扁平目录名（`aglib`），并加了一条「目录名不得含分隔符」的回归断言。

### 本轮新增的能力

#### C2 SO 加壳（opt-in：`-so-encrypt`）

把 `lib/<abi>/*.so` 从 APK 移除、整体加密存入 assets，壳启动时解密到应用私有目录，
并把该目录并入 `DexClassLoader` 的库搜索路径（`System.loadLibrary` 经
`ClassLoader.findLibrary` 解析，因此能找到）。**检测到 native 自加载框架特征
（`libflutter.so`/`libapp.so`/`libhermes.so`/`libunity.so` 等）会整体跳过**并写明原因——
这类框架用 `android_dlopen_ext` 从 APK 按偏移加载，移走 `lib/` 会让应用启动即崩，
且无法用库搜索路径挽救。

实测：Termux（2 个 .so，29.4 MB）加密后正常运行；RustDesk（Flutter）被审计跳过、
正常运行；Dhizuku（无原生库）空操作、正常运行。

#### 载荷完整性 MAC（opt-in：`-payload-mac`）

encrypt-then-MAC + HMAC-SHA256，密文格式扩为 `IV ‖ CT ‖ Tag`，MAC 输入绑定
**原始 DEX 名**（不绑 Asset——B8 会重命名 Asset），密钥用域分离派生，壳侧常量时间
比较、失败硬终止。关闭时载荷格式与旧版逐字节相同。

### 本轮**否掉**的两项（附证据）

#### A6 控制流混淆：当前形态不安全，不开放

两类插入形态都在真实应用上触发 ART 校验失败，关掉 A6 即恢复正常：

| 形态 | 结果 |
|---|---|
| 谓词 + 尾部死代码块（`goto` 跳回方法入口） | `VerifyError: ... [0x6D] wide register v7 has type Low-half Constant/Conflict` |
| 谓词改为两条分支**前向**汇聚（无回边） | 同一处、同样的错误 |

另外两种寄存器策略也都在实测中暴露问题：

- 只肯用「全方法从未被引用」的寄存器 ⇒ 优化过的 DEX 里几乎不存在，testapp 改写 0/28、
  样本 0/26，功能等于**没实现**（静默失效，正是本项目最忌讳的失败模式）；
- 放松为「入口处复用任意局部寄存器」⇒ 触发上述宽值类型冲突。

根因是：安全地改写方法体需要**寄存器类型/活跃性分析**（至少要能识别宽值寄存器对）。
在那之前，A6 按项目原则保持「未实现」状态——启用会被显式拒绝，而不是静默地少做防护。
实现与单元测试保留在 `internal/dex/cff.go`、`cff_test.go` 作为后续基础。

#### 「重排字符串池」修索引越界：方案本身不成立

见上文第 3 条：破坏 `string_ids` 有序性，ART 报 `Out-of-order string_ids` 并丢弃整个 DEX。

## 第四轮：欺骗类手法 + 控制流/花指令 + native 伪装

> 本轮按「把能想到的加固手法全部实现」的要求，新增 6 个功能项（A16~A20、C7），
> 并把 A6 从「未实现」推到可用。过程中在真机上一共抓出 **5 个会崩溃的真缺陷**，
> 其中 3 个只有「多启动一次」或「同时启用某两个功能项」才会暴露。
> **最终：三个应用在「全部 41 个已实现项同时启用」下均正常运行。**

### 新增功能项

| ID | 名称 | 做了什么 |
|---|---|---|
| A16 | 诱饵核心文件 | 注入大小写/同形变体的假 `AndroidManifest.xml`/`resources.arsc`/`classes.dex`。与 A9 的区别：A9 只伪造 DEX magic（解析必失败），A16 这一档**每个文件都是可被解析的完整结构**（假 Manifest 有 manifest/application/activity 元素树、假 DEX 能过 `dex.Parse`+`Verify`）。绝不与真核心文件同名——Android 只读精确名，所以大小写变体不影响运行，但自动化工具必须逐个读完才知道是假的 |
| A17 | 嵌套 APK 诱饵 | 在真载荷**同一目录树**下放一个结构完整、能被 apktool/jadx 打开的假 APK（自带合法 Manifest / arsc / 3 个 classes.dex / assets / META-INF，默认 1~4 MB）。这是对样本「内层真 APK」的**反向利用**：样本用嵌套 APK 藏真身，我们用嵌套 APK 喂假货——自动化脱壳脚本按「assets 最大条目」或「PK 形态」抓载荷时先抓到它，解包后得到一个看起来完全正常的假应用 |
| A18 | Manifest 诱饵元数据 | 注入假 `uses-permission`/`meta-data`/`uses-feature`/`queries`。安全约束是硬的：权限**只用系统未定义的自定义名**（安装器完全忽略，零运行影响）、特性**全部 required=false**（不参与商店设备筛选）、`queries` 只写不存在的包名、meta-data 只选与已知功能键**非精确匹配**的名字 |
| A19 | 字符串池垃圾 | 往每个 DEX 的池注入 300 条形似业务常量的串（URL/端点、`*_api_key`、形似令牌的 hex/base64、错误码、文件路径、中文/emoji 混排），推高 `strings` 输出的噪音 |
| A20 | 无害花指令 | 每个方法入口插 `nop×N` + 两条前向汇聚的 `goto/16`。**不写任何寄存器**，因此不存在类型冲突 |
| C7 | 原生库伪装 | 把 `libapkguard.so` 改名为 `libsqlite3x.so` 之类，并同步改写壳 DEX 里的 `loadLibrary` 参数（否则会「壳用旧名加载、产物里只有新名」必然崩） |

### 本轮抓出的真缺陷（全部在真机上复现并修复）

#### 1. `const-string` 索引越界 → 自动加宽为 jumbo

重建按 UTF-16 序重排字符串池，池超过 65535 时排序位移会让原本合法的 `const-string`
（16 位索引）落到 65536 以上：

```
dex: 指令 0x1a @word 23 引用索引 65592 超出 16 位，需要指令加宽
```

Termux 的 classes.dex 有 **65866** 个字符串（本身就超过 16 位）。修法是
`internal/dex/widen.go`：在处理链最后一步把越界的 `const-string` 替换为
`const-string/jumbo`，并**按项内相对偏移精确平移 `skip`**（那是 A2/A3 登记的
"已重映射、不可再映射"的绝对字位置，平移错会让池引用错乱）。有了它，
A1 的「追加字符串」通道不再需要在池接近上限时降级（那条降级已移除）。

#### 2. 载荷落盘后第二次启动必崩（EACCES）

```
java.lang.RuntimeException: Unable to instantiate application
  java.io.FileNotFoundException: .../app_ag/d0.dex: open failed: EACCES (Permission denied)
```

MarkReadOnly 打开时（targetSdk ≥ 34），上次启动已把 `d0.dex` 标记为**只读**；
`FileOutputStream` 覆盖只读文件没有写权限。**表现为「装上第一次能开、第二次就崩」**
（只有反复启动才暴露）。修法：写之前先 `File.delete()`——删只读文件在应用自己的
目录里是允许的。回归测试 `TestLoaderDeletesStaleDexBeforeWrite`。

#### 3. A6/A20 写寄存器 → 宽值高半类型冲突（**最后一个才找到根因**）

```
VerifyError: Verifier rejected class dqg: boolean dqg.hashCode() failed to verify:
  [0x49] wide register v6 has type Long (Low Half)/Integer
VerifyError: Verifier rejected class pan.bbu: [0x6D] wide register v7 has type
  Low-half Constant/Conflict
```

这条排查了**四轮**，每一轮都排除了一个假设：

| 假设 | 结果 |
|---|---|
| 死代码块跳回方法入口形成回边 → 校验器要在入口合并类型状态 | 改成纯前向汇聚后**仍崩** |
| 复用任意局部寄存器（"入口处尚未定义，应该安全"） | 崩（这是最初引入问题的改动） |
| 只肯用「全方法从未被引用」的寄存器 | 真实应用上改写 **0/28**：等于**没实现**（静默失效） |
| **`cffRegs` 只报告指令显式写出的寄存器，而 `long`/`double` 占两格** | **根因** |

最终修法：判空闲寄存器时，把每个被引用寄存器**及其相邻格**都算作已占用
（`used[r]=true; used[r+1]=true`）。写进宽值高半这条路被堵死，A6/A20 在
三个应用上全部通过。副作用是谓词路径在优化过的 DEX 上覆盖为零（找不到两个
连续空闲寄存器），真实覆盖落在**不需要寄存器**的不可达跳转块上
（RustDesk 2.3 万个方法）——零风险、覆盖面大。

#### 4. 削节头被 Android 链接器拒绝（功能项因此收缩）

C7 原设计是「改名 + 清除 ELF 节头（`readelf -S` 失败）」。实测两次真机崩溃：

```
UnsatisfiedLinkError: dlopen failed: ... has unsupported e_shentsize: 0x0 (expected 0x40)
UnsatisfiedLinkError: dlopen failed: ... has invalid e_shstrndx
```

即「加载只用 program header、节头随便改」的假设**不成立**——链接器会校验节头表
自洽性。改试「只清空 `.shstrtab` 内容（保留所有头字段）」能骗过链接器，但 C6 的
完整性校验要靠节名定位 `.text`/`.rodata`，节名读不出来就只能失败关闭（拒绝启动）
或失败开放（静默失效），两者都不比不做更好。**结论：C7 只保留改名**，
`-lib-strip-sections` 改为**显式报错**（并说明原因），而不是静默忽略。

#### 5. C6 的自校验在本机从来就没生效过（被"失败关闭"改动暴露）

把三处「取不到就当作完整」改成失败关闭后，应用立刻起不来，日志显示 C6 找不到
自身文件。根因：**native 库默认从 APK 内部直接加载**（`extractNativeLibs=false`），
`/proc/self/maps` 里对应的是 `base.apk` 而不是 `.so` 自己的路径——C6 一直静默
失效，只是没人发现。同时把自身定位从「匹配字面文件名」改为 **`dladdr` 反查实际
加载路径**（与改名无关），并给三处降级加上 **`__android_log_print` 日志**
（`tag=APKGUARD`），使这种能力边界在 logcat 里**可见**：

```
I/APKGUARD: C6: 打开自身文件失败（.../base.apk!/lib/x86_64/libsqlite3x.so），自校验跳过
```

真正的修法是「基于**内存镜像**（PT_LOAD）而不是磁盘文件做摘要」——它能在
APK 内加载的场景下工作，还能发现运行期内存改写。曾实现过一版，但实测在设备上
`SIGSEGV`（`ag_intact`），而 C 代码在本环境无法调试，故回退为「可用 + 可见」的
现状，并把内存摘要列为后续工作。

## 第五轮：审计修复（A14 / C1 / A3 / A6 / v1 签名 / arsc / B8 / 载荷密钥）

> 本轮不新增功能项，只修复审计确认的缺陷，并补上脚本与 CI 的门禁漏洞。
> 下面 1~9 条按缺陷逐条记录；**第 8 条在本轮会话中尚未修复，已如实标注为「已知未修复」**，
> 其余为已修。

### 1. A14：签名阶段新增的三个条目退回 1980 默认时间戳（重打包指纹）

**现象**：A14 统一时间戳后，E1 签名阶段新增的 `META-INF/MANIFEST.MF`、`CERT.SF`、
`CERT.RSA` 三个条目未沿用统一时间，退回 ZIP 的 1980-01-01 默认值，产物出现 **2 个**
时间戳——恰好构成 A14 想消除的「重打包指纹」。

**修法**：让 `sign.Options.Stamp` 接住 A14 的统一时间戳。修后产物唯一时间戳恢复为 1 个。
`verify-products.py` 里针对 A14 的断言（只允许一个时间戳、且不得残留 1980）此前是**死断言**
（e2e 从不把 `A14` 传进 verify 的 `feats`，那段永不执行），本轮已把 `A14` 接入
`2-full-checks.apk` 的产物校验。

### 2. C1：密钥 native 派生的接线断了，AES 密钥被逐字节内联进壳 DEX

**现象**：`shellInfo` 缺 `NativeKey` 字段、`classLoader.Run` 未设置
`LoaderSpec.NativeKey`，于是启用 C1 时 AES 密钥仍被逐字节内联进壳 DEX，native 派生形同虚设。

**修法**：接通上述两处接线，并新增断言「壳 DEX 常量里无法还原密钥 + 存在
`Native.derive` 的 invoke-static」。

### 3. A3：常量数组化对超长字符串用 `const/16` 写负数长度 → 运行期抛异常

**现象**：对长度 > 32767 的字符串，`const/16` 写入的长度溢出为负数，运行期抛
`NegativeArraySizeException`（termux 有真实 57328 字节的串）。

**修法**：改用 `const`(31i) 写长度。已加回归。

### 4. A6：`cffRegs` 把 32x 格式按 22x 解析，漏报源寄存器

**现象**：`cffRegs` 把 32x 格式按 22x 解析，漏报指令的源寄存器；不透明谓词据此选中的
「空闲」寄存器可能是活跃寄存器，谓词会写坏它。

**修法**：修正 32x 解析并计入源寄存器占用，同时把每个被引用寄存器的相邻格
（宽值高半）也算作已占用。已加回归。修后受控测试应用上不透明谓词覆盖降为 0，真实痕迹
落在**不可达前向跳转块**上；`verify-products.py` 的 A6 断言相应改为同时认「不透明谓词骨架」
与「不可达跳转块骨架」两种形态。

### 5. v1 签名：折行按字节切断多字节 UTF-8 字符

**现象**：`MANIFEST.MF` / `CERT.SF` 的 72 字节折行按**字节**切断，多字节 UTF-8 字符被切
成两半；API < 24 只认 v1 时校验失败。

**修法**：改为按**字符**折行。已加回归。

### 6. arsc：重写 resources.arsc 时静默丢弃字符串池的 style 数据

**现象**：重写 `resources.arsc` 时未保留字符串池的 style 数据，dhizuku 实测静默丢弃
**28 条 style / 456 字节**。

**修法**：保留 style 数据。

### 7. B8：诱饵容器与真实容器不同构（可被「找 PK 头」一次性区分）

**现象**：旧诱饵是顶层 `assets/<词>_<hex8>.zip`（带 `PK` 头），真载荷却是
`assets/<词>/<hex8>/<hex12>.<ext>` 的密文；脱壳脚本只要「找 PK 头 / 找 zip」就能直接锁定
诱饵、用排除法定位真载荷。

**修法**：诱饵改为与真载荷**同目录树、同命名形态、无 PK 头**——落在
`assets/<词>/<hex8>/<hex12>.<ext>`，另在同目录放一个 `<hex12>.json`（写假包名）。
`verify-products.py` 的诱饵正则与断言同步更新：删掉「诱饵必须带 PK 头」这条（语义已反转），
新增正向断言「容器目录下不存在任何 PK 开头的文件」。

### 8. 默认载荷密钥硬编码与 IV 确定性复用（**已修复**）

**问题**：`pack.Key("")` 回退到硬编码常量 `"apkguard"`；IV 由确定性种子派生，相同明文/种子
会复用同一 IV。任何拿到产物的人都能用源码里公开可算的密钥把载荷解回明文。

**修法**：
1. `pack.Key("")` 与 `deriveKey("","")` 不再回退到固定常量，改为 `crypto/rand` 生成随机
   密钥；`-dex-key` 留空即随机。
2. `-seed` 留空时由 CLI 生成随机种子（此前帮助文本承诺「留空则每次随机」但实现只是把空串
   透传），IV / 载荷名 / 垃圾名等一切由种子派生的东西随之每次不同。
3. B1 与 C2 的载荷密钥**每次运行只解析一次**并共享（见第六轮第 6 条：曾因各自生成随机密钥
   而互相不一致）。

**保留的能力**：显式给出 `-seed`（并可选 `-dex-key`）时产物仍**逐字节可复现**——这是有意
保留的排查/取证能力，不是缺陷。

### 9. A2：密钥曾写进日志 / 统计

**现象**：A2 的调试统计曾输出完整密钥 `A2.key`，泄漏到构建日志。

**修法**：改为只写 **4 字节指纹**。

### 脚本与 CI 门禁修复（与本轮同批）

- **空断言**：CI 与 `ci-local.sh` 的「未实现项必须报错」断言曾匹配功能项 ID `A6`，而输出里
  「启用功能项: …A6…」这一行本身就含 A6，等于恒真（把 A6 换成任意已实现项也照样通过），
  且 A6 早已实现。改为对确定未实现的 **A7** 断言，并匹配**错误文案**（`尚未实现…A7`）。
- **本地 CI 缺页对齐门禁**：`ci-local.sh` 补上 `build_native.py --check`（摘要 + 16KB 页对齐），
  并加入可用的 python 探测（Windows 上 `python3` 可能是应用商店空壳，执行即失败）。
- **e2e 功能集缺项**：补上 A6 / C2 / C7 / E5 的功能集与产物断言，并新增「所有已实现项至少出现
  在某次 `-enable` 里」的自检（该自检可真正失败）。
- **历史残留产物**：e2e 开跑前清空 `deliver/` 的旧 `*.apk` / `*.log`，避免把陈旧产物算进
  全局签名/对齐校验。
- **被静默跳过的关键测试**：CI 的 e2e 作业显式断言 `TestDeriveMatchesNativeC`（C/Go 派生
  逐字节对拍）与 `TestResourceRewritePreservesResourceIDs`（aapt2 资源 ID 复核）必须执行并
  通过，输出中不得出现 `--- SKIP`，并在作业环境里准备 C 编译器与 aapt2。

## 第六轮：装机复验（三个真实应用，模拟器 API 36）

> 这轮的驱动是「把产物装进模拟器，看应用到底还能不能用」，结果不仅验证了应用功能完好，
> 还暴露出一个**让两个功能项在所有设备上静默失效**的根因缺陷。逐条记录如下。

复验方式：`realworld/emu-out/` 下的三个产物由 `scripts/wsl-emu-build.sh` 生成
（`A1..A20` 除 A7、`B1..B8`、`C1,C2,C4,C5,C6,C7,D1,D4,E1..E4,E6` 全开，外加
`-package-shrink -manifest-pad-mb 8 -so-encrypt -lib-name libguardx.so -payload-mac`；
**刻意排除 D2/D3**——目标模拟器已 root，这两项会按设计拦停应用，那是正确行为，
只会把「应用功能是否完好」这个观测点搅浑；D5 需要真实设备标识，同样排除）。

### 1. `ag_seek` 返回值约定错误 → C6/D4 在**所有设备上**静默失效（根因）

**现象**：logcat 里反复出现
`C6: 自身文件缺少 .text/.rodata 节名，自校验跳过`，即完整性自校验与 D4 周期复检从未真正
生效——44 分钟前刚修过的「C6/D4 静默失效」其实只换了个说法，本质没变。

**根因**：`ag_seek` 被写成 `return (long)lseek(fd, off, SEEK_SET)`，而 lseek 成功时返回的是
**新的文件偏移**、只有 seek 0 才恰好返回 0。调用方全部按「0 表示成功」判断，于是
**任何非零偏移的 seek 都被当成失败**：ELF 节表定位在第一次非零 seek 处即告失败。同一个
约定错误还让 `ag_hash_region`（读 .text/.rodata 前先 seek）与 ZIP 条目定位里的
`ag_seek(...) == 0` 判断同时失效——一处写法，三处症状。

**修法**：`ag_seek` 改为返回 `0 / -1`，并在注释里写明为什么不能直接返回 lseek 的结果。

### 2. extractNativeLibs=false 时读不到自身文件 → 改为自己解析 ZIP

**现象**：dhizuku（targetSdk ≥ 30）的 native 库直接打包在 APK 内，`dladdr` 给出
`/data/app/…/base.apk!/lib/x86_64/libguardx.so`，旧实现把它当普通路径 `open()`，必然失败 →
C6/D4 在**绝大多数新设备**上失效。

**修法**：新增 `ag_self_open`：路径含 `!` 时打开 APK、解析中央目录定位 `lib/...so` 条目、
算出条目数据偏移作为 ELF 起点，再走同一套节表定位逻辑。只处理 Stored 条目（这类库必然
不压缩并按页对齐），遇到压缩/ZIP64 才降级。**不引入 inflate**——为一个不可能出现的分支
增加体积与攻击面不划算。

### 3. 守卫库的静态缓冲区在多线程下会互相踩

**问题**：ZIP 解析用了一个 66 KB 的 `static` 缓冲区、哈希用了一个 8 KB 的 `static`
缓冲区。D4 的看门狗线程每 3 秒调一次自检，Java 侧也可能调用 `Native.intact`；两者共用
同一块缓冲区会互相踩——轻则解析失败降级，重则算出错位偏移、摘要不匹配，把**正常的应用
杀掉**。

**修法**：66 KB 缓冲区改 `__thread`（线程局部），8 KB 的挪到栈上。修后三个应用在模拟器上
安装启动正常、无降级日志，篡改反例仍能正确命中（说明摘要算得对）。

### 4. 降级日志每 3 秒刷屏

**现象**：D4 的看门狗每 3 秒调一次 `ag_intact()`，降级提示随之每 3 秒打一行，实测每个进程
每 3 秒一条，把有效信息淹没。

**修法**：降级提示改用「只打一次」的 `AG_LOG_ONCE`。修为 1、2 之后实测已不再出现该提示
（即摘要真的算出来了）。

### 5. A19 体积统计口径错误（日志显示把 DEX 缩成了 22 KB）

**现象**：`A19 字符串池垃圾注入：… ；5012264 → 22528 字节（增加 -4989736）`——看起来像把
5 MB 的 DEX 毁成了 22 KB，与产物实际（增大了 22 KB）相反。原因是把「增量」当成了「处理后
大小」。

**修法**：如实累加增量并打印 `before → before+delta`。

### 6. B8 没有搬迁 C2 的库载荷（最大的 assets 条目仍留在顶层）

**现象**：B8 只搬 B1 的 DEX 载荷，C2 加密的原生库仍以顶层 `assets/<词>_<hex>.<ext>` 存在，
而它往往是**整个 APK 里最大的 assets 条目**（termux 的 `libtermux.so` 加密后 28 MB）。脱壳
脚本「按体积抓最大条目」一抓就中，「顶层不再直接暴露载荷」直接落空。

**修法**：B8 同时搬迁 C2 的库载荷进同一容器树（B3 在 B8 之后生成壳，读的是 `soItem.Asset`，
壳侧零改动）。修后三个产物顶层载荷条目数均为 **0**。

### 7. B1 与 C2 的载荷密钥互相不一致（由 e2e 的 C2 功能集抓到）

**现象**：启用 `-so-encrypt` 时报
`B3（ClassLoader 接管）执行失败: C2 的 SO 载荷密钥与 B1 载荷密钥不一致，无法由同一个壳解密`。
根因是第 8 条修复引入的回归：密钥留空时改为随机生成，而 B1 与 C2 是两个独立 Pass、
各自解析一次，两次随机必然不同。

**修法**：载荷密钥**每次运行只解析一次**并存入 `Artifact` 共享，B1/C2 复用同一结果。
新增单元回归 `TestB1AndC2SharePayloadKey`（已做正反例验证：绕过共享即失败）。

### 8. `verify-products.py` 自身的三类缺陷

- **变量遮蔽**：A17 断言里写 `with zipfile.ZipFile(self.apk) as zf:`，遮蔽了 `_run(zf)` 的同名
  参数并在 with 结束时关掉它，后续任何用 `zf` 的断言（如 E4 渠道）都抛
  `Attempt to use ZIP archive that was already closed`。改用传入的 `zf`。
- **四条在加壳场景下不成立的断言**：A13/A19（业务 DEX 已加密，`classes.dex` 只是壳）、
  A18（真实应用自己就声明 `android.permission.*`，不能断言「没有系统权限名」）、
  C2（B8 容器化后载荷不再匹配顶层命名）。已改为 B1 感知的**显式跳过并给出理由**，而不是
  静默通过或误报。

### 10. 第二轮审计（Pass 编排与配置）发现的三条缺陷

> 这个审计面此前失败过两次（一次上游超时、一次 agent 没产出内容），第三次才拿到报告。

- **B2+B3 但未启用 B1 → 产物启动即崩，工具却报成功**（最严重）。B2 只要看到 B3 启用
  就让壳生成对 `Lcom/apkguard/shell/Loader;` 的调用，而 B3 在没有加密载荷时会提前返回、
  **不注入 Loader 类体**。实测 `-enable B2,B3` 的产物：`classes.dex` 引用了 Loader，
  `class_defs` 里却只有 App —— 应用一启动就 `NoClassDefFoundError`。
  修法两道防线：依赖表补 `B3→B1`；B2 只在 `B3 && B1` 时才写 LoaderClass。
  B3 原本「无载荷时静默降级」的分支也改为明确报错（那不是安全跳过，而是启用了
  一个无事可做的功能项）。已加回归（正反例都验过）。
- **`C6.libs` 统计口径错误**：报的是 `len(native.Prebuilt())`（恒为 3），而 C1 只会
  给「原 APK 覆盖的 ABI」注入守卫库。实测 termux 实际只注入 1 个，报告却称覆盖 3 个 ABI。
  改为读 C1 记录的注入数（按文件名数会因 C7 改名而得到 0，这一点也踩过）。
- **A6 的注释与实现三处互相矛盾**：`passes.go` 还写着「A6 不注册」、`cff.go` 写着
  「只定义类型不在 Registry 注册」、`config.go` 的 Note 说「实现已就位但暂未开放 …
  会触发宽值类型冲突」——而 A6 早已注册、已在三个真实应用上实测可用。这类注释会让
  维护者把已修好的功能删掉，属高危误导，已全部更正。

顺带修掉两处「报告与实现不符」：A13 在 `ClassPadCount<=0` 时静默返回（现在留一行 Note）；
A14 的 Desc 声称统一 `flag_bits`（实际不改，因为 UTF-8 名称位必须保留），并补上
「清除 0x5455/0x000a 时间类扩展字段」——否则这些记录里的原始打包时刻会让时间统一失效。

### 11. 第三轮审计遗留的四条「潜在隐患」全部修掉

上一轮审计报告末尾列了四条「不影响当前产物正确性、但值得处理」的问题，本轮逐条修完：

- **Level 分层是死抽象**。`LevelDex`/`LevelFinal` 从未被任何 Pass 返回（37 个 Pass
  全是 `LevelZip`），`Run` 里的 `sort.SliceStable(by In())` 是空操作，却给人一种
  「层次会自动排序」的错觉——一旦有人给某个 Pass 改成 `LevelDex`，它会被静默移到所有
  ZIP 层之后，而真正的约束（A14 在 B1 之后、B4 在 B1 之前）并不体现在 Level 上。
  改为：**删除那处排序**，执行顺序明确就是注册顺序；Level 变成一份**被校验的声明**
  （`pipeline.CheckLevelChain`：起点必须是 LevelZip、相邻 Pass 的 Out 必须接上下一个的
  In），声明与顺序不一致时直接报错而不是悄悄重排。
  同时把 passes.go 注释里的顺序约束**变成可执行断言**（`order_contract_test.go`：
  20 条 before/after 关系 + 「A14 在所有新增条目的 Pass 之后」+「A15 必须最后」）。
  已做反例验证：把 B4/B1 注册顺序对调，测试立刻报错。
- **`B2.shell_bytes` 语义随 B1 是否启用而变**。并库成功时那是整份 `classes.dex`（含全部
  业务类），失败时才是纯壳——同一个键含义不同，报告与产物断言都没法可靠依赖它。
  改为恒报**纯壳 DEX**大小，并新增 `B2.entry_bytes`（写入条目的总长度）与 `B2.merged`；
  Note 里两者都写明。实测：并库时 `shell_bytes=1636 / entry_bytes=8280`，不并库时两者相等。
- **C1 对 E1 的依赖是无条件的**。C1 需要签名证书摘要作派生输入，而摘要有两个来源
  ——E1 签名时读密钥库，或用 `-sig-hash` 直接给出。依赖表却无条件要求 E1，把「先加固、
  后由发布流水线签名」这种正常用法挡在门外。改为**条件式依赖**（只有没给 `-sig-hash`
  时才要求 E1），错误信息同时给出两条出路。实测：`-disable E1 -enable ...C1 -sig-hash <sha256>`
  现在能跑通并产出；不给 `-sig-hash` 仍被明确拒绝。
- **`TestImplementedMatchesRegistry` 的盲区**。它为不误报而把 E1/E2/E3/E5 无条件当作
  已实现，「实现被删掉、implementedIDs 还留着」发现不了。补上功能性守卫
  `internal/pipeline/auditfix_impl_test.go`：E1/E2/E3 各做正例+反例（判据取自产物字节
  ——签名块 magic / v1 MANIFEST.MF / 条目数据偏移对齐 / 自检报错），删掉 sink 对应分支
  测试必失败（已做反例验证）；E5 由 `cmd/apkguard/batch_test.go` 真跑目录批量覆盖，
  并在该测试的注释里写明「新增同类项必须同时补守卫」。

### 复现脚本

本轮装机复验用的脚本都在 `scripts/` 下，需在 WSL 里跑（Windows 侧没有 JDK/SDK）：

| 脚本 | 作用 |
|------|------|
| `wsl-emu-start.sh` | 启动 AVD `anx36` 并等待开机完成 |
| `wsl-emu-build.sh` | 构建 linux 二进制 + 对三个应用做全选项加固，产物落 `realworld/emu-out/` |
| `wsl-emu-test.sh` | 干净安装 + 启动 + 崩溃/存活观测 |
| `wsl-emu-final.sh` | 安装启动 + 产物断言（调用 `verify-products.py`） |
| `wsl-emu-termux.sh` | Termux 终端里真实执行命令，验证解密后的 DEX 与 native 库 |
| `wsl-emu-tamper.sh` | **反例**：篡改已安装库的 `.text`，验证 D4 看门狗真的终止进程 |
| `wsl-native-rebuild.sh` | 重编三个 ABI 的原生库并校验 `.agexpect` 摘要（改 C 源码后必跑） |
| `wsl-e2e.sh` / `wsl-ci-local.sh` | 在 WSL 里跑项目的端到端 / 本地 CI |

调用方式统一为：`wsl.exe -d Ubuntu-26.04 -- bash /mnt/c/Users/admin/Desktop/apkguard/scripts/<脚本>`
