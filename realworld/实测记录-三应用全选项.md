# 三个真实应用的「全选项」加固实测记录

> 目标：对 **Termux / Dhizuku / RustDesk** 三个真实应用启用**全部已实现功能项**加固，
> 并修到它们都能在设备上正常运行。
>
> 环境：Android 16（API 36）x86_64 模拟器，已 root。
> 加固集合：31 个已实现项里的 29 个（**D2 Root 检测 / D3 模拟器检测除外**——
> 它们在这台 root 模拟器上命中属设计行为，实测单独确认过会拦停，见文末）。
> 签名：同一张测试密钥库；D5 绑定设备标识（采集方式见 §D5）。
> 结果：**三个应用全部正常运行**（进程存活、主界面 resume、日志零结构性错误）。

| 应用 | 版本 | 规模 | 结果 |
|---|---|---|---|
| Dhizuku | 2.12.0（`com.rosan.dhizuku`） | 1 DEX / 3292 类 / 无原生库 | ✅ 正常（进入首启设置流程） |
| Termux | 0.119.0-beta.3（`com.termux`，x86_64） | **30 DEX** / 8576 类 | ✅ 正常（TermuxActivity resume） |
| RustDesk | 1.4.9（`com.carriez.flutter_hbb`，x86_64） | 1 DEX（4.1 MB）/ 5449 类 / Flutter | ✅ 正常（MainActivity resume，UI 已渲染） |

复现命令（`harden-all.sh` 即全选项 + `-bind-device`，见下文）：

```bash
apkguard -in <app>.apk -out <out>.apk -ks <ks> -ks-pass <pass> \
  -enable "A1,A2,A3,A4,A5,A8,A9,A10,A11,A12,A13,A14,B1,B2,B3,B4,\
C1,C4,C5,C6,D1,D4,D5,E1,E2,E3,E4,E5,E6" \
  -bind-device <该应用自己报出的设备标识> -channels official
```

## 本轮修复的缺陷（全部在真机上复现过，并补了回归测试）

### 1. `android:appComponentFactory` 未处理 → 启动即 `ClassNotFoundException`

**现象**（三个应用都有这个属性，全部启动即死）：

```
E LoadedApk: java.lang.ClassNotFoundException:
    Didn't find class "androidx.core.app.CoreComponentFactory"
```

**根因**：该工厂类由 `LoadedApk.makeApplicationInner` 实例化，时机在壳的
`attachBaseContext`（我们接管 ClassLoader 的地方）**之前**；那时业务 DEX 还在
加密载荷里，工厂类根本不存在。

**修法**（`passes/shell.go`）：把 `android:appComponentFactory` 指向框架默认实现
`android.app.AppComponentFactory`。保留「按类名实例化组件」的标准语义，丢失的只有
androidx 的 `CompatWrapped` 包装特性。

---

### 2. A1 分配新类名时把「默认包」算成空前缀 → 非法描述符

**现象**：Dhizuku 加固后 DEX 被官方工具判非法：

```
dexdump E: Failure to verify dex file 'classes.dex': Invalid type descriptor: '[[auo;'
```

**根因**（`passes/rename.go`）：新名由 `包前缀 + 短名 + ";"` 拼成，而包前缀取
`LastIndex('/')` 之前的部分——**默认包**的类（混淆过的应用里极常见，如 `Lkf;`）
算出空串，于是生成 `auo;`（**缺开头的 `L`**），数组形式更会变成 `[[auo;`。

**修法**：`classPkgOf()`，默认包返回 `"L"`。回归测试：
`internal/passes/rename_defaultpkg_test.go`。

---

### 3. A1 的 `handler_off` 在类型索引跨 ULEB 边界时算错 → 整个 DEX 被 ART 丢弃

**现象**：

```
dexdump E: Failure to verify dex file: Bogus handler offset: 6
```

**根因**（`internal/dex/insn.go`）：`Encode` 用「把内存里的 handler 重新编码一遍」
来推算旧偏移，但那时**捕获类型的索引已经被改名改写**；索引跨过 ULEB128 的
127→128 边界时，重编码得到的布局不再是文件里的布局，映射查不到就**静默沿用旧
偏移**。索引小的应用（如本项目测试应用）永远碰不到这个边界。

**修法**：解析时记录每个处理器在原始字节里的真实偏移（`CodeItemFull.HandlerOffs`），
映射的键始终取字节事实；查不到时**直接 panic** 而不是静默产出非法 DEX。
同时把守卫改成用「解析出的字节事实」校验（此前它用同一个编码器重算，等于自己
校验自己，恒为真）。回归测试：`TestEncodeHandlerOffAfterTypeIndexGrowth`。

---

### 4. A1 不重写跨 DEX 引用 → `NoClassDefFoundError`

**现象**（Termux：原生就有 30 个 DEX）：

```
NoClassDefFoundError: Failed resolution of: Lcom/termux/shared/termux/TermuxConstants;
    ... DexPathList[[dex file ".../d0.dex", ... "d74.dex"]]
```

**根因**：A1 的改名计划只由「**本 DEX 定义**的类」构成。于是「A 定义、B 引用」的
类在 B 里仍写着旧名。RustDesk 一直没暴露这个问题，是因为它是**单 DEX**，那 16 份
分片是 B4 在**改名之后**才拆出来的。

**修法**：`Plan()` 把 `ClassMap` 中「非本 DEX 定义」的条目（纯引用）也纳入计划，
并为它们派生数组描述符。回归测试：`rename_crossdex_test.go`。

---

### 5. A1 的成员改名在跨 DEX 时不一致 → `NoSuchFieldError`

**现象**：

```
NoSuchFieldError: No field TERMUX_HOME_DIR of type Ljava/io/File;
    in class Lcom/termux/shared/termux/dt;
```

**根因**：成员改名按「名称字符串」生效，而各 DEX 各自决策、各自生成新名：
定义方改成 `a`、引用方仍是 `TERMUX_HOME_DIR`。

**修法**：成员改名也做成**全局决策**——① 每个 DEX 先各自表态；
② 只保留「所有用到它的 DEX 都同意改」的名称；③ 由一份全局生成器统一命名；
④ 对「有 DEX 不同意」的名称**显式全局保留**（`MemberKeep`，只排除在
`MemberMap` 之外是不够的：那样同意的一方仍会自行改名）。回归测试：
`rename_crossdex_member_test.go`。

---

### 6. A1 改名了「覆写框架方法」的方法 → `AbstractMethodError`

**现象**（Dhizuku）：

```
AbstractMethodError: abstract method "void android.view.View$OnAttachStateChangeListener
    .onViewAttachedToWindow(android.view.View)" on receiver ...
```

**根因**：框架接口的实现在本 DEX 里**没有调用点**（调用方是系统），
「引用者是否都在改名集合里」这条判据看不见它；而 `onViewAttachedToWindow`
也不在硬编码白名单里。

**修法**：新增判据——类若（沿本 DEX 内的继承链传递地）继承了**本 DEX 之外**的
父类型，则它的非私有实例方法「可能覆写看不见的方法」，不改名
（`hasInvisibleSuper` + `mayOverrideInvisible`）。
回归测试：`rename_override_test.go`。

---

### 7. A1 改名了「引用自不可见父类的成员」 → `NoSuchMethodError`

**现象**（Termux 的 `hiddenapibypass` 库）：

```
NoSuchMethodError: No virtual method aez(Ljava/lang/String;)Ljava/lang/Class;
    in class Lorg/lsposed/hiddenapibypass/nc; or its super classes
    at org.lsposed.hiddenapibypass.nc.loadClass(Unknown Source:15)
```

**根因**：`nc` 继承 `dalvik.system.PathClassLoader`，它调用 `loadClass` 时**静态
类型是自己的类**，于是 method_ids 里写的是 `Lnc;->loadClass(String)Class`——看起来
像应用内部方法，实际是**从框架父类继承来的**，改名后解析不到。

**修法**：引用若在**可见继承链**里找不到声明，就说明声明在看不见的父类型里，
该名称必须保留（`resolvesVisibly`）。回归测试：`rename_inherited_test.go`。

---

### 8. A1 改名了被布局 XML 按名字引用的类 → `InflateException`

**现象**（Termux）：

```
InflateException: Binary XML file line #8 in com.termux:layout/activity_termux:
    Error inflating class com.termux.app.terminal.TermuxActivityRootView
```

**根因**：自定义 View 以**字符串**形式写在布局里，与 DEX 的类型引用无关；
改类名不会同步改到它。

**修法**：新增「被动引用扫描」——把 `AndroidManifest.xml`、`res/**/*.xml`、
`resources.arsc` 字符串池与 `assets/**` 里**确实存在对应类**的类名加入保留集
（`passiveClassRefs`）。只保留真实存在的类，避免把普通字符串误当类名。

## D5 设备标识的正确采集方式（实测）

`adb shell settings get secure android_id` **取不到**应用内看到的那个值：
Android 8.0 起 `ANDROID_ID` 按「应用签名 + 用户 + 设备」作用域化。实测同一设备：

| 取值方式 | 值 |
|---|---|
| `adb shell settings get secure android_id` | `2ad89c08d44767b6` |
| 应用内 `Settings.Secure.getString(cr, "android_id")` | `32a023838d4d9174` |

因此 D5 的绑定值必须**由应用自己报出来**：用 `-debug-shell` 出排障版，在目标设备上
跑一次，`adb logcat -s APKGUARD-D5` 打印的就是要绑定值（本轮已加入该日志）。
作用域是按**签名证书**的，所以同一张密钥库签的多个应用取到同一个值。

| 单独启用 | 结果 |
|---|---|

| 只开 D3（模拟器检测） | 进程被拦停 ✅ 设计行为 |

这台模拟器已 root，且本身就是模拟器，因此**全选项**运行时这两个目标必须排除，
否则应用会被按设计拦停——这不是缺陷。真机上应全开。

## 剩余限制（如实说明）

- **A1 在成员改名上偏保守**：多 DEX 应用里，跨 DEX 共用的成员名会被一致保留；
  继承链含框架类型的类，其非私有实例方法也不改名。**类改名不受影响**
  （Dhizuku 3047 / Termux 372 / RustDesk 2785 个类），但方法/字段改名比例下降
  （RustDesk 仅 15 个方法、0 个字段）。这是「宁可少改，不可改错」的取舍：
  真实混淆器（R8/ProGuard）靠**库方法表**判断覆写关系，本工具没有该信息，
  只能用保守判据替代。
- 上述判据仍可能漏掉「通过字符串名反射调用」与「assets 里拼出来的类名」等
  被动引用形式；已覆盖 XML / 资源表 / assets 的类名扫描，但无法穷尽。

## 第二轮：新增功能（A15 / B8 / 包压缩 / 新 A2）后的全选项复验

> 版本变化：**RustDesk 1.4.9 → 1.5.0（universal）**；功能集合新增 A15（巨型 Manifest
> 填充）、B8（载荷容器化）、`-package-shrink`（A1 包名压缩），A2 的密文改为 Base64，
> A9/A10/A12 的垃圾条目质量提升。
> 环境不变：Android 16（API 36）x86_64 模拟器，已 root；D2/D3 仍按设计排除。
> 结果：**三个应用全部正常运行**，并查出 4 个新缺陷（1 个致命告警级 + 3 个「装上就崩」级）。

### 新增缺陷与修法

#### 1. 注入类的 `<clinit>` 缺 `ACC_CONSTRUCTOR` → ART 每次加载都告警

**现象**：

```
W/...: <clinit> didn't have expected constructor access flag
       in class com.apkguard.nativebridge.Native in dex file .../base.apk
```

**根因**（`internal/dex/assemble.go`）：生成入口只给 `<init>` 补了
`ACC_CONSTRUCTOR`（0x10000），`<clinit>` 漏了。**修法**：两个名字都补；
回归测试 `TestInjectedClinitHasConstructorFlag`。

#### 2. `-package-shrink` 把所有类压进默认包 → `IllegalAccessError`

**现象**（Termux，启动即崩）：

```
java.lang.IllegalAccessError: Illegal class access: 'ac' attempting to access
    'com.termux.app.utils.CrashUtils$1' (declaration of 'ac' appears in .../d39.dex)
```

**根因**：A1 的保留规则把 `$` 内部类（`CrashUtils$1`）连同其外层类留在原包，
而 `-package-shrink` 把其余可改名类统统压进**默认包**。于是原本同包的
package-private 访问变成了跨包访问。

**修法**（`internal/passes/rename.go`）：改为**按包压缩**——每个原包整体映射为
一个无意义短包名（`Lpa/`、`Lpb/`…），原来同包的类压缩后仍然同包；**含保留类的包
整体保持原包名**（否则搬走的类再也访问不到留下的 `$` 内部类）。
回归测试：`TestPackageShrinkCompressesPackageNames`、
`TestPackageShrinkKeepsPackagesWithKeptClasses`。
> 注：`internal/dex` 里的 `ShrinkPackage`（单 DEX 粗粒度开关）保留为库 API，
> 但其注释已明确写出这个坑，CLI 不再使用它。

#### 3. ServiceLoader 的两半类名只存在于资源里 → `Main dispatcher is missing`

**现象**（RustDesk 1.5.0，Flutter，UI 首次 attach 即崩）：

```
java.lang.ExceptionInInitializerError
Caused by: java.lang.IllegalStateException: Module with the Main dispatcher is
  missing. Add dependency providing the Main dispatcher, e.g.
  'kotlinx-coroutines-android' ...
```

**根因**：`META-INF/services/` 有**两半**引用，都只写在资源里、DEX 中没有对应
字符串常量，因此 `reflectedClasses` 看不见：

| 位置 | 本例的值 | 含义 |
|---|---|---|
| 文件**名** | `META-INF/services/j3.t` | 服务接口类名（R8 混淆后的 `j3.t`，即 `kotlinx.coroutines.internal.MainDispatcherFactory`） |
| 文件**内容** | `f3.a` | 提供者类名（`AndroidDispatcherFactory`） |

改任意一半，`ServiceLoader.load` 都会加载不到实现。

**修法**（`internal/passes/rename.go` 的 `passiveClassRefs`）：新增
`META-INF/services/` 分支，把**文件名**与**每行内容**（跳过 `#` 注释）都加入
保留类；顺带把 `res/` 下的非 XML 资源也纳入类名扫描。
回归测试：`TestServiceLoaderProviderIsNotRenamed`。

#### 4. A10 注入假 `MANIFEST.MF` → v1 签名校验失败

**现象**（RustDesk 1.5.0，`ServiceLoader` 读 `META-INF/services` 时）：

```
java.lang.SecurityException: Invalid signature file digest for Manifest main attributes
  at sun.security.util.SignatureFileVerifier.processImpl
  at java.util.jar.JarVerifier.processEntry
  at libcore.io.ClassPathURLStreamHandler$ClassPathURLConnection.getInputStream
  at java.util.ServiceLoader$LazyClassPathLookupIterator.parse
```

**根因**：A10 曾注入 `META-INF//MANIFEST.MF`、`META-INF/./MANIFEST.MF`、
`meta-inf/MANIFEST.MF`。ZIP 条目名在 Android 的 `JarFile`/`ZipUtils` 里是
**大小写不敏感**地比较 `META-INF/MANIFEST.MF`，于是校验器读到了**假 manifest
的主属性**，`.SF` 里的摘要自然对不上。触发链是「ServiceLoader 经 JarFile 读资源
→ 触发 v1 校验」——**只有同时用到 ServiceLoader 的应用才会暴露**。

**修法**（`internal/passes/passes.go`）：新增 `manifestCollision(name)` 守卫，
把条目名归一化（折叠重复斜杠、消解 `.`/`..` 段、统一大小写）后，拒绝任何
`META-INF/MANIFEST.MF` 或 `META-INF/*.{SF,RSA,DSA,EC}`；A10 与 A12 的注入
一律过这道守卫，畸形名改用 `.MFx` 之类不撞名的形态。
回归测试：`TestManifestCollisionGuard`、`TestJunkEntriesNeverInjectManifestCollision`。

### 本轮仍未做

- **B3 的 memfd / InMemoryDexClassLoader 路径**：当前 B3 用 `DexClassLoader`
  把解密后的 DEX 落到应用私有目录。内存加载需要多 DEX 场景下的
  `InMemoryDexClassLoader(ByteBuffer[], parent)`（API 29+ 才支持多 buffer），
  属可用性/兼容性权衡，尚未落地。
- **A8 诱饵组件写入 Manifest**：诱饵类已注入，但尚未把它们声明成组件
  （需要 AXML 元素插入能力，当前 axml 包只做字符串池/属性改写）。
